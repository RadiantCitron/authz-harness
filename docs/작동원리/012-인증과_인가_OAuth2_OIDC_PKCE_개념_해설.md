## 1부. [Q1] 인증(AuthN) 구현 수준, JWT, OAuth vs OIDC, 그리고 실용성 평가

### 1. 인증(AuthN)을 어느 정도 수준으로 구현했나?

단순한 테스트용 흉내가 아니라, **상용 수준의 기계 간(M2M: Machine-to-Machine) 인증 체계를 매우 탄탄하게 구현**하셨습니다.

실제 `internal/authn/` 모듈에 구현된 요소를 보면:
- **클라이언트 자격증명 인증 (`ClientRegistry`)**: 상수 시간 비교(`subtle.ConstantTimeCompare`)를 통한 타이밍 공격 방어 및 정지(`SUSPENDED`) 계정 차단.
- **비대칭 키 수명주기 관리 (`KeyManager`)**: Ed25519 키 생성, 무중단 키 회전(`RotateKey`), 긴급 키 폐기(`RevokeKey`), `kid` 기반 다중 키 검증.
- **토큰 검증 (`TokenVerifier`)**: 서명 위변조, 발급자(`iss`)/수신처(`aud`), 유효기간(`nbf`/`exp`), **1회성 리플레이 공격 방지(`ReplayLedger`)**.
- **위임 검증 (`ExchangeService`)**: RFC 8693 기반 부모-자식 위임 계보(`act` 클레임) 및 세대 번호(`Epoch`) 연쇄 무효화.

### 2. JWT가 핵심인가?

**네, 맞습니다.** JWT가 인증(AuthN)과 인가(AuthZ)를 잇는 **핵심 매개체**입니다.

- 정확히는 **Ed25519 전자 서명**이 신뢰의 근거이고, **JWT(RFC 9068 포맷)**는 그 신원(`sub`), 고유번호(`jti`), 권한 상한선(`scope`), 위임 족보(`act`)를 표준 규격에 담아 검문소(PEP)까지 안전하게 실어 나르는 **운반체(Carrier)**입니다.

### 3. OAuth는 인가용, OIDC는 인증용인데 둘 다 한 것인가?

**엄밀히 구분하면: OAuth 2.1(인가 + M2M 인증)은 깊게 구현하셨지만, OIDC(OpenID Connect)는 구현하지 않으셨습니다.**

- **OIDC (OpenID Connect)가 아닌 이유**:
  - OIDC는 **"사람(최종 사용자)의 브라우저 로그인"**을 위한 표준입니다. 핵심 산출물은 `ID Token`이며, 로그인 화면 리다이렉트(Authorization Code Flow + PKCE), `/userinfo` 엔드포인트, SSO 등이 포함됩니다.
  - 현재 프로젝트에는 사람 로그인 UI나 `ID Token`이 없습니다.
- **현재 구현하신 것**:
  - **OAuth 2.1 기반의 기계 간(M2M) 클라이언트 인증 + Access Token(RFC 9068) + Token Exchange(RFC 8693)**입니다.
  - 즉, **"인증(AuthN)을 구현하신 것은 맞지만, 그것은 OIDC가 아니라 OAuth 2.1의 클라이언트 인증 및 토큰 검증 프로파일"**입니다.

### 4. 혼자 쓰려고 한다면 이 정도 구현은 어느 정도 쓸만한가?

솔직한 엔지니어링 관점에서 **장단점이 뚜렷합니다.**

#### ① 보안·신뢰성 측면: "1인용으로는 과분할 만큼 최상급"
- 시중에 나와 있는 대부분의 오픈소스 AI 에이전트들도 보통 단순 API 키나 디렉터리 격리 정도만 구현하지, **Ed25519 서명 + 축소 위임(Downscoping) + 5대 승인 바인딩 + SHA-256 감사 해시 사슬**까지 갖춘 곳은 거의 없습니다.
- 혼자 쓰면서 에이전트에게 내 로컬 파일 수정이나 외부 네트워크 호출을 맡길 때, **"에이전트가 폭주하거나 프롬프트 인젝션을 당해도 내 시스템을 망가뜨리지 못하게 막는 안전장치"**로서는 최상급입니다.

#### ② 실용성·사용성 측면: "수동 CLI 조작은 번거로움"
- 혼자 일상적으로 쓰기에는 `grant create` ➔ `token issue` ➔ `token exchange` ➔ `approval grant` (특히 `jti`와 `arg-hash` 복사) 과정이 수동 CLI 위주라 번거롭습니다.
- 따라서 실전에서 혼자 편하게 쓰시려면, 현재의 견고한 코어(`internal/`) 위에 **이 명령어들을 자동으로 엮어주는 오케스트레이터 래퍼(Wrapper)나 간단한 승인 프롬프트 UI**를 얹어서 쓰시면 보안성과 실용성을 모두 갖춘 매우 훌륭한 개인용 에이전트 실행 환경이 됩니다.

## 2부. [Q2] 에이전트 환경에서의 충분성과 OIDC의 진짜 용도

1. **에이전트용으로는 충분한가?**
   - **네, 충분하고도 넘칩니다.**
   - 화면 없이 백그라운드에서 돌아가는 에이전트 프로세스끼리 신원을 확인하고 권한을 쪼개어 위임(Token Exchange)하는 데에는 지금 구현하신 **OAuth 2.1 M2M (RFC 9068 Access Token + RFC 8693 Token Exchange)** 방식이 업계 표준이자 정석입니다.

2. **OIDC는 일반 사용자의 웹 인증용인가?**
   - **네, 맞습니다.**
   - OIDC(OpenID Connect)는 사람이 웹 브라우저나 앱에서 아이디/비밀번호를 치거나 *"Google로 로그인"* 같은 버튼을 눌러 로그인할 때, **"방금 로그인한 사람이 홍길동 맞다(`ID Token`)"**를 증명하는 **사람(최종 사용자) 대면 인증 표준**입니다.
   - 나중에 이 시스템 위에 여러 사람이 접속하는 웹 관리 대시보드(SaaS)를 붙이는 게 아니라면, **에이전트 실행 엔진 내부에서는 OIDC가 전혀 필요 없습니다.** 지금 구조가 딱 맞습니다.

## 3부. [Q3] OIDC PKCE 구조와 현재 인증 체계의 비교

보안 원리(철학) 면에서는 아주 비슷해 보이지만, **실제 작동 구조와 목적은 다릅니다.** "PKCE의 간략한 버전"이라기보다 **적용 환경이 달라서 쓰는 표준 방식이 다른 것**입니다.

### 1. PKCE와 현재 하네스 인증의 결정적 차이

| 구분 | OIDC + PKCE (RFC 7636) | 현재 하네스 (`authz-harness`) |
|---|---|---|
| **대상 환경** | 모바일 앱, 웹 브라우저(SPA) 등<br>**비밀번호(`client_secret`)를 숨길 수 없는 곳** | 백엔드 서버, 로컬 CLI 프로세스 등<br>**비밀번호(`client_secret`)를 안전히 보관할 수 있는 곳** |
| **핵심 인증 수단** | 매번 즉석에서 만드는 일회용 난수(`code_verifier`)와 그 해시(`code_challenge`) | 사전에 등록된 고정 **`client_secret`** (`ClientRegistry`) |
| **교환 대상** | 임시 `Authorization Code` ➔ `Access Token` | `부모 JWT` ➔ 권한이 축소된 `자식 JWT` (`token exchange`) |

즉, PKCE는 **"브라우저에 비밀번호(`client_secret`)를 심어두면 해커가 소스코드에서 훔쳐가니까, 비밀번호 없이 일회용 난수 해시로 증명하자"**는 목적으로 만든 브라우저/앱 전용 우회로입니다.  
반면 현재 하네스는 백엔드/CLI 환경이므로 정석대로 **`client_secret`으로 인증**합니다.

### 2. 그런데 왜 구조가 같아 보일까? (공통된 보안 철학)

*"구조가 같은 걸로 보인다"*고 느끼시는 이유는, **두 시스템이 공유하는 핵심 보안 원리가 똑같기 때문**입니다:

1. **2단계 교환 구조**:
   - **PKCE**: 1단계(임시 코드 발급) ➔ 2단계(검증값을 대고 진짜 토큰으로 교환)
   - **하네스**: 1단계(`token issue` 부모 토큰 발급) ➔ 2단계(`token exchange` 자식 토큰으로 교환)
2. **해시 바인딩을 통한 탈취/바꿔치기 방어**:
   - **PKCE**: 미리 보낸 해시(`code_challenge`)와 나중에 낸 원본(`code_verifier`)이 일치해야만 토큰을 내주어, **중간에서 코드를 가로챈 공격자를 막습니다.**
   - **하네스**: 승인 장부에 미리 걸어둔 해시(`ArgHash`)와 실행 시 낸 데이터의 해시가 일치해야만 통과시켜, **중간에서 내용을 바꿔치기하는 공격자(Confused Deputy)를 막습니다.**

## 4부. [Q4] `client_secret` 저장소 문제와 "저장 못한다"는 말의 맥락

**`client_secret`을 코드에 하드코딩했느냐 DB/환경변수로 빼느냐는 단순한 구현/저장소 문제일 뿐, 백엔드 환경에서 `client_secret`을 쓰는 것 자체는 지극히 정상적인 표준입니다.**

### "`client_secret`을 저장 못한다"의 진짜 맥락

이 말은 **내 서버(백엔드)**가 아니라, **웹 브라우저(React/Vue)나 스마트폰 앱(iOS/Android)** 환경에서 나오는 이야기입니다.

1. **브라우저/모바일 앱은 "남의 컴퓨터"에서 실행됩니다**:
   - 웹 브라우저(SPA)를 열면 HTML과 자바스크립트 파일이 **사용자 컴퓨터로 통째로 다운로드**됩니다.
   - 스마트폰 앱도 앱스토어에서 **바이너리가 사용자 폰으로 다운로드**됩니다.
2. **비밀번호를 적어두면 100% 털립니다**:
   - 만약 프론트엔드 코드 안에 `client_secret = "secret-1234"`라고 넣어두면, 해커나 일반 사용자가 브라우저에서 **F12(개발자 도구)만 열어도 비밀번호가 평문으로 그대로 보입니다.** 모바일 앱도 디컴파일하면 바로 뚫립니다.
   - 즉, **"클라이언트 프로그램이 불특정 다수의 기기에서 실행되므로, 비밀값(`client_secret`)을 남들에게 들키지 않고 안전하게 보관(저장)할 물리적 방법이 없다"**는 뜻입니다.

### 그래서 PKCE가 필요했던 것 vs 우리 시스템에 필요 없는 이유

- **웹 브라우저 / 모바일 앱 (Public Client)**:
  - `client_secret`을 저장할 수 없으니, **비밀번호 없이** 매번 즉석에서 만든 일회용 난수 해시(**PKCE**)로 증명해야 합니다.
- **우리 시스템 `authz-harness` (Confidential Client)**:
  - 내 서버, 내 터미널, 백엔드 프로세스 등 **내가 통제하는 안전한 공간**에서 실행됩니다.
  - 따라서 `client_secret`을 환경변수나 비밀 금고에 안전하게 저장할 수 있으므로, **굳이 PKCE 같은 우회로 없이 정석대로 `client_secret`을 쓰는 것**이 맞습니다.

## 5부. [Q5] PKCE의 본질 — 일회용 동적 시크릿 한 단계

**PKCE는 거창한 마법이 아니라, 일회용 동적 시크릿 한 단계를 더 붙인 것에 불과합니다:**

1. 고정된 `client_secret`을 저장해 둘 수 없으니까,
2. 요청할 때마다 클라이언트가 **즉석에서 일회용 임시 비밀번호(`code_verifier`)**를 하나 만들고,
3. 그 해시값(`code_challenge`)을 인증 서버에 먼저 던져서 **"이번 요청의 임시 비밀번호는 이거다"**라고 매핑해 놓은 뒤,
4. 나중에 진짜 토큰을 교환할 때 아까 만든 임시 비밀번호 원본을 내밀어 확인받는 **'일회용 동적 시크릿' 한 단계를 더 붙인 것**입니다.

즉, **안전하게 비밀값을 저장할 수 있는 백엔드/CLI 환경(`authz-harness`)에서는 굳이 이런 동적 매핑 단계를 거칠 필요 없이 바로 `client_secret`을 쓰는 것이 훨씬 깔끔하고 정석적인 설계**입니다.
