## 1. PAP는 1회용 토큰을 발급하는가? (JWT vs 1회용 Approval 티켓)

### 1-1. 사실: PAP는 토큰(JWT)을 발급하지 않는다
결론부터 말하면 **PAP는 토큰을 만들지 않습니다.** 토큰(OAuth 2.1 RFC 9068 Bearer Access Token)을 발급하는 곳은 [internal/authn/token/issuer.go](../../internal/authn/token/issuer.go)의 `TokenIssuer`입니다.

PAP([internal/authz/pap/service.go](../../internal/authz/pap/service.go))가 발급하는 것은 암호화 서명 토큰(JWT)이 아니라, 디스크 원장([.authz-state/public/grants_state.json](../../.authz-state/public/grants_state.json))에 한 줄 기록되는 **1회용 승인 티켓(`Approval`)**입니다.

### 1-2. 왜 둘을 명확히 구분해야 하는가?
- **토큰 (JWT)**: 주체(`sub`), 허용 범위(`scope`), 만료 시각(`exp`), 일련번호(`jti`)가 적혀 있고 비대칭 개인키(Zone A 특권)로 서명된 **이동형 신분증**입니다. 프로세스가 손에 쥐고 돌아다닙니다.
- **1회용 승인 티켓 (`Approval`)**: `apprv-`로 시작하는 식별자와 함께 「이 토큰 JTI가 이 자원에 대해 이 작업을 수행하는 것을 1회 허가한다」는 내용이 적힌 **원장 속의 정적 레코드**입니다. 프로세스가 들고 다니는 것이 아니라, 검문소(PEP) 뒤편 장부실에 꽂혀 있습니다.

## 2. 승인 티켓은 자식 프로세스에게 어떻게 전달되는가?

### 2-1. 사실: 자식 프로세스에게 티켓을 전달하지 않는다
자식 프로세스(워커)는 승인 티켓의 존재 자체를 모릅니다.

1. **승인 티켓의 저장 위치**:
   - 관리자(사람)가 `authz-harness approval grant`를 치면, 승인 티켓은 자식에게 가는 것이 아니라 공유 장부 파일([.authz-state/public/grants_state.json](../../.authz-state/public/grants_state.json))의 `approvals` 슬라이스에 기록됩니다.
2. **자식 프로세스가 들고 오는 것**:
   - 자식은 오직 부모에게 받은 **기존 JWT 토큰**과 **실행할 명령(예: `file:write`)**만 들고 작업을 요청합니다.
3. **대조와 1회용 소비 (Delete-on-Use)**:
   - 자식 내부에서 실행된 판정관(PDP)이 장부를 확인하여 매칭되는 유효 승인 티켓을 발견하면 `DecisionAllow`를 내립니다.
   - 검문소(PEP Gateway)는 작업을 실행하기 직전, 장부에서 해당 승인 티켓을 **즉시 삭제(`Delete-on-Use`)**합니다 ([internal/authz/state/approval.go](../../internal/authz/state/approval.go) · `ConsumeApproval`).

따라서 자식에게 티켓을 쥐어주는 것이 아니라, **관리자가 검문소 뒤편 공유 장부에 쪽지를 넣어두고 검문소가 확인 후 찢어버리는 구조**입니다.

## 3. 프로세스 간 통신(IPC)과 PEP의 실체

### 3-1. stdin 주입의 정확한 대상
- 부모 오케스트레이터(`orchestrate spawn`)는 자식 프로세스(`subagent worker`)를 띄울 때 커맨드라인 인자(`argv`)에 토큰을 노출하지 않기 위해(OS의 `ps`, `/proc` 조회에 의한 토큰 탈취 방지), **자식 프로세스의 `stdin` 파이프에 단일 JSON 프레임(`SubagentRequest`) 형태로 토큰과 요청을 주입**합니다 ([internal/orchestrator/spawner.go](../../internal/orchestrator/spawner.go)).

### 3-2. PEP 게이트웨이는 독립된 서버가 아니다
- PEP(Policy Enforcement Point)는 네트워크 데몬이나 외부 서버가 아닙니다.
- 자식 워커 프로세스([internal/cli/subagent.go](../../internal/cli/subagent.go)) 코드 내부에 라이브러리로 직접 링크되어 실행되는 Go 인터페이스 객체([internal/authz/pep/gateway.go](../../internal/authz/pep/gateway.go))입니다.
- 즉, 자식 프로세스가 `stdin`으로 JSON을 읽어 파싱한 뒤, 프로세스 내부 메모리에서 `pep.Gateway.Execute()` 함수를 직접 호출하는 방식입니다.

## 4. '관리자'의 정체와 프로세스가 PAP를 부르지 않는 이유

### 4-1. 누가 관리자인가?
- 이 프로그램에서 관리자는 백그라운드 프로세스가 아니라, **터미널 콘솔 앞에 앉아 CLI 명령어를 직접 입력하는 사람(운영자/보안담당자)** 또는 상위 운영 자동화 스크립트입니다.

### 4-2. 프로세스가 PAP에 직접 요청하지 않는 이유 (Fail-Closed)
- 워커 프로세스나 자식 프로세스가 작업 도중 임의로 PAP를 호출해 자기 자신에게 승인 티켓을 발급할 수 있다면, 사람 개입(Human-in-the-loop) 보안 통제는 완전히 무력화됩니다.
- 따라서 일반 워커는 Zone B 원장을 조회(PIP)만 할 수 있을 뿐, PAP를 실행하거나 원장을 변경할 수 없습니다.

### 4-3. 승인 필요 시 일어나는 실제 흐름
1. **자식의 시도**: 자식이 사람 승인이 필요한 고위험 작업을 요청합니다.
2. **차단 (종료 코드 18)**: PDP가 승인 쪽지가 없음을 확인하고 `DecisionAsk`를 내리며, 프로세스는 작업 수행 없이 **종료 코드 18 (`ExitApprovalRequired`)**로 즉시 종료됩니다.
3. **관리자의 승인**: 관리자(사람)가 콘솔에서 `authz-harness approval grant ...` 명령(PAP)을 쳐서 장부에 1회용 승인 티켓을 꽂아 넣습니다.
4. **재시도 및 통과**: 동일한 명령을 다시 실행하면, PDP가 방금 등록된 승인 티켓을 확인하여 허용하고 PEP가 이를 삭제한 뒤 작업을 집행합니다.

## 5. 프로그램 안에서 PAP를 부르는 4가지 경우

PAP([internal/authz/pap/service.go](../../internal/authz/pap/service.go))는 1회용 승인 외에도 원장의 정책을 조작하는 모든 순간에 호출됩니다:

| 번호 | 관리 작업 | CLI 명령어 | PAP 메서드 | 목적 |
|:---:|:---|:---|:---|:---|
| **1** | **상시 권한 부여** | `authz-harness grant create` | `CreateGrant()` | 주체에게 `file:read`, `file:write` 등의 허용 정책 등록 |
| **2** | **권한 즉시 회수** | `authz-harness grant revoke` | `RevokeGrant()` | 부여했던 권한(`Grant`) 취소 및 삭제 |
| **3** | **토큰 일괄 무효화** | `authz-harness grant bump-epoch` | `BumpEpoch()` | 탈취 의심 시 세대 번호를 올려 기존 토큰 전체 무효화 |
| **4** | **1회용 승인 발급** | `authz-harness approval grant` | `CreateApproval()` | 고위험 작업 1회 실행 허가 쪽지 등록 |

## 6. 승인 티켓 발급의 전제 조건과 플래그 규칙

### 6-1. PAP로 승인을 발급하려면 이미 등록되어 있어야 한다
- 맞습니다. PAP에서 1회용 승인(`CreateApproval`)을 만들려면, 원장에 해당 주체·액션·리소스에 대한 **기초 활성 권한(`Grant`)이 사전에 반드시 존재**해야 합니다 ([internal/authz/pap/service.go](../../internal/authz/pap/service.go) · `requireApprovalGrant`).
- 기초 Grant가 없으면 `ReasonNoActiveGrant` 에러로 승인 발급이 거절됩니다.

### 6-2. `--requires-approval` 플래그는 필수인가? 하드코딩 여부
- **반드시 명시해야 합니다. 코드상에 하드코딩된 액션별 강제 승인 규칙은 없습니다.**
- 파일 쓰기(`file:write`)나 네트워크 호출이라도 `grant create` 시 `--requires-approval` 플래그를 붙이지 않으면 일반 권한(`RequiresApproval: false`)으로 생성되어 사람 승인 없이 즉시 통과(ALLOW)됩니다.
- 또한 일반 권한에 대해 1회용 승인을 발급하려 하면 PAP가 `"matching active grant does not require approval"` (`ReasonInvalidArguments`)이라며 생성을 거부합니다.

## 7. 토큰 요청 자격과 하드코딩 명부 (ClientRegistry)

### 7-1. 아무나 승인/토큰을 요청할 수 없다
- 맞습니다. 토큰 발급 창구(`token issue`)는 아무 클라이언트나 요청을 받아주지 않습니다.
- 코드([internal/authn/token/client.go](../../internal/authn/token/client.go))에 **사전 등록(하드코딩)된 3대 기관 계정**이 정해져 있습니다:

```go
// 1. client-orchestrator (팀장 워크로드)
ClientID:    "client-orchestrator"
Secret:      "orchestrator-secret-key-01"
AllowedSubs: ["*"] // 모든 서브에이전트 주체 대리 가능

// 2. client-subagent (말단 작업자 워크로드)
ClientID:    "client-subagent"
Secret:      "subagent-secret-key-02"
AllowedSubs: ["worker-01", "worker-02", "worker-03"] // 지정된 3개 워커만 대리 가능

// 3. client-admin (관리자 워크로드)
ClientID:    "client-admin"
Secret:      "admin-secret-key-00"
AllowedSubs: ["*"]
```

### 7-2. 차단 규칙
1. `ClientID` 또는 `ClientSecret`이 일치하지 않으면 즉시 `ExitAuthnFailed`로 거부됩니다.
2. `client-subagent`가 허용 목록(`AllowedSubs`)에 없는 엉뚱한 이름(`intruder`, `admin` 등)으로 토큰을 발급받으려 하면 `ReasonNoActiveGrant` / `ReasonClientSubjectNotAllowed`로 거부됩니다.

## 8. 토큰 발급 시 PAP 등록 여부 (인증과 인가의 분리)

### 8-1. 토큰을 발급받을 때 PAP에 등록되어 있어야 하는가?
- **아닙니다. 토큰을 만들 때는 PAP 등록 여부를 보지 않습니다.**
- [internal/authn/token/issuer.go](../../internal/authn/token/issuer.go)의 `IssueToken()`은 클라이언트 자격(`ClientID`/`Secret`)과 주체 대리 자격(`AllowedSubs`)만 확인되면, PAP에 Grant가 있든 없든 유효한 서명 JWT를 발급합니다.

### 8-2. 왜 그렇게 만들었는가? (OAuth 2.1 아키텍처 원칙)
- **신분증 발급(인증, AuthN)**과 **방문 허가(인가, AuthZ)**를 철저히 분리하기 위함입니다.
- 주민센터(Issuer)가 신분증(JWT)을 발급할 때 그 사람이 특정 회사 사무실에 들어갈 권한(Grant)이 있는지를 검사하지 않는 것과 같습니다.
- 신분증은 적법한 절차로 발급해주되, 실제 파일이나 자원에 접근하려고 **검문소(PEP/PDP)를 통과하는 순간에 비로소 PAP 장부(`grants_state.json`)의 Grant 존재 여부를 대조**하여 허용 또는 거부를 결정합니다.

## 9. 결론 요약 매트릭스

| 대상 / 질문 | 누구의 소관인가? | 하드코딩 여부 | 검증 시점 |
|---|---|---|---|
| **토큰(JWT) 발급 자격** | `TokenIssuer` (`internal/authn/token`) | **코드 하드코딩** (`ClientRegistry`: ID/Secret/AllowedSubs) | 토큰 발급 시점 (`token issue`) |
| **토큰(JWT) 문자열 생성** | `TokenIssuer` (Ed25519 Zone A 개인키 서명) | 서명 키는 Zone A 금고 파일 | 토큰 발급 시점 |
| **작업 허가 규정 (Grant)** | `PAP` (`internal/authz/pap`) | **원장 등록** (`grants_state.json`, `--requires-approval`) | 실제 작업 집행 시점 (`PEP/PDP`) |
| **1회용 승인 티켓 (Approval)** | `PAP` (`internal/authz/pap`) | **원장 등록** (사전에 승인 필요 Grant 필수) | 실제 작업 집행 시점 (PEP에서 1회 소비 후 삭제) |
