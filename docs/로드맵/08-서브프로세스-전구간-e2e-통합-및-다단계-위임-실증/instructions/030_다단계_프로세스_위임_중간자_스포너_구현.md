## 1. 목적 및 배경

RFC 8693 Token Exchange는 최대 위임 깊이(`MaxDelegationDepth = 3`)와 중첩 `act` 클레임을 지원하도록 설계되어 있으나, 지금까지는 단일 홉(부모 1대 → 자식 1대)만 검증되어 왔습니다.
본 단계에서는 **루트 오케스트레이터(PID 1, Depth 0) → 중간 관리 서브에이전트(PID 2, Depth 1) → 작업 워커 서브에이전트(PID 3, Depth 2)**로 이어지는 **2-Hop OS 프로세스 연쇄 스폰 엔진(`MultiHopSpawner`)**을 구현하고, 이를 32대 E2E 카탈로그에 신규 시나리오(`E2E-31`, `E2E-32`)로 공식 등록합니다.

## 3. 세부 구현 명세

### 3.1 2-Hop 다단계 스포너 아키텍처 (`multi_hop.go`)
1. **Root Orchestrator (Depth 0)**:
   - 부모 토큰(`file:read file:write`, subject: `orchestrator-main`) 보유.
   - STS에 `lead-01`용 축소 토큰(`file:read file:write`, Depth 1) 교환 요청.
   - 자식 OS 서브프로세스(`authz-harness subagent lead`) 스폰.
2. **Middle Lead Process (Depth 2)**:
   - 전달받은 Depth 1 토큰으로 기동.
   - STS에 `worker-01`용 2차 축소 토큰(`file:read`, Depth 2) 교환 요청.
   - 손자(Grandchild) OS 서브프로세스(`authz-harness subagent worker`) 스폰.
3. **Leaf Worker Process (Depth 2)**:
   - Depth 2 토큰으로 파일 읽기(`file:read`) 수행.
   - PEP를 통과하여 데이터 읽기 성공 (`Exit 0`).
   - 종료 코드가 Worker → Lead → Root로 거슬러 올라가 수거됨.

### 3.2 신규 E2E 시나리오 명세

#### `E2E-31`: 2-Hop 다단계 정상 위임 및 권한 축소 실행
- **공격/시나리오 클래스**: `MultiHopDelegationAllow`
- **시나리오 의도**: 부모 → 중간 관리자 → 작업 워커로 권한이 순차 축소(`read+write` → `read+write` → `read`)되며 정상적으로 자식 프로세스가 파일을 읽고 종료 코드 `0`을 반환함을 증명.
- **기대 결과 (Quad-Assertion)**:
  - Exit Code: `0`
  - File Mutation: 0바이트 (읽기 작업)
  - Audit Event: 단일 `TraceID` 하에 `ORCHESTRATE_SPAWN`, `token.exchanged` (depth 1, 2), `pep.allow` 순차 기록
  - Hash Chain: 전체 체인 유효 및 원시 JWT 유출 없음

#### `E2E-32`: 2-Hop 중간 관리자의 권한 초과 위임 시도 차단
- **공격/시나리오 클래스**: `MultiHopDelegationScopeExceeded`
- **시나리오 의도**: 중간 관리자(`lead-01`)가 `file:read` 권한만 위임받았음에도, 하위 워커(`worker-01`)에게 `file:write` 권한을 부여하려 할 때 2차 교환 관문에서 차단됨을 증명.
- **기대 결과 (Quad-Assertion)**:
  - Exit Code: `12` (`ExitAuthzDenied`)
  - File Mutation: 0바이트
  - Audit Event: `token.exchange.deny` (`ReasonDelegationScopeExceeded`)
  - Hash Chain: 유효
