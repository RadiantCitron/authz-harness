## 1. 목적

원안 `010`(코드리딩 동선·DIP 해부)과 `020`(7대 패턴·안티패턴 교본)을 한 편으로 합친다. 001~006편이 「프로그램이 무엇을 하는가」를 다룬다면, 이 편은 「코드가 왜 이렇게 나뉘어 있고 어디부터 읽으면 되는가」를 다룬다. 파일 이름은 `docs/설명서/007-코드읽는순서와_의존방향.md`로 한다.

1. **읽는 순서**: `internal/domain` → `internal/authz/pdp` → `internal/authz/pep` → 어댑터(`storage`·`authz/state`·`authn/budget`·`audit`·`observe`·`jail`·`netguard`·`execguard`·`confinement`) → 프로세스 경계·조립(`orchestrator`·`subagent`·`mcp`·`app`·`cli`). 단계마다 「여기서 무엇을 알게 되는가」를 한 문장으로 쓴다.
2. **의존 방향**: `domain.SnapshotProvider`·`domain.AuditWriter`를 `domain`이 소유하고(`audit.Writer`는 별칭) `pdp`가 `domain`에만 의존하는 이유. 이를 지키는 가드 `TestArchitectureGuardrails`·`TC-170-01`~`03`([architecture_test.go](../../../../internal/harness/architecture_test.go)).
3. **실재하는 구조 패턴**: 코드에 실제로 있는 것만 쓴다 — 단일 출구 파이프라인(`runStage`·`finalize`), 순수 판정과 I/O 셸(`pdp.Evaluate` / `pdpService.Decide`), 제네릭 원자 저장소(`storage.AtomicFileStore[T]`), 포트·어댑터(`observe.Observer`, `confinement.Confiner`), 단일 합성 루트(`app.BuildStack`), 아키텍처 가드 테스트. 데코레이터(`WithBeforeIOHook`)는 [030](030_설명서_006_격리_관측성_체크포인트_편.md) §2의 사실과 같은 내용으로만 쓴다. 패턴 수를 「7대」처럼 미리 정하지 않는다.
4. **배척한 방식(4부)**: 원안의 「안티패턴」은 이 부에 쓴다. 각 항목은 「택했다면 무슨 일이 생기는가」와 「포기한 것」을 쓴다. 과거 코드를 인용해야 하면 본문에 옮기지 않고 커밋 해시와 `git show` 명령만 머리의 `다시 확인하는 법`에 둔다(설명서 갱신 규칙). `ToolHandler` 폐기 이유도 여기에 요약하고 005편으로 링크한다.
5. **밖으로 가져갈 때의 제약(5부 ① 「지금은 없는 것」, 결정 D-2)**: 코어가 모두 `internal/` 아래에 있어 다른 Go 모듈에서 import할 수 없다는 사실, 원격(네트워크) 어댑터가 없다는 사실만 적는다. 이식 절차·예제 코드는 쓰지 않는다.

## 2. 인수 기준

[010 §4](010_설명서_001_004_현행화.md)의 A-1~A-6에 더해:

| 번호 | 기준 |
|:---:|---|
| D-1 | 읽은 사람이 「왜 `pdp`는 파일을 읽는 코드를 import하지 않는가, 그것을 무엇이 지키는가」를 말할 수 있다 |
| D-2 | 패턴마다 코드 위치와 그 패턴을 지키는 테스트(없으면 「없다」)를 5부 ②에 둔다 |
| D-3 | 존재하지 않는 식별자(`pep.ToolHandler`, `internal/confine`)가 본문에 「있는 것」으로 나오지 않는다 (`grep -n "ToolHandler\|internal/confine/" <편>`으로 확인, 4부 배척 설명만 허용) |
| D-4 | [설명서 README](../../../설명서/README.md) §3 목차에 007행을 추가한다 |
