## 1. 목적

10~17번 이후 PEP가 판정과 실행 사이에 하는 일 가운데 기존 편에 없는 세 가지를 [TEMPLATE.md](../../../설명서/TEMPLATE.md)의 0장 + 5부 구조로 한 편에 쓴다. 파일 이름은 `docs/설명서/005-승인_예산과_도구확장.md`로 한다(제목은 집필 시 TEMPLATE 규칙에 맞게 정한다).

1. **사람의 승인을 기다리는 판정(`ask`)**: PDP가 왜 allow/deny 외에 ask를 내는가, 1회용 승인이 무엇에 묶이는가(`domain.ApprovalBinding`, `arg_hash`), 왜 jti는 PDP allow 뒤에 소비하는가, 승인 소비가 삭제인 이유, 종료 코드 `18`.
2. **예산 축소 위임**: 왜 부모 예산보다 큰 예산을 자식에게 줄 수 없는가, 별도 원장(`internal/authn/budget`)과 PEP 단일 집행(`StageBudget`)을 택한 이유.
3. **도구 종류 확장(`net:fetch`·`exec:run`)**: 루프백 전용 GET과 allow-list ID 전용 실행이라는 제한의 이유(`internal/netguard`, `internal/execguard`), Gate 0·2c·Stage 5의 도구 분기. **도구 분기가 인터페이스(`ToolHandler`)가 아니라 `switch`인 이유**(도구 4종 고정, [015번 헌장](../../../보고서/015-지속적_수정발생_근본원인_진단_및_과잉설계_제거_구조단순화_보고서.md) §2.3, 17번 D-03)를 4부 「배척한 방식」에 쓴다.

## 2. 쓰지 않는 것

- `pep.ToolHandler`를 있는 것처럼 쓰지 않는다(코드에 없다).
- 「도구 하나를 더하는 절차」를 안내하지 않는다. 지금 확장점이 없다는 사실과 그 이유만 쓴다.
- 001편이 자세히 다루는 관문 전체 순서는 요약과 링크로 넘긴다.
