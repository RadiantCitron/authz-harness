## 1. 왜 이 로드맵을 하는가? (Why)

00번부터 04번 로드맵까지 우리는 보안 시스템의 모든 핵심 부품을 만들었습니다:
- 엄격한 원칙으로 판정하는 법관(PDP)
- 도용과 위조를 막는 신분증(OAuth 2.1 Access Token)
- 신분증의 권한을 줄여서 심부름을 보내는 위임 체계(RFC 8693 Downscoping)
- 허가된 방 밖으로의 탈출을 막고 증거를 남기는 문지기(PEP & Workspace Jail)
- 팀장과 일꾼을 완전히 갈라놓는 독립된 작업장(OS Subprocess Isolation)

하지만 부품들이 제각기 잘 작동한다고 해서, **"실제 해커나 잘못된 일꾼이 시스템을 공격해 왔을 때 모든 공격이 빠짐없이 방어되는가?"**를 증명할 수 있을까요?

보안 시스템에서 가장 치명적인 착각은 "잘 만들어 두었으니 안전할 것이다"라는 낙관입니다.
보안이 실제로 살아있음을 증명하는 유일한 방법은, **수많은 실패와 공격 시나리오를 직접 퍼붓고 시스템이 그것을 한 치의 오차도 없이 막아내는 모습을 관찰 가능한 증거로 보여주는 것**입니다.

이 로드맵은 바로 엔터프라이즈 환경에서 발생할 수 있는 30가지 공격과 경계 상황을 단 하나의 명령으로 자동 실행하고, 모든 방어가 완벽히 작동했음을 증명하는 **"자동 시나리오 테스트 하네스(Automated Scenario Test Harness)"**를 구축하기 위해 시작합니다.

## 2. 왜 단순한 성공/실패 대신 '4중 검증(Quad-Assertion)'을 고집하는가?

보통의 소프트웨어 테스트는 "프로그램이 에러 코드를 냈는가?" 정도만 확인하고 끝납니다.
하지만 보안 하네스에서는 그것만으로 절대 안심할 수 없습니다:

1. **종료 코드만 맞추는 겉핥기 위험**:
   - 일꾼이 "접근 거부(`12`)"라는 종료 코드를 뱉고 죽었더라도, 죽기 직전에 허가되지 않은 파일에 1바이트라도 글자를 써버렸다면 보안은 이미 뚫린 것입니다.
2. **엉뚱한 사유로 실패할 위험**:
   - 해커가 변조된 토큰을 보냈는데, 시스템이 토큰 위조를 잡은 게 아니라 단순히 파일명이 이상해서 죽은 것이라면 올바른 방어라고 볼 수 없습니다.
3. **감사 기록 누락 위험**:
   - 공격을 막아냈더라도 감사 장부(`audit.jsonl`)에 아무런 기록이 남지 않았거나, 장부의 위변조 방지 도장(해시 체인)이 깨져버렸다면 사후 법적 증거로 채택될 수 없습니다.

따라서 우리는 단 하나의 시나리오를 검증하더라도 다음의 **4가지 질문을 동시에 만족(Quad-Assertion)**해야만 비로소 '통과(PASS)'로 인정합니다:
- **첫째 (종료 코드)**: 약속된 정확한 실패 코드(11~15)로 끝났는가?
- **둘째 (파일 상태)**: 거부되었을 때 파일 시스템에 단 1바이트의 흔적도 남지 않았는가?
- **셋째 (감사 사유)**: 장부에 정확히 우리가 의도한 보안 사유(예: 토큰 만료, 경로 탈출 등)로 거부되었다고 적혔는가?
- **넷째 (장부 무결성)**: 장부의 해시 체인이 전혀 손상되지 않았고 민감한 비밀값이 새어 나가지 않았는가?

## 3. 왜 `sleep` 대기를 철저히 배제하고 가상 시계를 쓰는가?

토큰 만료나 시간 경계 상황을 테스트하기 위해 실제 현실의 시간을 기다린다면(`time.Sleep` 1초~2초), 30개의 시나리오를 돌리는 데 1분 이상의 지루한 시간이 걸리게 됩니다. 테스트가 느려지면 개발자는 테스트를 자주 돌리지 않게 되고, 결국 보안에 구멍이 생깁니다.

우리는 현실의 시간을 기다리는 대신 **"자유자재로 시간을 조작할 수 있는 마법의 시계(가상 Clock)"**를 주입합니다.
버튼 하나로 미래 시점으로 즉시 이동하여 0.001초 만에 토큰 만료를 시뮬레이션함으로써, 30개 전 구간의 복잡한 보안 테스트를 단 수 초 만에 완주하도록 만듭니다.

## 4. 왜 딱 이 정도 범위까지만 하는가? (Why this scope)

이번 05번 로드맵에서는 30개 전 구간 시나리오의 자동 판정 하네스와 초보자용 시각적 해설 UX(`explain`)를 완성합니다.
- 외부 개발자나 면접관이 리포지토리를 클론하여 1분 만에 둘러볼 수 있도록 다듬는 최종 패키징과 최상위 `README.md` 문서화는 마지막 06번 로드맵에서 집중적으로 다룹니다.
- 왜냐하면 30개 시나리오가 단 한 건의 오차도 없이 100% 자동으로 통과하는 단단한 검증 하네스가 먼저 완성되어야만, 최종 문서에 부끄러움 없이 "이 시스템은 30개 공격을 완벽히 방어한다"고 기록할 수 있기 때문입니다.

이번 05번 로드맵의 완성은 **"명령어 한 줄(`run --scenario all`)로 30대 엔터프라이즈 보안 공격 시나리오가 일괄 실행되고, 4중 불변식(Quad-Assertion)에 의해 단 한 건의 예외 없이 방어 성공이 증명되는 자동화 검증 엔진의 완성"**입니다.
