## 1. 목적 (Context & Why)

본 지시서는 Phase 0부터 Phase 4까지 구축된 전 계층(인증, 토큰, PDP, PEP/Jail, 오케스트레이터 격리, 감사 추적)의 보안 경계와 방어 기제를 전수 검증하기 위한 **7대 그룹 30개 E2E 시나리오 카탈로그(`internal/harness/catalog`)**를 구현하는 작업이다.

보안 불변식에 따라:
1. **모든 인가 및 실패 경계 전수 검증**:
   - 정상 경로(Happy Path) 2개뿐만 아니라, 위조·변조·만료·탈출·Replay·초과 위임·감사 장애 등 28개의 부정 시나리오(Negative Testing)를 전수 정의한다.
   - 각 시나리오는 사전에 정의된 `ExpectedAssertion` 명세(종료 코드, 파일 무변화/일치, 감사 사유 코드, 해시 체인 무결성)에 따라 Quad-Assertion 엔진에 의해 일괄 판정된다.
2. **무대기(Zero-Sleep) 결정론적 초고속 실행**:
   - `time.Sleep`을 일체 사용하지 않고, 주입 가능한 `domain.Clock` 및 시간 오프셋 메커니즘을 통해 30개 전체 시나리오를 수 초 이내에 완주한다.
3. **독립된 Ephemeral Sandbox 격리**:
   - 각 시나리오는 010 단계에서 구축된 `SandboxEnvironment`를 통해 개별 임시 디렉터리(Zone A 서명키, Zone B JWKS/Grant/Replay 원장, Zone C Workspace 디렉터리, `audit.jsonl`)에서 독립적으로 초기화되고 실행 후 안전하게 자동 정리(Cleanup)된다.
4. **플러그인 형태의 일괄 등록 레지스트리**:
   - `catalog.AllScenarios()` 및 `catalog.RegisterAll(runner harness.Runner)` 함수를 제공하여 상위 CLI 러너가 30개 시나리오를 손쉽게 발견하고 일괄 실행할 수 있도록 한다.

## 2. 패키지 배치 및 6계층 DAG 구조

```text
Layer 5:  [cmd/authz-harness]
                │
                v
Layer 5:  [internal/harness] (Core Harness)
                ▲
                │
Layer 5:  [internal/harness/catalog] (30 E2E Scenario Catalog)
           ├── catalog.go               (AllScenarios, RegisterAll, Group 정의)
           ├── helpers.go               (시나리오 공통 Setup/Execute 헬퍼)
           ├── g1_lifecycle.go          (E2E-01 ~ E2E-03: 정상 생명주기 및 회수)
           ├── g2_authn.go              (E2E-04 ~ E2E-06: 워크로드 인증 AuthN)
           ├── g3_token_integrity.go    (E2E-07 ~ E2E-13: 토큰 무결성 및 키 관리)
           ├── g4_claims_replay.go      (E2E-14 ~ E2E-18: 시간, 바인딩, Replay)
           ├── g5_delegation_pdp.go     (E2E-19 ~ E2E-24: RFC 8693 위임 및 PDP)
           ├── g6_jail_path.go          (E2E-25 ~ E2E-27: Workspace Jail 경로 탈출)
           ├── g7_observability_audit.go (E2E-28 ~ E2E-30: 관측성 및 감사 Fail-Closed)
           └── catalog_test.go          (30개 전 시나리오 전수 검증 테스트)
                │
                v
Layer 4:  [internal/orchestrator, internal/subagent]
Layer 3:  [internal/authz/pep, internal/cli]
Layer 2:  [internal/authn, internal/authz/pdp, internal/jail]
Layer 0/1: [internal/audit, internal/domain, internal/clock]
```

- **Layer 5 (`internal/harness/catalog`)**:
  - `catalog.go`: 30개 시나리오 인터페이스 구현체를 단일 컬렉션으로 묶는 레지스트리
  - `helpers.go`: Ed25519 서명키 초기화, 클라이언트 토큰 발급, Grant 등록 등 공통 셋업 헬퍼 함수
  - `g1`~`g7`: 각 보안 영역별 시나리오 그룹 구현체
- **금지 결합 (Forbidden Couplings)**:
  - `catalog` 패키지는 `internal/harness`의 공개 인터페이스(`harness.Scenario`, `harness.SandboxEnvironment`, `harness.ExpectedAssertion`)만 참조하며, 하네스 내부 비공개 구조체에 직접 결합하지 않는다.
  - 시나리오 간 파일 시스템 또는 전역 메모리 상태를 공유하지 않는다.

## 4. 파급 범위와 무영향 근거 증명

### 4.1 파급 범위 (Impact Scope)
- **신규 파일 생성**:
  - `internal/harness/catalog/catalog.go`: 시나리오 등록 인터페이스 및 카탈로그 레지스트리
  - `internal/harness/catalog/helpers.go`: 공통 테스트 하네스 셋업/실행 헬퍼
  - `internal/harness/catalog/g1_lifecycle.go`: E2E-01 ~ 03
  - `internal/harness/catalog/g2_authn.go`: E2E-04 ~ 06
  - `internal/harness/catalog/g3_token_integrity.go`: E2E-07 ~ 13
  - `internal/harness/catalog/g4_claims_replay.go`: E2E-14 ~ 18
  - `internal/harness/catalog/g5_delegation_pdp.go`: E2E-19 ~ 24
  - `internal/harness/catalog/g6_jail_path.go`: E2E-25 ~ 27
  - `internal/harness/catalog/g7_observability_audit.go`: E2E-28 ~ 30
  - `internal/harness/catalog/catalog_test.go`: 30개 시나리오 전수 검증 테스트

### 4.2 무영향 근거 (Proof of Zero Blast Radius)
- **Layer 0 ~ Layer 4 불변**:
  - 기존 `internal/audit`, `internal/authn`, `internal/authz`, `internal/jail`, `internal/orchestrator` 코드는 수정하지 않고 읽기/실행 전용으로 호출한다.
  - 기존 단위 테스트(`go test ./...`) 결과에 일체 영향을 주지 않는다.

## 5. 사전 점검 및 실패 위험 분석 (Pre-Mortem)

| 위험 요소 | 실패 시나리오 | 방어 설계 (Countermeasure) |
|---|---|---|
| **시나리오 실행 속도 지연** | 토큰 만료를 검증하기 위해 `time.Sleep`을 호출하여 30개 검증에 수십 초 이상 소요 | `time.Sleep`을 완전히 배제하고 `SandboxEnvironment.MockClock` 시간 오프셋을 활용하여 0.001초 단위로 시간 경계 만료 시뮬레이션 |
| **시나리오 간 상태 누수** | 이전 시나리오의 파일, Grant, Replay 원장이 다음 시나리오에 남아 간섭 발생 | 각 시나리오 실행 시 `harness.Runner`가 독립 임시 디렉터리를 생성하고 종료 시 즉시 `Cleanup()` 수행 |
| **감사 사유 코드 불일치** | `ROADMAP.md`의 기술 명칭과 실제 Go 코드 `domain.Reason` 상수의 철자 차이로 검증 실패 | `internal/domain/constants.go`에 정의된 정본 상수(`domain.ReasonTokenExpired` 등)를 100% 매핑하여 기대값 설정 |
| **심볼릭 링크 권한 및 OS 차이** | 심볼릭 링크 생성 시 호스트 OS 권한 부족 또는 플랫폼 경로 분리 기호 문제 | `os.Symlink` 지원 여부를 격리 디렉터리 내에서 검증하고, 실패 시 친절한 에러 리포트 제공 |
| **Fail-Closed 감사 파일 잠금/권한 오류** | E2E-29 시나리오에서 읽기 전용 파일 모드로 감사 장애 유도 시 플랫폼별 상이한 거동 | 감사 파일 권한을 `0400`으로 변경하거나 디렉터리 차단을 통해 확실한 쓰기 실패 유도 |

## 6. 4층위 검증 범위 설계 (Verification Grid)

- **1층위 (자동화 스크립트 배제 및 통합 테스트)**:
  - `go test -v ./internal/harness/catalog` 단일 명령으로 30개 시나리오 일괄 실행
- **2층위 (단위 및 그룹 검증)**:
  - G1 ~ G7 7개 그룹별 독립 단위 테스트 (`TestGroup_G1`, `TestGroup_G2`, ..., `TestGroup_G7`)
- **3층위 (불변식 Quad-Assertion 판정 검증)**:
  - 30개 시나리오 모두 Exit Code, File 0-mutation, Audit Reason, Hash Chain 무결성을 Quad-Assertion으로 동시 통과
- **4층위 (전체 카탈로그 완주 검증)**:
  - `RegisterAll(runner)` 등록 후 30개 전 시나리오가 10초 이내에 100% PASS 완주
