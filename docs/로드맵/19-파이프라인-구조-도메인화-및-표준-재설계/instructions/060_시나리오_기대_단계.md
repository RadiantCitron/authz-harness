4중 판정이 「어느 단계에서 막혔는가」도 보게 합니다. 보고서 036 9장의 원인 1번을 해소합니다. 보고서 036 M1 변이가 여기서 실패하기 시작해야 합니다.

## 2. 파급 범위와 무영향 근거

- **변경**: `internal/harness/assertion.go`, 카탈로그 기대값, 시나리오 요약 출력의 판정 칸
- **무영향**: 시나리오 실행 절차, 나머지 네 판정

## 3. 구현

**순서가 중요합니다. 코드보다 표가 먼저입니다.**

1. 아래 규칙으로 79건의 기대 단계 표를 이 지시서 부록에 **먼저** 적고 커밋한다. 실행 결과를 보고 적지 않는다.
2. `AuditExpectation.ExpectedStage domain.Stage`를 더한다.
3. 판정은 감사 기록의 `Stage`를 읽는다. 값이 비어 있으면 그 판정을 건너뛰지 않고 `NotEntered`를 뜻하는 명시값과 대조한다.
4. 모든 시나리오는 기대 단계를 적어야 한다. 빈 값이면 등록이 실패한다.

**기대 단계 규칙 (요구사항에서 도출)**

| 요청의 결과 | 기대 단계 |
|---|---|
| 정상 실행 | `execute` 또는 `settle` 통과 |
| 입력·추적 ID 문제 | `input` |
| 토큰 형식·서명·시간·키·재사용 | `authn` |
| Grant, Epoch, 스코프, 승인 필요 | `authz` |
| 경로·주소·명령 경계 | `boundary` |
| 승인 소비 경합·만료 | `approval` |
| 예산 소진 (쓰기·실행) | `budget` |
| 예산 소진 (읽기) | `settle` |
| 감사 실패 | `precommit_audit` |
| 발급·교환에서 거부, 관문 미진입 | `NotEntered` (교환은 080 뒤 교환 단계로 갱신) |
| 격리·자원 한계·감사 변조처럼 관문 밖 판정 | `NotEntered` |

## 4. 사전 점검

- 다단계 시나리오는 어느 요청을 볼지 정해야 한다 → `ExpectedTraceID`가 지정한 요청의 단계를 본다
- 실제 값이 표와 다르면 표를 맞추지 말고 멈춰 보고한다. 표가 틀렸는지 코드가 틀렸는지는 사용자가 판단한다

## 5. 4층위 검증
