## 3. 구현

**순서가 중요합니다. 코드보다 표가 먼저입니다.**

1. 아래 규칙으로 79건의 기대 단계 표를 이 지시서 부록에 **먼저** 적고 커밋한다. 실행 결과를 보고 적지 않는다.
2. `AuditExpectation.ExpectedStage domain.Stage`와 `AssertionResult.AuditActualStage`를 더한다. `harness`에 명시값 `NoStageRecord`를 둔다. 도메인 단계가 아니라 판정기의 값이므로 `domain`에 넣지 않는다.
3. 판정은 기존 감사 판정이 **매칭한 이벤트**의 `Stage`를 읽어 `AuditActualStage`에 담는다. 값이 비어 있으면 그 판정을 건너뛰지 않고 `NoStageRecord`와 대조한다.
4. `RequireEvent`가 거짓이라 매칭이 없는 시나리오는 감사 전체에 `Stage`가 있는 이벤트가 없어야 `NoStageRecord`로 합격한다.
5. 모든 시나리오는 기대 단계를 적어야 한다. 빈 값이면 `DefaultRunner.Register`가 실패한다.

**기대 단계 규칙 (요구사항에서 도출)**

기대 단계는 「요청이 어디서 멈췄는가」가 아니라 **매칭한 감사 기록에 무엇이 적혀 있어야 하는가**다. 값은 하나만 적는다.

| 요청의 결과 | 기대 단계 |
|---|---|
| 정상 실행 | `execute`. 예산 토큰의 읽기처럼 정산을 거치면 `settle` (완료 감사는 마지막 통과 단계를 적는다) |
| 입력·추적 ID 문제 | `input` |
| 토큰 형식·서명·시간·키·재사용 | `authn` |
| Grant, Epoch, 스코프, 승인 필요 | `authz` |
| 경로·주소·명령 경계 | `boundary` |
| 동시 요청의 jti 소비 경합 | `replay` |
| 승인 소비 경합·만료 | `approval` |
| 호출 횟수 소진, 쓰기 바이트 소진 | `budget` |
| 읽기·출력 바이트 소진 | `settle` |
| 사전 감사 실패 (E2E-29) | `NoStageRecord`. 이 실패는 감사가 남지 않는 것이 정상이다. `precommit_audit` 도달은 `TestStageOrder_FailurePathsKeepInvariant`가 `Result.Stage`로 확인한다 |
| 실행 뒤 감사 변조 적발 (E2E-30, 61~63) | `execute`. 요청은 성공했고 `pep.allow`를 매칭한다. 적발은 종료 코드 15가 판정한다 |
| 발급·교환 거부 | `NoStageRecord` (교환은 080 뒤 교환 단계로 갱신) |
| 격리·자원 한계 (`agent.*`) | `NoStageRecord` |
| 자식 프로세스 미기동으로 감사가 없는 경우 (G8) | `NoStageRecord` |

## 4. 사전 점검

- 다단계 시나리오는 어느 요청을 볼지 정해야 한다 → 기존 감사 판정이 매칭한 이벤트를 그대로 쓴다. `ExpectedTraceID`가 있으면 그 요청이고, 없으면 `ExpectedAction`에 맞는 마지막 이벤트다
- `pep.allow`는 한 요청에 사전 감사와 완료 두 건이 남는다 → 역순 탐색이므로 완료 기록을 본다. 완료 감사 기록이 실패한 요청은 사전 감사 기록을 보게 된다
- 실제 값이 표와 다르면 표를 맞추지 말고 멈춰 보고한다. 표가 틀렸는지 코드가 틀렸는지는 사용자가 판단한다
