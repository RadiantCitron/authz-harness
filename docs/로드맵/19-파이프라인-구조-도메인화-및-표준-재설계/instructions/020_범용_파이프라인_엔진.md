## 2. 파급 범위와 무영향 근거

- **변경**: `internal/pipeline/` 신규, `internal/harness/architecture_test.go`에 `pipelineAllowedImports`(표준 라이브러리만)와 변이 시험 추가. `TC-130-01`(`time.Now` 금지)과 `TC-140-01`(`log/slog` 금지)의 대상 목록에 `pipeline` 추가. 둘 다 표준 라이브러리라 허용 목록으로는 막히지 않기 때문이다. `TC-110-01`(`internal/confinement`)은 허용 목록이 이미 막으므로 고치지 않는다
- **무영향**: 소비자가 없음

## 3. 구현

- `Kind`와 등급: `Check`·`Decide`=0, `Consume`=1, `Record`=2, `Execute`=3, `Settle`=4
- `New(steps, hook) (*Engine[S], error)`: 빈 목록, 빈·중복 ID, 모르는 `Kind`, `Run` 없음, 등급 하강을 거부
- `Run(ctx, s) Trace`: 앞에서부터 실행. `Applies`가 거짓이면 건너뜀으로 기록. 실패하면 완료한 단계의 `Compensate`를 역순으로 한 번씩 호출하고 멈춤. 실패한 단계 자신은 완료한 단계가 아니므로 보상하지 않음
- `Trace{Passed []string, Skipped []string, Failed string, Err error}`
- `Hook[S any]` 포트: `OnStepStart(ctx, id, s *S)`, `OnStepEnd(ctx, id, s *S, err error)`. `nil`이면 아무것도 안 함. 엔진은 한 번 조립해 재사용하므로 요청별 값은 `s`로만 전달한다. 건너뛴 단계는 Hook을 부르지 않는다. 현재 `runStage`도 조건부 단계가 해당 없으면 부르지 않는다
- 엔진은 시각을 읽지 않는다. 소요 시간은 Hook 구현이 주입된 시계로 잰다
- `ctx` 취소는 단계 함수가 판단한다. 엔진은 재시도하지 않는다

## 4. 사전 점검

- 단계 함수의 panic은 잡지 않는다. 기존 동작과 같고, 잡으면 Fail-Closed가 흐려진다
- `Compensate`가 실패해도 원래 오류를 바꾸지 않는다. 보상의 실패 처리는 소비자 책임이다
