## 1. 목적

보고서 036 2장의 결함을 없앱니다. 화면은 추측하지 않고 실제 기록을 그립니다. 모르면 `PASS`로 그리지 않습니다.

## 2. 파급 범위와 무영향 근거

- **변경**: `internal/ui/pipeline.go`, `explain.go`, `internal/cli/pep.go`, `internal/cli/pdp.go`, `internal/harness/runner.go`(결과에 관측 단계 전달), `ui` 시험(`ui_test.go`의 `sampleResult`는 `AuditActualStage`가 없어 다시 만든다)
- **삭제**: `ComputePipelineGates`의 추측 표, 시나리오 ID 분기, 6단계 이름표, `stageLabels`, `pdp` 화면의 `Simulated Context` 고정 줄
- **무영향**: 판정 결과, `summary`·`json` 출력의 기존 필드

## 3. 구현

- 공통 표시 상태: `통과`, `차단`, `건너뜀`, `해당 없음`, `미진입`, `판단 불가`
- 칸 목록과 이름은 `domain.PEPStages()`에서 읽는다
- `explain`은 시나리오가 관측한 단계 기록(`AuditActualStage`)을 아래 표대로 그린다
- 관문 밖 판정은 관문 칸과 별도 줄로 표시한다. 기존 「실행 감독」 줄을 일반화한다
- `pdp` 화면은 PDP만 실행한 사실대로 판정 칸 하나만 그린다
- 해설 문구의 `Gate N`과 `explain.go`의 「6대 관문」 표현을 단계 이름이나 일반 표현으로 바꾼다

**표시 규칙**

| 관측 | PEP 칸 | 별도 줄 |
|---|---|---|
| `pep.deny`, 단계 값이 `PEPStages()`에 있음 | 그 칸 `차단`, 뒤 칸 `건너뜀`, 앞 칸은 아래 앞 칸 규칙 | 없음 |
| `pep.allow`, 종료 코드 0 | 기록된 단계까지 앞 칸 규칙 | 없음 |
| `pep.allow`, 종료 코드 15 (E2E-30, 61~63) | 기록된 단계까지 앞 칸 규칙 | `감사 검증: 차단` |
| 단계 기록 없음, 종료 코드 15 (E2E-29) | 전 칸 `판단 불가` | `감사 기록: 실패` |
| `token.issue.deny` (E2E-04~06) | 전 칸 `미진입` | `토큰 발급: 차단` |
| `token.exchange.deny` | 전 칸 `미진입` | `토큰 교환: 차단` |
| `agent.*` (격리, 자원 한계) | 같은 요청의 PEP 기록이 있으면 그 기록, 없으면 전 칸 `미진입` | `실행 감독: 차단` 또는 `격리: 차단` |
| 그 외 기록 없음, 종료 코드가 0이 아님 (G8 어댑터 거부처럼 자식이 기동되지 않은 경우) | 전 칸 `미진입` | `진입 전: 차단` |
| 그 외 기록 없음, 종료 코드 0 | 전 칸 `미진입` | 없음 |
| 모르는 단계 값, 읽기 실패, v3 이하 기록 | 전 칸 `판단 불가` | 없음 |

**앞 칸 규칙**: 감사에는 종단 단계만 남으므로 앞 칸은 다음 근거로만 그린다.

| 칸 | 근거 | 표시 |
|---|---|---|
| 필수 단계 | 엔진이 순서를 보장한다 | `통과` |
| `approval` | 같은 요청의 `approval.consumed` 유무. 승인 소비는 기록에 실패하면 거부되므로 없다는 것도 증거다 | `통과` 또는 `해당 없음` |
| `budget` | 종단 단계가 `settle`이면 예산 토큰이 확실하다. 그 외에는 증거가 없다 | `통과` 또는 `판단 불가` |
| `settle` | 완료 기록의 단계가 `settle`이면 통과, `execute`면 돌지 않았다 | `통과` 또는 `해당 없음` |

`건너뜀`은 앞 단계가 막아서 돌지 않은 것이고, `해당 없음`은 조건에 맞지 않아 돌지 않은 것이다. `pep` 명령 화면은 `Result.Passed`가 있으므로 `판단 불가` 없이 그린다.
