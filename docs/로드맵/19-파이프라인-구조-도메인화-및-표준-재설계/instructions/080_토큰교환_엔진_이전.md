## 1. 목적

엔진의 두 번째 소비자를 만듭니다. `ExchangeService.Exchange`의 반복되는 거부 감사 분기를 마감 한 곳으로 모읍니다. 범용 엔진이 정말 범용인지 검증하는 단계이기도 합니다.

## 2. 파급 범위와 무영향 근거

- **변경**: `internal/authn/exchange/service.go`, `internal/domain/stage.go`(교환 단계와 `ExchangeStages()` 추가), `internal/ui/pipeline.go`(교환 단계 표시), 관련 시나리오의 기대 단계
- **무영향**: `validator.go`의 불변식, 토큰 서명, 예산 원장. 사유 코드, 종료 코드, 감사 내용

## 3. 구현

**단계** (`service.go`의 현재 순서입니다. 순서를 바꾸지 않습니다)

| 순서 | 단계 | 성격 | 조건부 | 내용 |
|:-:|---|---|:-:|---|
| 1 | `client_auth` | 검사 | | 클라이언트 인증 |
| 2 | `delegation_subject` | 검사 | | 자식 주체 허용 |
| 3 | `parent_token` | 검사 | | 부모 토큰 검증 |
| 4 | `lineage_epoch` | 검사 | 예 (스냅샷 제공자가 있을 때) | 부모·조상 Epoch |
| 5 | `downscope` | 판정 | | 축소 불변식 |
| 6 | `budget_downscope` | 검사 | 예 (예산이 관여할 때) | 예산 정적 검사, 원장 배선 확인 |
| 7 | `token_issue` | 실행 | | `act` 체인 구성, 자식 토큰 서명·발급 |
| 8 | `budget_reserve` | 정산 | 예 (예산이 관여할 때) | 부모 잔여에서 예약. 실패하면 자식 토큰을 돌려주지 않음 |

- 예약이 발급 뒤인 이유: `Reserve`는 `IssueToken`이 만든 자식 jti와 만료를 인자로 받는다. 그래서 성격은 소비가 아니라 정산이다 ([ADR 0007](../../../adr/0007-파이프라인-단계-분류-기준.md) 4장)
- 교환은 `Compensate`를 쓰지 않는다. 마지막 단계의 실패를 되돌릴 앞선 소비가 없다
- 마감 함수 한 곳이 거부 감사, `AUDIT_LOG_FAILED` 승격, 성공 시 `token.exchanged` 기록을 처리한다. 성공 감사 실패가 자식 토큰을 돌려주지 않는 기존 동작을 유지한다
- 단계마다 감사 사유와 호출자에게 돌려주는 오류가 다르다. 현재 일부는 `*domain.Error`가 아니다. 단계 함수는 둘을 상태 필드에 남기고 마감이 그대로 돌려준다
- `domain.ExchangeStages()`를 더하고 조립 목록과의 일치를 ID·순서·성격·조건부로 시험한다
- `token.exchange.deny`의 `Stage`는 실패 단계이고, `token.exchanged`의 `Stage`는 마지막 통과 단계다
- 화면은 값이 `ExchangeStages()`에 있으면 PEP 칸을 모두 `미진입`으로 두고 별도 줄 `토큰 교환: <Label> 차단`을 그린다. 이 처리가 없으면 070의 「모르는 값」 규칙에 걸려 `판단 불가`가 된다
- 엔진에 새 기능이 필요해지면 멈추고 보고한다. 필요한 기능이 PEP와 달라 엔진이 뒤틀린다면 ADR 0008의 전제가 틀린 것이다

## 4. 사전 점검

- 감사 내용이 달라질 위험 → 착수 전 교환 거부·성공 경로의 감사 이벤트를 스냅샷으로 뜨고 이것을 합격선으로 삼는다. 단, 시각·해시 제외
- `recordAuditDenied` 호출마다 넘기는 `parentJTI`가 다르다 → 상태 필드로 옮기되 빈 값 시점이 같아야 한다. `parent_token`까지는 비어 있고 `lineage_epoch`부터 채워진다
- 예약 실패 시 서명된 자식 토큰은 버려지지만 `IssueToken` 안에서 이미 `token.issued`가 기록됐다 → 기존 동작이다. 이 단계에서 고치지 않고 스냅샷으로 고정한다
