## 1. 목적

엔진의 두 번째 소비자를 만듭니다. `ExchangeService.Exchange`의 반복되는 거부 감사 분기를 마감 한 곳으로 모읍니다. 범용 엔진이 정말 범용인지 검증하는 단계이기도 합니다.

## 2. 파급 범위와 무영향 근거

- **변경**: `internal/authn/exchange/service.go`, `internal/domain/stage.go`(교환 단계 추가), 관련 시나리오의 기대 단계
- **무영향**: `validator.go`의 불변식, 토큰 서명, 예산 원장. 사유 코드, 종료 코드, 감사 내용

## 3. 구현

**단계 후보** (코드의 현재 순서를 따릅니다. 성격은 착수 때 코드와 대조해 확정합니다)

| 단계 | 성격 | 내용 |
|---|---|---|
| `client_auth` | 검사 | 클라이언트 인증 |
| `delegation_subject` | 검사 | 자식 주체 허용 |
| `parent_token` | 검사 | 부모 토큰 검증 |
| `lineage_epoch` | 검사 | 부모·조상 Epoch |
| `downscope` | 판정 | 축소 불변식 |
| `budget_downscope` | 검사 | 예산 정적 검사 |
| `budget_reserve` | 소비 | 예산 예약, 실패 시 보상 |
| `token_issue` | 실행 | 자식 토큰 서명·발급 |

- 마감 함수 한 곳이 거부 감사와 `AUDIT_LOG_FAILED` 승격을 처리한다
- 엔진에 새 기능이 필요해지면 멈추고 보고한다. 필요한 기능이 PEP와 달라 엔진이 뒤틀린다면 ADR 0008의 전제가 틀린 것이다

## 4. 사전 점검

- 감사 내용이 달라질 위험 → 착수 전 교환 거부·성공 경로의 감사 이벤트를 스냅샷으로 뜨고 이것을 합격선으로 삼는다. 단, 시각·해시 제외
- `recordAuditDenied` 호출마다 넘기는 `parentJTI`가 다르다 → 상태 필드로 옮기되 빈 값 시점이 같아야 한다
- 예약 뒤 발급 실패의 기존 처리를 먼저 코드에서 확인한다
