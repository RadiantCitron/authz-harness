## 1. 개요

이 로드맵은 단계 이름이 어지럽다는 불편에서 시작했지만, 보고서 036이 밝힌 문제는 이름이 아니었습니다. 요청이 지나가는 구조를 정의한 곳이 없어서 코드, 화면, 문서가 같은 구조를 일곱 가지로 불렀고, 초보자용 `explain` 화면은 거부된 요청을 「전부 통과」로 그렸습니다. 그런데도 시험은 모두 통과했습니다. 시험이 거부의 정확성만 보고 구조는 보지 않았기 때문입니다.

결과로 구조를 한 곳에서 정의했고(`domain.Stage`·`StageKind`), 범용 엔진으로 PEP와 토큰 교환을 돌렸으며, 화면은 감사 기록만으로 그리게 했고, 구조가 어긋나면 시험이 실패하게 만들었습니다.

```text
[010] 단계 도메인 정의 ─ [020] 범용 파이프라인 엔진 ─ [030] 도구 전략 추출
        │
[040] PEP 엔진 이전·검사 후 소비 ─ [050] 감사 스키마 v4 ─ [090] 도메인 에러의 단계 필드 제거
        │
[080] 토큰 교환 엔진 이전 ─ [060] 시나리오 기대 단계 ─ [070] 화면을 감사 기록에서 그리기
        │
[100] 문서 동기화와 전체 회귀 (100-1 ~ 100-5)
```

규모: 코드 `internal/`·`cmd/` 113개 파일(+4,306 / −1,546), 문서(설명서·로드맵·ADR) 41개 파일. 기준은 `a0640f4`(010)부터 100 완료 시점까지의 변경입니다.

## 3. 보고서 036이 지적한 결함의 해소

| 결함 | 이전 | 이후 |
|---|---|---|
| 구조를 부르는 체계가 일곱 가지 | 코드·화면·문서·감사가 서로 다른 이름 | 이름·순서·성격의 정의는 `domain/stage.go` 한 곳, 순서는 조립 목록과 대조하는 시험 |
| 틀린 화면 | 거부 요청이 「전부 통과」 | 감사 기록만 근거로 그림. 기록이 없으면 `판단 불가`. 거부 시나리오 중 전 칸 통과로 그린 것 0건 |
| 소비가 검사보다 앞 | `jti`가 `authz` 직후 소비되어 `boundary` 거부에도 소진 | 소비 단계는 모든 검사 단계 뒤에만 오도록 엔진이 시작할 때 강제 |
| 단계 값이 시험으로 보호되지 않음 | M1 변이가 `go test` 전부 통과 | 같은 변이에서 `internal/domain` 시험 실패 |
| 감사 단계 값 변조 | 거의 검출되지 않음 | `stage`가 v4 해시 입력에 들어가 `audit verify`가 `AUDIT_INTEGRITY_BROKEN`(`15`) |

변이 시험(저장소 사본)은 보고서 036 9장의 M1~M4와 순서 변이를 다시 돌렸습니다. 모든 변이에서 시험이 실패했고, PDP 거부 무력화는 대조군으로 14건 FAIL을 유지했습니다.

## 5. 검증 증거

- `go test -race ./...` 전 패키지 통과, `go vet ./...`, `scripts/prepush_checks.sh` 통과.
- `run --scenario all`: 79건 중 79건 PASS. `explain` 전수 79건에서 거부 시나리오를 전 칸 통과로 그린 것 0건.
- 변이 시험 TC-100-01~07 통과(대시보드 실행 기록 참조).
- `internal/docsync`가 살아 있는 문서(설명서 36편 포함)에서 옛 `Gate`/`Stage` 번호와 사라진 식별자를 막고, 사유 코드 표가 `domain` 상수와 일치하는지 검사합니다.
- 설명서·로드맵·ADR·루트 문서의 상대 링크 깨짐 0건(단, 설명서 `TEMPLATE.md`의 자리표시자는 제외).

## 6. 이번 작업에서 바로잡은 기존 오류

로드맵을 진행하며 문서가 코드와 달랐던 곳을 같이 고쳤습니다.

- 해설서 두 곳이 「완료 감사 기록 실패 시 결과를 폐기하고 종료 코드 `15`로 덮어쓴다」고 적었으나, 실제로는 성공 결과를 돌려주고 운영 로그에만 남깁니다(차단 감사 기록이 실패할 때만 `15`).
- 설명서 008은 `ComputePipelineGates`가 신규 사유를 모두 `PASS`로 그린다는 한계를 적었으나, 그 함수는 070에서 사라졌고 지금 한계는 「기록에 없는 앞 칸은 `판단 불가`」입니다.
- 설명서 013·007이 이미 제거된 `DomainEvent`/`EventRecorder`를 설명하고 있었습니다.
- 설명서의 깨진 소스 링크 10건을 실제 파일로 고쳤습니다. `verifier.go`의 소비 시점 주석도 실제 순서에 맞췄습니다.

## 7. 알려진 한계와 후속 후보

- 변이 시험은 일회성 수동 확인입니다. 자동 시험으로 남은 것은 `docsync`와 각 패키지의 단계 순서·감사 어휘 시험입니다.
- (해소됨, [계획 015](../../계획/015-예산차감_감사기록_추가_및_예산칸_판단불가_해소.md)) 화면의 `예산 차감` 칸은 이제 `budget.consumed` 기록으로 그립니다. 남은 한계는 그 기록이 생기기 전에 쓰인 v4 기록의 예산 토큰 요청이 `해당 없음`으로 그려지는 것입니다([ADR 0009](../../adr/0009-감사-스키마-v4-단계-보호.md) 5장).
- 설명서 000·007 해설서는 단계 어휘와 PEP 서술만 동기화했고, 보고서 035 반영분이 해설서에 있는지는 확인하지 않았습니다.
- (재검증함, [계획 016](../../계획/016-설명서_본편_재대조_및_DEMO_GUIDE_재검증.md)) 000·001·005·007·009·013·015 본편은 2026-11-06에 식별자·링크·수치·확인 명령으로 다시 대조했고 고칠 사실 오류는 없었습니다. `DEMO_GUIDE` 장면 7~9는 다시 실행해 단계 이름 2곳과 표본 줄 번호를 고쳤습니다. 줄 단위로 읽지 않은 범위는 각 편의 「검증 방법」 문단에 적었습니다.
- 토큰 발급과 PAP의 엔진 이전, Linux 런타임 검증은 범위 밖이었고 하지 않았습니다.
