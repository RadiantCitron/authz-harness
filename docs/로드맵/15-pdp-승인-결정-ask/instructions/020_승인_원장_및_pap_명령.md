## 1. 목적 및 배경

사람 승인자를 대역하는 PAP CLI(`approval grant/list`)와, 승인을 **ID로 찾아 재검증한 뒤 지우는** 원자적 1회 소비를 구현한다. 원장은 기존 `grants_state.json`의 `Approvals` 필드다(024 A-6). 새 파일·새 스토어·경로 파생·새 플래그는 없다. 그래서 부모와 워커는 기존 `-state-file`([`helpers.go`](../../../../internal/harness/catalog/helpers.go) 167행)만으로 같은 원장을 본다.

## 2. 파급 범위와 무영향 근거

- **변경**:
  - `internal/authz/state/store.go`: `GrantsState`에 `Approvals []domain.Approval` (`json:"approvals,omitempty"`)를 추가한다. `ensureStateFields`는 nil을 빈 슬라이스로 맞춘다. `Version` 필드의 의미는 바꾸지 않는다(`StateVersion` 보류, 024 결정 2).
  - `internal/authz/state/approval.go` [신규]: §3.1~3.3. 모두 `Store.Update` 한 번 안에서 동작하므로 어떤 `Store` 구현에도 쓸 수 있다.
    - `CreateApproval(s Store, a domain.Approval, now time.Time) error`
    - `ConsumeApproval(s Store, id string, b domain.ApprovalBinding, now time.Time) error`
    - `NewApprovalConsumer(s Store) *ApprovalConsumer`: 040의 `pep.ApprovalConsumer` 포트 구현(메서드 `ConsumeApproval(id, b, now) error`)
  - `internal/authz/pap/service.go`:
    - `CreateGrantRequest.RequiresApproval bool`을 Grant에 그대로 옮긴다.
    - `CreateApproval(ctx, CreateApprovalRequest{Subject, Action, Resource, TokenJTI, ArgHash, TTL}) (*domain.Approval, error)`: `ValidateApprovalTTL`·`ValidateArgHash`로 검증하고(어긋나면 14), ID는 `approval-<UnixNano>`, 시각은 PAP 시계로 정한다. 저장은 `state.CreateApproval`, 그 뒤 `approval.granted` 감사를 남기며, 감사가 실패하면 15다.
    - `ListApprovals(ctx, subject string) ([]domain.Approval, error)`
  - `internal/cli/grant.go`: `grant create --requires-approval`.
  - `internal/cli/approval.go` [신규], `cmd/authz-harness/main.go`: `approval grant --subject … --action … --resource … --jti … [--arg-hash sha256:…] [--ttl 5m]`, `approval list [--subject …]`. 조립은 `app.BuildStack`(VerifyOnly 아님)으로만 한다.
- **바꾸지 않는 것**:
  - `app.AppConfig`·`SandboxEnvironment`·워커 CLI 플래그(경로 추가 없음).
  - 기존 `grants_state.json`과의 호환(`approvals` 키가 없으면 빈 목록).
  - `architecture_test.go`의 `TC-060-02`(유지만 확인한다).

## 3. 세부 명세

1. **생성**: `Update` 안에서 만료분을 정리(§3.3)하고 새 승인을 붙인다. 같은 `ID`가 이미 있으면 오류(16)다.
2. **소비 (1회성 = 삭제)**: `Update` 안에서 다음 순서로 처리한다.
   - ① 만료분을 정리한다.
   - ② `ID`로 찾는다. 없으면 `domain.NewError(ReasonApprovalRequired, "approval_store", "approval not found or already consumed", nil)`(18)이다.
   - ③ `a.Matches(b, now)`가 `AUTHORIZED`가 아니면 그 Reason(18)이다. PDP 판정 뒤 바뀐 상태를 다시 검증하는 것이다.
   - ④ 슬라이스에서 지운다.

   두 프로세스가 같은 ID를 동시에 소비해도 flock 직렬화로 정확히 1건만 ④에 도달한다.
3. **만료 정리**: `now >= ExpiresAt`인 승인을 쓰기 트랜잭션마다 지운다. 시각은 호출자가 넘긴 `now`다(PEP는 `ClockOffset`을 반영한 시각). 정리되면 그 뒤 판정은 `APPROVAL_REQUIRED`가 된다. 같은 18이고, 이력은 감사에 있다.
4. **감사 시점**: `Update`(잠금)를 반환한 뒤에만 감사를 기록한다. 잠금 안에서 감사나 다른 저장소를 호출하지 않는다([013번 보고서](../../../보고서/013-5대_표준공학검증기법_기반_잔여로드맵_전수정밀진단_및_교정_보고서.md) `DEF-05`).
5. **자기 승인의 범위 (024 A-7)**: 정직한 워커 경로(`subagent worker`, `pep` CLI)는 `VerifyOnly` 스택이라 `AppStack.PAP == nil`이다. 따라서 승인을 만드는 API가 없다. 워커는 소비하려면 원장에 써야 하고 11번 격리도 Zone B 쓰기를 허용하므로, 악의 워커의 원장 직접 변조는 막지 않는다(WHY 한계).
6. **승인자가 jti를 아는 방법**: ask 결과의 `pep.Result.TokenJTI`, 또는 감사 `pep.deny` 레코드의 `token_jti`다(원시 토큰은 기록하지 않는다).
