## 1. 목적 및 배경

승인의 성질을 7대 시나리오로 증명한다. 이 시나리오는 인메모리와 서브프로세스 양 모드에서 모두 통과해야 한다. 서브프로세스 모드는 010의 스포너 18 전파가 있어야 성립한다.
- **핵심 흐름**: 미승인 차단 → 승인 → 같은 토큰 재시도 성공
- **1회성**: 재사용 차단
- **바인딩**: 다른 jti, 인자 바꿔치기
- **만료**
- **회수 우선**

## 3. 신규 시나리오 명세 (`G14`)

| ID | 시나리오명 | 입력 조건 | 기대 Exit | 기대 감사 (`ExpectedAction` / `ExpectedDecision` / `ExpectedReason`) | 핵심 증거 |
|:---:|---|---|:---:|---|---|
| `E2E-67` | 승인 필수 작업의 미승인 ask 차단 | 승인 필요 쓰기 Grant + 일회성 토큰, 승인 없음 | `18` | `pep.deny` / `ask` / `APPROVAL_REQUIRED` | 파일 0바이트 무변화 |
| `E2E-68` | ask 후 승인, 같은 토큰 재시도 성공 | 일회성 토큰 1차 호출(18) → `Result`/감사의 jti로 승인 → 같은 토큰 재시도 | `0` | `pep.allow` / `allow` / `AUTHORIZED` | 파일에 재시도 내용 기록, 원장 승인 0건, 감사에 앞선 `ask` 레코드 존재 |
| `E2E-69` | 승인 1회 소비 후 재사용 차단 | 예산 토큰(`MaxCalls: 2`)에 승인 1건 → 1차(0) → 2차 | `18` | `pep.deny` / `ask` / `APPROVAL_REQUIRED` | 리플레이(11)가 아니라 승인 1회성으로 차단, 파일은 1차 내용 |
| `E2E-70` | 다른 토큰(jti)의 승인 도용 차단 | 토큰 A의 jti에 승인 → 토큰 B로 호출 | `18` | `pep.deny` / `ask` / `APPROVAL_MISMATCH` | 파일 무변화, 승인 원장 무변화 |
| `E2E-71` | 승인 후 인자 바꿔치기 차단 (Confused Deputy) | `--arg-hash = DataDigest("approved")`로 승인 → 같은 토큰으로 `"tampered"` 쓰기 | `18` | `pep.deny` / `ask` / `APPROVAL_MISMATCH` | 파일 무변화, 감사 `arg_hash == DataDigest("tampered")` ≠ 승인 지문 |
| `E2E-72` | TTL 만료 승인 차단 | 승인 TTL 1분, 토큰 TTL 10분, `ClockOffset: 2m`로 호출 | `18` | `pep.deny` / `ask` / `APPROVAL_EXPIRED` | `pdp.Request.Now`(오프셋 반영) 기반 만료 |
| `E2E-73` | 승인 후 Grant 회수 시 승인 우회 차단 | 유효 승인 발급 → `RevokeGrant` → 호출 | `12` | `pep.deny` / `deny` / `GRANT_REVOKED` | 승인이 있어도 회수가 우선 |

> **서브프로세스 역순 스캔 규약 ([013번 보고서](../../../보고서/013-5대_표준공학검증기법_기반_잔여로드맵_전수정밀진단_및_교정_보고서.md) `DEF-01`)**: 서브프로세스 모드에서는 부모 스포너가 마지막에 `ORCHESTRATE_COLLECT` 이벤트를 남긴다. 그래서 모든 G14 시나리오는 `ExpectedAction`(`pep.deny`/`pep.allow`)을 명시해 [`assertion.go`](../../../../internal/harness/assertion.go)가 실제 PEP 판정 이벤트를 검사하게 한다.
>
> **E2E-68·E2E-70·E2E-71의 jti**: 시나리오는 토큰을 직접 발급하므로 `IssueResult.Claims.JWTID`를 쓴다. 승인자가 ask 결과에서 jti를 얻는 경로(`Result.TokenJTI`)는 040 TC-040-01이 증명한다.
