## 1. 목적 및 배경

PDP가 `ASK`를 내면 PEP는 Gate 2에서 멈추고 `18`로 끝난다. 이때 jti·승인·예산·파일 어느 것도 바뀌지 않는다. PDP가 승인으로 `ALLOW`를 내면, PEP는 그 승인(`ApprovalID`)만 원자적으로 소비한 뒤 실행한다.
지금 PEP는 Gate 1에서 jti를 바로 소비한다([`gateway.go`](../../../../internal/authz/pep/gateway.go) 243행 `RecordReplay: true`, [`verifier.go`](../../../../internal/authn/token/verifier.go) 270행). 그래서 ask 뒤 같은 토큰으로 재시도하면 항상 11이다. 사용자 결정 1(D-06)에 따라 **Gate 1은 읽기 확인만 하고, PDP allow 직후에 소비**한다. 원장 롤백 연산은 만들지 않는다.

## 2. 파급 범위와 무영향 근거

- **변경**:
  - `internal/authn/token/replay.go`: `ReplayLedger`에 `IsConsumed(jti string) (bool, error)`(공유 잠금 읽기)를 추가한다.
  - `internal/authn/token/verifier.go`:
    - `VerifyOptions.CheckReplay bool`: 9단계에서 `IsConsumed`만 본다. 이미 쓴 jti면 지금 9단계와 **같은** 감사(`authn.verify`, `TOKEN_REPLAY_DETECTED`)를 남기고 11을 반환한다. 예산 토큰은 지금처럼 건너뛴다.
    - `TokenVerifier`에 `ConsumeReplay(claims domain.TokenClaims, auditCtx domain.AuditContext) error`를 추가한다. `claims.Budget != nil`이거나 원장이 nil이면 아무것도 하지 않는다. 그 밖에는 `CheckAndConsume` 한 번으로 소비하고, 실패하면 9단계와 같은 감사 + 11이다(감사 실패는 15). [`gateway_test.go`](../../../../internal/authz/pep/gateway_test.go)의 `stubVerifier`(840행)에도 구현한다.
  - `internal/authz/pep/gateway.go`:
    - `StageReplay Stage = "gate2b_replay"`, `StageApproval Stage = "stage3a_approval"`.
    - `type ApprovalConsumer interface { ConsumeApproval(id string, b domain.ApprovalBinding, now time.Time) error }`, `Config.ApprovalConsumer`. 구체 패키지 `state`는 import하지 않는다.
    - Gate 1: `RecordReplay: false, CheckReplay: true`.
    - Gate 2: `pdp.Request`에 `TokenJTI: state.tokenJTI`, `ArgHash: state.argHash`(이미 있음, 138·162행), `Now: g.clock.Now().UTC().Add(req.ClockOffset)`을 넣는다. `Now`는 `state.evalNow`에 둔다. `ALLOW`이면 `state.approvalID = decision.ApprovalID`. `ALLOW`가 아니면 지금처럼 `decision.Reason`으로 오류를 반환한다(`ASK`는 Reason이 18로 매핑된다).
    - `StageReplay`(Gate 2 직후): `g.cfg.Verifier.ConsumeReplay(verifiedClaims.Claims, auditCtx)`.
    - `StageApproval`(Gate 2c 뒤, Stage 3b 앞, `state.approvalID != ""`일 때만):
      - `ApprovalConsumer`가 nil이면 `INTERNAL_ERROR`(16, Fail-Closed).
      - 그렇지 않으면 `ConsumeApproval(state.approvalID, binding, state.evalNow)`. 실패하면 그 Reason(18)이다.
      - 성공하면 잠금이 풀린 뒤 `approval.consumed` 감사(`TokenJTI`, `ArgHash`, `Metadata.approval_id`)를 남긴다. 감사가 실패하면 `AUDIT_LOG_FAILED`(15)다. 승인은 이미 소멸했으므로 Fail-Closed다.
    - `logEvent`: `!success && domain.ExitCodeForReason(reason) == domain.ExitApprovalRequired`이면 `Decision: "ask"`.
  - `internal/app/builder.go`: `pep.Config.ApprovalConsumer = state.NewApprovalConsumer(stateStore)`(`stateStore != nil`일 때).
- **바꾸지 않는 것**:
  - `audit.NormalizeEvent`. 소문자 `"ask"`를 이미 보존한다(`audit.go` 76~99행). 회귀 TC만 둔다.
  - 교환(`RecordReplay: false`)과 `token verify` CLI(`RecordReplay` 플래그).
  - 재사용 토큰의 Gate 1 거부(E2E-18, TC-PEP-05, E2E-60): 거부 단계·사유·감사가 그대로다.
  - 승인이 필요 없는 요청: `StageApproval`을 건너뛴다.
  - `TC-060-04`(`Execute` 단일 `return`): ask도 `finalize`로 수렴한다.
- **의도된 동작 변경**: PDP가 deny(12)를 낸 일회성 토큰은 소비되지 않는다. 실행이 없었으므로 「1회 실행」 의미는 유지된다.

## 3. 세부 명세

1. **단계 순서 (D-08)**: Gate 0 → Gate 1(읽기 확인) → Gate 2(PDP, ask면 정지) → `StageReplay` → Gate 2c Jail → `StageApproval` → Stage 3b Budget → Stage 4 감사 → Stage 5 I/O.
   - `StageReplay`가 Jail 앞에 있으므로, 경로 위반 요청도 토큰은 소비한다(지금과 같음).
   - `StageApproval`이 Jail 뒤에 있으므로 경로 위반은 승인을 태우지 않는다. Budget 앞에 있으므로 승인 경합에서 진 요청은 예산을 차감하지 않는다.
   - 소비한 승인은 이후 단계(Budget·Stage 4·Stage 5)가 실패해도 되돌리지 않는다(D-07).
2. **ask 후 재시도 흐름**:
   - 일회성 토큰(`jti-1`)으로 호출하면 Gate 2가 `ASK`(18)를 낸다. 파일·jti·예산은 무변화이고, `Result.TokenJTI == "jti-1"`이다.
   - `approval grant --jti jti-1` 뒤 같은 토큰으로 재호출하면 Gate 1 확인을 통과(미소비)하고, Gate 2가 `ALLOW`+ID를 낸다. 그다음 `StageReplay`에서 소비, `StageApproval`에서 승인 삭제, I/O를 거쳐 0으로 끝난다.
3. **동시성**: 같은 일회성 토큰 두 요청은 모두 Gate 1을 통과할 수 있지만 `StageReplay`의 `CheckAndConsume`에서 하나만 이긴다(패자 11). 승인 재사용 경합은 예산 토큰(리플레이 미적용)에서만 생기고, `StageApproval`에서 하나만 이긴다(패자 18).
