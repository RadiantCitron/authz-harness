## 1. 목적 및 배경

PDP가 `DecisionAsk`를 반환했을 때 PEP가 Stage 5(파일 I/O)로 진입하지 않고 즉시 `ExitApprovalRequired(18)`로 Fail-Closed 종료하도록 배선하고, 반대로 승인이 확인되어 `DecisionAllow`가 났을 때는 Stage 4(사전 커밋 감사) 직전에 승인 원장에서 해당 승인을 **원자적으로 1회용 소비(`ConsumeMatching`)**하도록 구현한다.
특히 두 가지 코드 수준 정합성을 함께 보장한다:
1. **`ask(18)` 반환 시 토큰 `jti` 비소진 보존**: 워커가 미승인 상태에서 `ask(18)`를 받은 뒤 사람이 해당 토큰의 `jti`에 `approval grant --jti <jti>`를 발급하면 동일 토큰으로 재시도할 수 있어야 하므로, `DecisionAsk`로 멈춘 요청은 `ReplayLedger`에서 토큰 `jti`를 소진하지 않도록 처리한다.
2. **감사 `Decision: "ask"` 일관 보존**: [`internal/audit/audit.go`](../../../../internal/audit/audit.go)의 `NormalizeEvent`와 [`internal/authz/pep/gateway.go`](../../../../internal/authz/pep/gateway.go)의 `logEvent` 모두에서 `ExitApprovalRequired(18)`일 때 `"deny"`가 아닌 `"ask"`를 기록하여 [`internal/harness/assertion.go`](../../../../internal/harness/assertion.go)의 역순 감사 검증(`ExpectedDecision: "ask"`)과 정확히 일치시킨다.

## 2. 파급 범위와 무영향 근거

- **변경**:
  - `internal/audit/audit.go`: `NormalizeEvent`에서 `strings.EqualFold(ev.Decision, "ASK")`일 때 `"ask"`로 정규화 보존하도록 분기 추가
  - `internal/authz/pep/gateway.go`:
    - `internal/authz/state` 구체 패키지를 import하지 않고 `Config`에 `ApprovalConsumer domain.ApprovalConsumer` 포트 필드 추가 ([014번 보고서](../../../보고서/014-모듈레벨_아키텍처원칙_및_내부구현패턴_안티패턴_집중진단_보고서.md) `ARCH-03`)
    - `StageGate2AuthZ`에서 `pdp.Request`에 `TokenJTI: state.tokenJTI`, `ArgHash: state.argHash`(`sha256(req.Data)`), `Now: g.clock.Now().UTC().Add(req.ClockOffset)` 전달
    - `DecisionAsk` 반환 시 토큰 `jti`가 소진된 상태로 남지 않도록 처리하고(예: `Gate 1` 검증 후 `DecisionAsk`가 아닐 때 리플레이 원장 확정, 또는 `DecisionAsk` 시 `ReplayLedger` 롤백), `ExitApprovalRequired(18)` 에러를 반환하여 `finalize`에 수렴(`TC-060-04` 단일 `return` 유지)
    - **Stage 4 직전 원장 소비 순서 고정 ([012번 보고서](../../../보고서/012-타에이전트_구현이관대비_전체설계정합성_및_코어구조_위험요소_검증보고서.md) §3.3-B)**: Gate 2c 통과 후 `Stage4Audit` 직전에 ① 일회성 토큰 `ReplayLedger` 확정 → ② (`RequiresApproval`일 때) `g.cfg.ApprovalStore.ConsumeMatching(state.subject, state.normAction, state.resource, state.tokenJTI, state.argHash, effectiveNow)` 원자적 1회용 소비(`approval.consumed` 감사 기록) → ③ (`Budget != nil`이고 쓰기 요청일 때) `BudgetLedger.Consume` 순서로 실행하여, 동시 승인 소비 경합(`TC-020-01`)에서 패배한 요청이 예산을 차감하지 않고 즉시 `ExitApprovalRequired(18)`로 종료되도록 보장
    - `g.logEvent`에서 `!success && domain.ExitCodeForReason(reason) == domain.ExitApprovalRequired`이면 `Decision: "ask"`로 기록
  - `internal/mcp/errors.go`, `internal/ui/pipeline.go`, `internal/ui/explain.go`: 종료 코드 `18`(`ExitApprovalRequired`) 및 `APPROVAL_REQUIRED`/`APPROVAL_EXPIRED`/`APPROVAL_MISMATCH` 매핑·해설 추가
- **무영향**:
  - 일반 Grant(`RequiresApproval: false`) 요청은 승인 소비 단계를 거치지 않으며, 기존 `Gate 1`·`Gate 2(DENY)` 리플레이 동작(`TC-PEP-05`, `E2E-20`)과 100% 동일하게 동작한다.

## 3. 세부 명세

1. **`ask(18)` 후 동일 토큰(`jti`) 재시도 흐름 및 1회용 승인 소비 검증**:
   - 미승인 상태에서 토큰(`jti-1`)으로 호출 시 `Gate 2(PDP)`가 `DecisionAsk(18)`를 반환하며 파일은 0바이트 무변화로 남고 `jti-1`은 리플레이 원장에 소비되지 않는다.
   - 이후 `approval grant --jti jti-1`로 승인을 발급하고 동일 토큰(`jti-1`)으로 재호출하면 `Gate 1`과 `Gate 2`를 통과하고 PEP가 `ConsumeMatching`으로 승인을 원자 소비(`Consumed = true`)한 뒤 파일 I/O를 완료(`Exit 0`)한다.
   - **승인의 1회성 검증(`TC-040-02`)**: 1차 실행 성공 후 동일 `jti`로 2차 실행했을 때 토큰 리플레이(`11`)가 아닌 **승인 원장의 1회성 소비(`18 / APPROVAL_REQUIRED`)**에 의해 차단됨을 검증하기 위해, `TC-040-02`(및 `050`의 `E2E-68`)에서는 다회 호출이 허용된 토큰(또는 `RecordReplay: false` 검증 조건)으로 2회 연속 호출하여 1회차 `ExitCode == 0`, 2회차 `ExitCode == 18`(`APPROVAL_REQUIRED`)을 검증한다.
2. **`audit.NormalizeEvent` 및 `pep.Gateway.logEvent` `"ask"` 보존**:
   - `DefaultEvaluator.Evaluate`는 감사 로그의 마지막 이벤트를 역순 조회하므로, `pdp.decide` 이벤트뿐 아니라 `pep.Gateway.finalize`가 기록하는 마지막 `pep.deny` 이벤트에서도 `ExitCodeForReason(reason) == domain.ExitApprovalRequired`일 때 반드시 `event.Decision = "ask"`로 세팅한다.
