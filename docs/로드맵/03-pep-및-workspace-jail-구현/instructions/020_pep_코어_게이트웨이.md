## 1. 목적 (Context & Why)

본 지시서는 Gate 1(AuthN TokenVerifier)과 Gate 2(Pure PDP)의 인가 판정 결과를 물리적 격리 환경(Workspace File Jail) 및 감사 로깅과 안전하게 결합하는 **정책 집행 게이트웨이(PEP Core Gateway, `internal/authz/pep`)**를 구축하는 작업이다.

보안 불변식 및 설계 원칙:
1. **단일 정책 집행점 (Single Point of Enforcement)**:
   - 파일 I/O(읽기/쓰기)를 수행하려는 모든 작업은 반드시 PEP 게이트웨이를 경유해야 하며, 게이트웨이를 우회하는 직접 디스크 I/O 호출을 차단한다.
2. **5단계 순차 관문 파이프라인 (5-Stage Gate Pipeline)**:
   - `Gate 1(AuthN)` -> `Gate 2(PDP)` -> `Gate 2c(Jail)` -> `Stage 4(Pre-Commit Audit)` -> `Stage 5(Confined File I/O)`의 단방향 상태 머신을 통과해야만 파일 작업이 집행된다.
3. **감사 기록 실패 시 즉각 중단 (Fail-Closed Audit Enforcement, AP-09)**:
   - 인가 결정이 `ALLOW`이고 경로가 안전하더라도, 실행 전 감사 로그(`audit.Writer`) 기록이 실패하거나 결함 주입(`--inject-audit-failure`)된 경우, 파일 생성/수정을 즉시 중단하고 `EXIT_AUDIT_FAILURE(15)`를 반환한다.
4. **거부 시 무부작용 불변식 (Zero Side-Effects on Deny)**:
   - 인증 실패(`11`), 인가 거부(`12`), 경로 위반(`13`), 감사 실패(`15`) 등 어떠한 실패/거부 상황에서도 파일 디스크립터 생성 또는 디스크 쓰기 부작용 0바이트를 보장한다.
5. **Zero Leakage 및 원시 토큰 유출 원천 차단**:
   - 감사 로그 및 운영 진단 로그에 서명된 원시 Bearer 토큰 문자열 출력을 금지하며, 오직 `TokenJTI`, 주체(`Subject`), 클레임 요약만을 기록한다.
6. **표준 프로세스 종료 규약 준수**:
   - 마스터 로드맵 §13에 정의된 `ExitSuccess(0)`, `ExitTokenInvalid(11)`, `ExitAuthzDenied(12)`, `ExitPathViolation(13)`, `ExitBadInput(14)`, `ExitAuditFailure(15)`를 엄격히 반환한다.

        │                       │       │                        │                        │

                                                v

- **Layer 3 (`internal/authz/pep`)**:
  - 시스템의 중심에서 AuthN, PDP, Jail, Audit 계층을 조합(Orchestrate)하여 인가 정책 집행을 보장한다.
  - 하위 계층(Layer 2A, 2B, 2C, 1, 0)에만 의존하며, CLI(Layer 5)나 OS 프로세스 런타임(Layer 4)을 참조하지 않는 단방향 계층 원칙을 준수한다.
- **Layer 2B (`internal/authz/pdp`)**: 파일 I/O 부작용 0%의 순수 인가 결정 엔진 유지.
- **Layer 2C (`internal/jail`)**: 상위 탈출 및 외부 심볼릭 링크를 차단하는 순수 파일 경계 격리 엔진.
- **Layer 1 (`internal/audit`)**: 불변 해시 체인 기반 감사 증거 기록.

## 3. 세부 설계 및 인터페이스 계약

### 3.1 요청/응답 데이터 모델 (`internal/authz/pep`)

```go
package pep

import (
	"context"

	"authz-harness/internal/domain"
)

// Stage 는 5단계 관문 집행 파이프라인의 현재 단계를 식별한다.
type Stage string

const (
	StageGate1AuthN Stage = "gate1_authn"
	StageGate2AuthZ Stage = "gate2_authz"
	StageGate2cJail Stage = "gate2c_jail"
	Stage4Audit     Stage = "stage4_audit"
	Stage5FileIO    Stage = "stage5_io"
)

// Request 는 PEP에 파일 작업 집행을 요청하는 매개변수 명세다.
type Request struct {
	Token              string        // Bearer Access Token (RFC 9068)
	Action             domain.Action // domain.ActionRead ("read") 또는 domain.ActionWrite ("write")
	Resource           string        // 접근 대상 파일 경로 (상대 경로 권장)
	Data               []byte        // 쓰기 요청(ActionWrite) 시 기록할 바이트 데이터
	InjectAuditFailure bool          // 결함 주입 스위치: Pre-Commit 감사 실패 시뮬레이션
	ExpectedAudience   string        // 토큰 수신자 기대값 (기본값: "authz-harness")
	ExpectedSubject    string        // 선택적 주체 기대값 검증
	TraceID            string        // 트랜잭션 추적 식별자 (미지정 시 자동 생성)
}

// Result 는 PEP 관문 집행 결과 및 단계별 판정 세부 정보다.
type Result struct {
	Allowed    bool            `json:"allowed"`
	ExitCode   domain.ExitCode `json:"exit_code"`
	Stage      Stage           `json:"failed_stage,omitempty"`
	Reason     domain.Reason   `json:"reason"`
	Details    string          `json:"details,omitempty"`
	Subject    string          `json:"subject,omitempty"`
	TokenJTI   string          `json:"token_jti,omitempty"`
	SafePath   string          `json:"safe_path,omitempty"`
	BytesRead  int             `json:"bytes_read,omitempty"`
	BytesWrote int             `json:"bytes_wrote,omitempty"`
	Data       []byte          `json:"-"` // 읽기 요청 성공 시 반환되는 파일 내용 (JSON 직렬화 제외)
}
```

### 3.2 게이트웨이 인터페이스 및 구성체

```go
// Gateway 는 파일 I/O 요청에 대한 인가 집행 관문 인터페이스다.
type Gateway interface {
	// Execute 는 5단계 관문(AuthN -> PDP -> Jail -> Audit -> I/O)을 거쳐 파일 작업을 집행한다.
	Execute(ctx context.Context, req Request) (*Result, error)
}

// Config 는 Gateway 생성에 필요한 하위 컴포넌트 의존성 주입 구조체다.
type Config struct {
	Verifier    token.TokenVerifier // Layer 2A: Gate 1 Bearer 토큰 검증기
	PDP         pdp.Service         // Layer 2B: Gate 2 순수 인가 결정 엔진
	Jail        jail.Jail           // Layer 2C: Gate 2c 격리 파일 경계
	AuditWriter audit.Writer        // Layer 1: 감사 로그 기록기
}
```

## 4. 5단계 관문 집행 상태 머신 및 에러 매핑

```text
[요청 도착: Execute(ctx, req)]
      │
      ├── 0. 입력 기본 검증 (Action, Resource 빈값 검증)
      │      실패 시: ExitBadInput (14), Reason: INVALID_ARGUMENTS
      │
      v
[Stage 1: Gate 1 - AuthN Token Verification]
  ├── verifier.VerifyToken(req.Token, VerifyOptions{...}, auditCtx)
  └── 실패 시:
        - 감사 이벤트 기록 (pep.gate1_denied, success: false, reason: verifiedErr)
        - 반환: Result{Allowed: false, ExitCode: ExitTokenInvalid (11), Stage: StageGate1AuthN, Reason: reason}
      │ (성공: verifiedClaims 획득)
      v
[Stage 2: Gate 2 - Pure PDP Authorization]
  ├── pdp.Request{Subject: verifiedClaims.Subject, Action: req.Action, Resource: req.Resource, Epoch: verifiedClaims.Epoch}
  ├── pdpService.Decide(ctx, pdpReq)
  └── 실패 또는 Decision == DENY 시:
        - 감사 이벤트 기록 (pep.gate2_denied, success: false, reason: decision.Reason)
        - 반환: Result{Allowed: false, ExitCode: ExitAuthzDenied (12), Stage: StageGate2AuthZ, Reason: decision.Reason}
      │ (성공: Decision == ALLOW)
      v
[Stage 3: Gate 2c - Workspace Jail Boundary Verification]
  ├── jail.ResolvePath(req.Resource, req.Action == domain.ActionWrite)
  └── 실패 시 (ErrPathViolation, ErrSymlinkEscape 등):
        - 감사 이벤트 기록 (pep.gate2c_denied, success: false, reason: pathErrReason)
        - 반환: Result{Allowed: false, ExitCode: ExitPathViolation (13), Stage: StageGate2cJail, Reason: pathReason}
      │ (성공: safePath 획득)
      v
[Stage 4: Pre-Commit Audit Verification (Fail-Closed)]
  ├── req.InjectAuditFailure == true 이거나 auditWriter.Log(...) 실패 시:
        - **파일 I/O 즉시 중단 (디스크 변경 0바이트 사수)**
        - 반환: Result{Allowed: false, ExitCode: ExitAuditFailure (15), Stage: Stage4Audit, Reason: "AUDIT_LOG_FAILED"}
      │ (성공: 감사 로그 기록 완료)
      v
[Stage 5: Confined File I/O Execution]
  ├── Read 요청: jail.ReadFile(req.Resource)
  ├── Write 요청: jail.WriteFile(req.Resource, req.Data)
  └── 성공 시:
        - 최종 성공 감사 기록 (pep.execute_success, success: true)
        - 반환: Result{Allowed: true, ExitCode: ExitSuccess (0), Stage: Stage5FileIO, SafePath: safePath, Data: ...}
```

## 5. 사전 점검 및 실패 위험 분석 (Pre-Mortem)

1. **위험: Pre-Commit 감사 실패 시 파일 변경 누출 (Fail-Open 취약점)**
   - *영향*: 결함 주입(`InjectAuditFailure=true`) 또는 디스크 풀로 감사 쓰기가 실패했을 때, 파일 쓰기가 먼저 실행되었거나 버퍼에 남아있어 증거 없는 파일 변조 발생.
   - *방어책*: Stage 4의 `AuditWriter.Log()`가 성공적으로 리턴되기 전에는 `jail.WriteFile`을 호출하지 않는다. 에러 발생 시 즉시 리턴하고 디스크 부작용 0바이트를 테스트로 입증한다.
2. **위험: PDP 리소스 경로와 Jail 실제 경로의 불일치로 인한 인가 우회**
   - *영향*: PDP 인가 요청에는 `./report.txt`를 보내고 Jail은 `sub/report.txt`를 열어버리는 의미적 불일치(Semantic Desynchronization).
   - *방어책*: PEP는 `req.Resource`를 정규화하여 PDP 검증과 Jail `ResolvePath`에 동일하게 전달하며, Jail의 격리 검증을 통과한 안전 경로(`safePath`)를 최종 결과에 바인딩한다.
3. **위험: 감사 로그에 원시 Bearer 토큰 문자열 유출 (Security Leakage)**
   - *영향*: JWT 서명 토큰 전체가 `audit.jsonl`에 남아 로그 탈취 시 토큰 재사용 공격에 노출.
   - *방어책*: PEP의 감사 이벤트 페이로드에는 오직 `verifiedClaims.JTI`와 `Subject`만 담고, `req.Token` 원본 문자열은 일체 직렬화하지 않는다.
