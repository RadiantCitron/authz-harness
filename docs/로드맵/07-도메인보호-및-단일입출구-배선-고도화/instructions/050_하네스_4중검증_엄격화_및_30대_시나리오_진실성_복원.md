## 1. 목적 (Context & Why)

본 지시서는 감사 보고서에서 적발된 동어반복(자기충족적) 테스트 안티패턴 3종 — **AP-07(`assertion.go`가 해시 필드가 비어 있으면 해시 체인 검사를 건너뛰어 가짜 통과시키고, `E2E-30` 감사 변조 탐지 시나리오가 `RequireValidChain: false` 및 `ExitSuccess(0)`로 변조 적발 자체를 우회한 문제)**, **AP-08(`assertion.go`가 `ExpectedAction` 불일치 시 `if !found` 폴백 루프로 필터를 버리고 아무 이벤트나 채택한 문제)**, **AP-09(`E2E-28` `trace_id` 누락 시나리오가 실제로는 빈 `Action("")`으로 `ExitBadInput`을 유도하고, 카탈로그 시나리오들이 OS 서브프로세스 경계를 거치지 않은 문제)** — 을 전면 교정하여 **100% 정직하고 엄격한 4중 검증(Quad-Assertion)**을 완성하는 단계다.

보안 및 검증 불변식에 따라 ([AGENTS.md](../../../../AGENTS.md) §2 준수):
1. **가짜 해시 체인 통과(Vacuous Pass) 원천 제거**:
   - `internal/harness/assertion.go`에서 `exp.HashChain.RequireValidChain == true`일 때 이벤트에 `curr_hash`가 비어 있으면 건너뛰지 않고 **즉시 `HashChainPassed = false`로 실패 판정**한다.
   - 해시 체인 검증은 `audit.VerifyHashChain(env.AuditPath)`를 호출하여 첫 줄부터 마지막 줄까지 SHA-256 체인 무결성을 엄격히 검증한다.
2. **무단 폴백(`if !found`) 제거 및 정확한 `ExpectedAction`·`ExpectedTraceID` 매칭**:
   - `assertion.go`에서 `ExpectedAction` 또는 `ExpectedTraceID`가 지정되었는데 일치하는 감사 이벤트를 찾지 못하면, 다른 이벤트를 끌어다 쓰는 폴백 없이 즉시 `AuditPassed = false`로 실패 판정한다.
3. **`E2E-28`·`E2E-30` 진실성 복원 및 서브프로세스 E2E 경유 보장**:
   - `E2E-28`(`trace_id` 누락 요청 차단): 유효한 `Action: domain.ActionFileWrite`와 유효한 `Resource`를 넣되 `TraceID: ""`(또는 `SubagentRequest{TraceID: ""}`)로 요청하여, 실제로 **`TraceID` 누락(`ReasonMissingTraceContext`, 종료 코드 `14`) 때문에 차단**되는지 정직하게 검증한다.
   - `E2E-30`(사후 감사 로그 변조 적발): 정상 파일 쓰기 후 `audit.jsonl`을 변조한 뒤 `audit.VerifyHashChain(env.AuditPath)`(또는 `audit verify` 러너)를 실행하여 **실제로 변조를 적발하고 `ExitAuditFailure (15)` 및 `ReasonAuditIntegrityBroken`을 반환**할 때만 `PASS`하도록 복원한다.
   - 카탈로그 내 위임/워커 실행 시나리오가 실제 `orchestrator.SubprocessSpawner` → `subagent` OS 서브프로세스 경계를 통과하여 검증되도록 보강한다.

## 3. 세부 설계 및 인터페이스 계약

### 3.1 엄격화된 `DefaultEvaluator.Evaluate` 알고리즘 (`internal/harness/assertion.go`)

1. **Assertion 3 (Audit Reason & Decision) 엄격 매칭**:
   - `events`를 역순 탐색하되:
     - `exp.Audit.ExpectedTraceID != ""`이면 `ev.TraceID == exp.Audit.ExpectedTraceID`인 이벤트만 대상.
     - `exp.Audit.ExpectedAction != ""`이면 `ev.Action == exp.Audit.ExpectedAction`인 이벤트만 대상.
   - 일치하는 이벤트가 없으면 **절대 다른 이벤트를 대신 채택하지 않고** `res.AuditPassed = false`, `res.Passed = false`로 기록한다.
2. **Assertion 4 (Hash Chain Integrity) 엄격 매칭**:
   - `exp.HashChain.RequireValidChain == true`인 경우:
     - `len(events) == 0`이거나 어느 한 이벤트라도 `CurrHash == ""`이면 즉시 `res.HashChainPassed = false` 처리.
     - `audit.VerifyHashChain(env.AuditPath)`를 호출하여 에러가 반환되면 즉시 `res.HashChainPassed = false` 처리.

### 3.2 `E2E-28` 및 `E2E-30` 시나리오 복원 명세 (`internal/harness/catalog/g7_observability_audit.go`)

- **`E2E-28` (`trace_id` 누락 요청 차단)**:
  - `Action: domain.ActionFileWrite`, `Resource: "output.txt"`, `TraceID: ""`, `RequireTraceID: true`(또는 `subagent.SubagentRequest{TraceID: ""}`)로 실행.
  - 기대 결과: `ExitCode: domain.ExitBadInput (14)`, `ExpectedReason: domain.ReasonMissingTraceContext`, 파일 생성 0건.
- **`E2E-30` (`사후 감사 로그 변조 적발`)**:
  - `Execute` 내부 실행 절차 (4단계 순차 실행):
    1. `res, err := stack.PEP.Execute(ctx, ...)`: 정상 파일 쓰기 수행 (최초 정상 종료코드 0 기록).
    2. `data, err := os.ReadFile(env.AuditPath)`: 파일 내용을 읽어 유효한 JSON 형식 내의 특정 필드(예: 첫 번째 레코드의 `resource`)를 `"tampered.txt"`로 변조하여 재저장.
    3. `verifyErr := audit.VerifyHashChain(env.AuditPath)`: 변조 직후 사후 감사 무결성 검증기 직접 호출.
    4. `return domain.ExitCodeFromError(verifyErr, domain.ExitSuccess), nil`: 변조가 적발되어 `verifyErr`가 반환되면 표준 매핑 규칙에 따라 `ExitAuditFailure (15)`를 최종 반환!
  - 기대 결과: `ExitCode: domain.ExitAuditFailure (15)`, `ExpectedReason: domain.ReasonAuditIntegrityBroken`, `RequireValidChain: false` (사후 검증에서 이미 적발 완료되었음을 증명).

## 4. 사전 점검 및 실패 위험 분석 (Pre-Mortem)

1. **위험: `E2E-04`~`06`(G2 AuthN 거부)이나 `E2E-19`~`21`(G5 위임 거부)에서 `setupHarnessStack`이 초기 키 생성 이벤트(`key.rotated`)를 먼저 기록하고 본 실행이 거부 이벤트를 기록할 때, 역순 탐색이 정확히 마지막 거부 이벤트를 찾는지 확인 필요**
   - *방어책*: 역순 탐색(`len(events)-1`부터 `0`까지)은 가장 마지막에 기록된 본 실행의 거부 이벤트를 먼저 만나며, `ExpectedAction`(`token.issue.deny`, `token.exchange.deny`, `pep.deny`)이 정확히 일치하므로 `key.rotated`와 혼동되지 않는다.
2. **위험: `E2E-30`에서 파일이 변조되었으므로 `Evaluate`가 `env.ReadAuditEvents()`를 호출할 때 변조된 줄 때문에 JSON 파싱 에러가 날 가능성**
   - *방어책*: `E2E-30`의 변조 시뮬레이션은 유효한 JSON 형식을 유지하면서 내부 필드값(예: 첫 번째 이벤트의 `actor` 또는 `resource` 문자열)만 살짝 바꾼 뒤 저장한다. 그러면 JSON 파싱은 정상 수행되면서 SHA-256 해시 체인 검증(`VerifyHashChain`)에서만 정확히 해시 불일치(`ReasonAuditIntegrityBroken`, Exit `15`)가 적발된다!
3. **위험: 카탈로그 시나리오가 OS 서브프로세스 경유 시 사전 컴파일된 `BinaryPath` 부재로 `go test` 환경에서 실패할 위험**
   - *방어책*: 일상적인 고속 회귀 검증(30개 카탈로그)은 순수 `StackBuilder` 기반의 인메모리 프로세스 파이프라인(100ms 대)을 유지하되, 실제 OS 서브프로세스 격리 경계(`orchestrator.Spawner` -> `subagent` worker CLI) 검증은 `internal/orchestrator/spawner_test.go` 및 전용 통합 테스트(`TestSubprocessE2E`)에서 `os.Executable()` 또는 테스트 바이너리를 활용해 독립 검증하도록 역할을 명확히 분리한다.

## 5. 4층위 검증 범위 설계

1. **1층위 (정적 분석)**: `assertion.go` 내에 `if !found` 무단 폴백 루프와 `if evPrevHash != "" || evCurrHash != ""` 조건부 스킵 코드가 제거되었는지 확인.
2. **2층위 (단위 검증 — `harness_test.go`)**:
   - 해시 필드(`curr_hash`)가 없는 가짜 감사 이벤트를 넣고 `RequireValidChain: true`로 `Evaluate`를 호출했을 때 **반드시 `HashChainPassed == false`가 반환**되는지 단위 테스트(`TestQuadAssertion_MissingHashFails`)로 검증.
   - `ExpectedAction: "pep.deny"`를 기대했는데 실제 로그에는 `"key.created"`만 있을 때 **반드시 `AuditPassed == false`가 반환**되는지 검증.
3. **3층위 (카탈로그 개별 그룹 검증)**:
   - `go test -v ./internal/harness/catalog/...` 실행 시 `G1`~`G7` 30개 전 시나리오가 엄격해진 `Evaluator` 하에서 100% 통과하는지 검증.
4. **4층위 (CLI 전 구간 E2E 검증)**:
   - `authz-harness run --scenario all` 및 `authz-harness run --scenario E2E-30 --output-format explain` 실행 시 `E2E-30`이 종료 코드 `15`(`ExitAuditFailure`)로 변조 적발 성공(`PASS`)으로 표시되는지 확인.
