## 1. 목적 (Context & Why)

본 지시서는 감사 보고서에서 최우선 치명적 결함으로 지적된 **AP-01(PEP가 비즈니스 정책인 토큰 `Scope` 검증을 월권 수행하고 정작 순수 결정 엔진인 `pdp.Evaluate`에는 `Scope` 검증이 누락된 문제)**과 **AP-02(도메인 로직과 감사 디스크 I/O의 강결합)**를 해결하여 철저한 **도메인 보호(Domain Protection)와 의존성 역전(DIP)**을 확립하는 단계다.

보안 및 아키텍처 불변식에 따라:
1. **결정(PDP)과 집행(PEP)의 엄격한 분리 복원 ([NIST SP 800-162](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-162.pdf))**:
   - `internal/authz/pep/gateway.go`에 임시로 들어가 있던 `tokenScopeAllows` 함수(및 근거 없는 `"*"` / `"admin"` 슈퍼유저 우회 조건)를 제거하고, 순수 결정 엔진인 `internal/authz/pdp`의 `Evaluate` 함수로 이관한다.
   - `pdp.Evaluate`는 파일 I/O 의존성 0%를 유지하면서 **① 주체 Epoch 일치 → ② 토큰 Scope 포함(`TOKEN_INSUFFICIENT_SCOPE`) → ③ 활성/회수 Grant 매칭**의 3단 인가 공식을 단일 순수 함수로 완성한다.
2. **순수 도메인 이벤트(`domain.EventRecorder`) 계약 도입 (DIP 적용)**:
   - 도메인 코어가 디스크 파일을 직접 다루지 않고도 무엇이 결정되었는지 구조화된 사건을 발행할 수 있도록 `internal/domain`에 도메인 이벤트 모델과 인메모리 수집기(`EventRecorder`) 계약을 정의한다.

## 2. 파급 범위와 무영향 근거 증명 및 6계층 DAG 구조

```text
Layer 3:  [internal/authz/pep/gateway.go]
          ├── tokenScopeAllows 삭제 (PEP 내 정책 판단 0% 달성!)
          └── Verifier에서 획득한 claims.Scope 및 claims.Actor를 pdp.Request에 담아 PDP.Decide 호출
                │
                v
Layer 2B: [internal/authz/pdp/service.go]
          ├── pdp.Request 에 TokenScope string, Actor *domain.ActorClaim, TraceID string 필드 추가
          └── Evaluate(req, snapshot) 순수 함수:
               1) 입력 무결성 검증
               2) Security Epoch 일치 검증 (SUBJECT_EPOCH_REVOKED)
               3) TokenScope 포함 검증 (Scope가 지정된 경우 불충분 시 TOKEN_INSUFFICIENT_SCOPE 반환!)
               4) ActiveGrants / RevokedGrants 대조 (AUTHORIZED / GRANT_REVOKED / NO_ACTIVE_GRANT)
                │
                v
Layer 0:  [internal/domain]
          ├── scope.go : ScopeMatches(scopeStr string, action Action, resource string) bool 순수 도메인 규칙
          └── event.go : DomainEvent 및 인메모리 EventBuffer 정의
```

- **변경 파급 범위**:
  - `internal/domain`: `scope.go`(명시적 Scope 매칭 도메인 규칙) 및 `event.go` 신설.
  - `internal/authz/pdp`: `Request` 구조체에 `TokenScope`·`Actor`·`TraceID` 추가 및 `Evaluate` 내 Scope 검증 단계 통합.
  - `internal/authz/pep`: `tokenScopeAllows` 제거 및 `pdp.Request`에 `TokenScope: claims.Claims.Scope` 전달.
  - `internal/cli/pdp.go`: `--scope` 선택적 플래그 지원 추가(순수 PDP CLI에서도 토큰 Scope 결합 시뮬레이션 가능).
- **무영향 근거 증명**:
  - `pdp.Request.TokenScope`가 명시적으로 전달된 경우(예: PEP 경유 시 `RequireScope: true` 또는 `TokenScope != ""`)에는 엄격히 Scope를 대조하고, 토큰 없이 순수 Grant 저장소만 시뮬레이션하는 기존 `pdp_test.go` 케이스(`TokenScope` 미지정)는 하위 호환을 유지하여 기존 테스트가 깨지지 않는다.

## 3. 세부 설계 및 인터페이스 계약

### 3.1 순수 도메인 Scope 매칭 규칙 (`internal/domain/scope.go`)

```go
package domain

// ScopeMatches 는 공백으로 구분된 OAuth 2.1 scope 문자열이 요청된 (action, resource)를 허용하는지 판정하는 순수 함수다.
// 규칙:
// 1. "file:read" 또는 "file:write" (2단 액션 스코프): 해당 액션에 대한 접근 허용
// 2. "file:read:docs/plan.txt" (3단 액션+리소스 특정 스코프): 액션과 정규화된 리소스 경로가 정확히 일치할 때만 허용
// 3. 임의의 암묵적 슈퍼유저("admin" 등) 우회는 허용하지 않는다 (Least Privilege 엄수).
func ScopeMatches(scopeStr string, action Action, resource string) bool
```

### 3.2 확장된 `pdp.Request` 및 `pdp.Evaluate` 계약 (`internal/authz/pdp/service.go`)

```go
type Request struct {
	Subject      string             `json:"subject"`
	Action       domain.Action      `json:"action"`
	Resource     string             `json:"resource"`
	Epoch        domain.Epoch       `json:"epoch"`
	TokenScope   string             `json:"token_scope,omitempty"`
	RequireScope bool               `json:"require_scope,omitempty"` // true 인 경우 TokenScope 가 비어있어도 즉시 거부
	Actor        *domain.ActorClaim `json:"actor,omitempty"`
	TraceID      string             `json:"trace_id,omitempty"`
}

// Evaluate 는 파일 I/O나 외부 상태 변경 없이 오직 req와 snapshot만으로 인가 결정을 내리는 순수 함수다.
func Evaluate(req Request, snapshot *pip.SubjectSnapshot) Decision
```

> **`Actor` 필드의 책임 및 용도 규약**:
> - `pdp.Request.Actor`는 RFC 8693 위임 체인(`act` 클레임)을 통해 요청을 대리 수행하는 위임자 메타데이터다.
> - **1차 책임 (컨텍스트 전파)**: `pdp.Evaluate`가 반환하는 `domain.DomainEvent` 및 최외곽 단일 출구 감사 배선에 대리인 정보(`Actor`)를 결합하여 감사 추적성(`audit.Event.AgentID` 및 위임 계보)을 보존한다.
> - **2차 책임 (인가 확장 포인트)**: 본 단계에서는 주체(`Subject`)의 Grant/Epoch/Scope를 중심으로 판정하되, 향후 대리인의 권한 상한 검증 정책 추가 시 활용할 수 있는 순수 데이터 계약으로 고정한다 (미사용 데드 필드 방지).

## 4. 사전 점검 및 실패 위험 분석 (Pre-Mortem)

1. **위험: 토큰에 빈 `Scope("")`가 들어왔을 때 `TokenScope == ""`를 "Scope 검사 생략"으로 오판하여 통과시킬 위험**
   - *방어책*: `pdp.Request`에 `RequireScope bool` 플래그를 두어, PEP(`pep/gateway.go`)가 호출할 때는 항상 `RequireScope: true`로 설정한다. 따라서 토큰의 `Scope`가 빈 문자열(`""`)이면 `pdp.Evaluate`가 예외 없이 `TOKEN_INSUFFICIENT_SCOPE`로 차단한다.
2. **위험: 3단 리소스 지정 Scope(`file:read:docs/a.txt`)를 가진 토큰으로 다른 파일(`docs/b.txt`)을 요청했을 때 통과될 위험**
   - *방어책*: `domain.ScopeMatches`에서 3단 형식(`action:resource`)인 경우 요청된 `resource`와 정확히 일치할 때만 `true`를 반환하도록 단위 테스트로 철저히 검증한다.

## 5. 4층위 검증 범위 설계

1. **1층위 (정적 아키텍처 검증)**:
   - `TestPDP_StrictNoOSImports` 유지: `internal/authz/pdp`가 `os`, `path/filepath`, `internal/jail`을 절대 import하지 않음을 검증.
   - `internal/authz/pep/gateway.go` 내에 독자적인 Scope 문자열 파싱 함수(`tokenScopeAllows`)가 존재하지 않음을 확인.
2. **2층위 (순수 도메인 단위 테스트 — 디스크 I/O 0%)**:
   - `internal/domain/scope_test.go` 및 `internal/authz/pdp/pdp_test.go`:
     - 중앙 Grant에 `file:write`가 활성 상태이더라도, `TokenScope: "file:read"`, `RequireScope: true`로 `file:write`를 요청하면 `pdp.Evaluate`가 `DecisionDeny` 및 `ReasonTokenInsufficientScope`를 반환함을 메모리 상에서 즉시 검증.
     - `TokenScope: "file:read:docs/a.txt"`로 `docs/b.txt` 읽기를 요청하면 `pdp.Evaluate`가 `ReasonTokenInsufficientScope`를 반환함을 검증.
3. **3층위 (상태 및 정합성 검증)**:
   - PEP를 통해 Scope 부족 요청 실행 시 `StageGate2AuthZ` 단계에서 차단되고, 파일 시스템 변경 0바이트 및 감사 사유 `TOKEN_INSUFFICIENT_SCOPE`가 기록됨을 확인.
4. **4층위 (CLI 통합 검증)**:
   - `authz-harness pdp decide --sub worker-01 --action file:write --resource a.txt --scope file:read` 실행 시 종료 코드 `12`(`ExitAuthzDenied`) 및 `TOKEN_INSUFFICIENT_SCOPE` 출력 확인.

## 6. 10대 사전 인수 테스트 시나리오 (Acceptance Scenarios)

| ID | 테스트 시나리오 명 | 입력 조건 (`pdp.Request` + `Snapshot`) | 기대 결과 (`Decision` / `Reason`) | 검증 포인트 |
|---|---|---|---|---|
| **TC-020-01** | Write Grant 보유 + Read 전용 토큰으로 Write 요청 | Grant=`file:write:a.txt`, TokenScope=`"file:read"`, Action=`file:write` | `DENY` / `TOKEN_INSUFFICIENT_SCOPE` | **핵심 결함 AP-01 해결 증명**: Grant가 있어도 축소된 토큰 Scope 밖이면 PDP가 차단 |
| **TC-020-02** | 특정 파일 Scope(`a.txt`) 토큰으로 타 파일(`b.txt`) 요청 | Grant=`file:read:b.txt`, TokenScope=`"file:read:a.txt"`, Resource=`b.txt` | `DENY` / `TOKEN_INSUFFICIENT_SCOPE` | 3단 리소스 한정 Scope의 엄격한 경계 검증 |
| **TC-020-03** | `RequireScope: true` 상태에서 빈 Scope(`""`) 요청 | Grant=`file:read:a.txt`, TokenScope=`""`, RequireScope=`true` | `DENY` / `TOKEN_INSUFFICIENT_SCOPE` | 빈 Scope 우회 원천 차단 |
| **TC-020-04** | 암묵적 `"admin"` Scope 문자열 우회 차단 | Grant=`file:write:a.txt`, TokenScope=`"admin"`, Action=`file:write` | `DENY` / `TOKEN_INSUFFICIENT_SCOPE` | PEP에 있던 비표준 `"admin"` 슈퍼유저 백도어 제거 증명 |
| **TC-020-05** | 다중 Scope(`"file:read:a.txt file:write:b.txt"`) 정상 매칭 | Grant=`file:write:b.txt`, TokenScope=`"file:read:a.txt file:write:b.txt"` | `ALLOW` / `AUTHORIZED` | 공백 구분 복수 Scope 내 정확한 매칭 확인 |
| **TC-020-06** | Epoch 불일치와 Scope 부족이 동시 발생할 때 우선순위 | CurrentEpoch=`2`, ReqEpoch=`1`, TokenScope=`"file:read"`, Action=`file:write` | `DENY` / `SUBJECT_EPOCH_REVOKED` | 킬스위치인 Epoch 불일치가 최우선으로 평가됨을 보장 |
| **TC-020-07** | Scope는 충분하나 Grant가 Revoke된 경우 | RevokedGrant=`file:read:a.txt`, TokenScope=`"file:read:a.txt"` | `DENY` / `GRANT_REVOKED` | 토큰 Scope와 실시간 Grant 둘 다 충족해야 허용됨을 증명 |
| **TC-020-08** | Scope는 충분하나 Grant가 아예 없는 경우 | ActiveGrants=`[]`, TokenScope=`"file:read:a.txt"` | `DENY` / `NO_ACTIVE_GRANT` | 토큰만 있고 중앙 권한이 없을 때 차단 증명 |
| **TC-020-09** | `pdp decide` CLI에서 `--scope` 플래그 시뮬레이션 | `--sub worker-01 --action file:write --resource a.txt --scope file:read` | Exit Code `12`, `TOKEN_INSUFFICIENT_SCOPE` | CLI에서도 순수 PDP Scope 평가 가능 확인 |
| **TC-020-10** | `EventRecorder` 인메모리 도메인 이벤트 수집 | 컨텍스트 내 `EventBuffer`에 도메인 결정 이벤트 기록 | 디스크 파일 생성 없이 메모리 슬라이스에 이벤트 정확히 적재 | 도메인 이벤트와 디스크 I/O의 분리 입증 |
