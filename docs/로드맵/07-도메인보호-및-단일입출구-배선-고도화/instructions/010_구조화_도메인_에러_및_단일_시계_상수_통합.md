## 1. 목적 (Context & Why)

본 지시서는 감사 보고서에서 적발된 **AP-10(`strings.Contains(err.Error(), ...)` 문자열 검색에 의존하는 에러·종료코드 분기 안티패턴)**과 **AP-12(토큰 발급 기본 `Audience`와 PEP 검증 기본 `Audience` 불일치, `keys.Clock` 중복 정의 및 `time.Now()` 직접 호출)**를 구조적으로 제거하는 첫 번째 단계다.

보안 및 아키텍처 불변식에 따라:
1. **문자열 에러 파싱 전면 추방 (`errors.As` 기반 타입 안전 번역)**:
   - 에러 메시지 문구를 한 단어만 수정해도 상위 호출자의 종료 코드(`ExitCode`)와 감사 사유(`Reason`)가 깨지는 현상을 원천 방지하기 위해, `internal/domain`에 `*domain.Error`(`Reason`, `Stage`, `ExitCode`, `Message`, `Cause` 내장)를 정의하고 전 계층이 `errors.As`로만 에러를 판별하게 한다.
2. **단일 도메인 상수 일원화 (`DefaultAudience = "authz-harness"`)**:
   - `internal/authn/token/issuer.go`와 `internal/cli/token.go`가 `"authz-service"`를 기본값으로 쓰고 `internal/authz/pep/gateway.go`가 `"authz-harness"`를 기대하던 불일치를 `domain.DefaultAudience = "authz-harness"` 및 `domain.DefaultIssuer = "authz-harness"` 단일 상수로 통일한다.
3. **결정론적 단일 시계(`domain.Clock`) 통합**:
   - `internal/authn/keys/manager.go`에 중복 선언된 `keys.Clock` 인터페이스를 제거하고 `domain.Clock`으로 통합하며, `pap`, `pdp`, `pip`, `pep`, `audit`, `orchestrator`에 남아 있는 `time.Now()` 직접 호출을 주입된 `domain.Clock` 호출로 일원화한다.

## 2. 파급 범위와 무영향 근거 증명 및 6계층 DAG 구조

```text
Layer 5:  [internal/cli/{pep,token,grant,pdp,keys}]
                │ (strings.Contains 제거 -> domain.ReasonFromError / ExitCodeFromError 호출)
                v

                v

          ├── constants.go : DefaultIssuer, DefaultAudience, ReasonMissingTraceContext, ReasonAuditIntegrityBroken 추가
          └── token.go     : Clock, RealClock, OffsetClock (전 계층 유일한 시계 계약)
```

- **변경 파급 범위**:
  - `internal/domain`: `error.go` 신설 및 `constants.go` 상수 보강.
  - `internal/authn/keys`, `internal/authn/token`, `internal/authn/exchange`, `internal/authz/pap`, `internal/authz/pep`, `internal/jail`, `internal/cli`: 에러 반환 시 `*domain.Error` 래핑 적용 및 `strings.Contains` 분기 제거, `domain.Clock` 주입 통일.
- **무영향 근거 증명**:
  - `*domain.Error.Error()` 메서드가 기존 에러 메시지와 사유 코드를 그대로 포함한 문자열을 반환하고 `Unwrap()`을 구현하므로, 기존 센티넬 에러 검사(`errors.Is(err, ErrTokenExpired)` 등)를 사용하는 모든 기존 단위 테스트는 단 한 줄도 깨지지 않고 100% 하위 호환된다.

## 3. 세부 설계 및 인터페이스 계약

### 3.1 구조화된 도메인 에러 모델 (`internal/domain/error.go`)

```go
package domain

import (
	"errors"
	"fmt"
)

// Error 는 사유 코드(Reason), 발생 관문(Stage), 종료 코드(ExitCode)를 내장한 표준 도메인 에러다.
type Error struct {
	Reason   Reason
	Stage    string
	ExitCode ExitCode
	Message  string
	Cause    error
}

// Error 는 표준 error 인터페이스를 구현한다.
func (e *Error) Error() string {
	if e.Cause != nil {
		return fmt.Sprintf("%s: %v (%s)", e.Message, e.Cause, e.Reason)
	}
	return fmt.Sprintf("%s (%s)", e.Message, e.Reason)
}

// Unwrap 은 errors.Is 및 errors.As 체인 탐색을 지원한다.
func (e *Error) Unwrap() error {
	return e.Cause
}

// NewError 는 원인 에러와 사유 코드로 표준 *domain.Error 를 생성하며, Reason 에 대응하는 표준 ExitCode 를 자동 매핑한다.
func NewError(reason Reason, stage, message string, cause error) *Error

// ReasonFromError 는 에러 체인에서 *domain.Error 를 찾아 Reason 을 반환한다 (문자열 파싱 일체 없음).
func ReasonFromError(err error, fallback Reason) Reason

// ExitCodeFromError 는 에러 체인에서 *domain.Error 를 찾아 표준 ExitCode 를 반환한다.
func ExitCodeFromError(err error, fallback ExitCode) ExitCode

// ExitCodeForReason 은 Reason 상수로부터 결정론적 ExitCode(0, 11~16)를 산출하는 순수 매핑 함수다.
func ExitCodeForReason(r Reason) ExitCode
```

### 3.2 `Reason` → `ExitCode` 결정론적 매핑 불변식

- `ReasonAuthorized` $\rightarrow$ `ExitSuccess (0)`
- `ReasonAuthn*`, `ReasonToken*`, `ReasonInvalidToken` (단, `ReasonTokenInsufficientScope` 제외) $\rightarrow$ `ExitTokenInvalid (11)`
- `ReasonNoActiveGrant`, `ReasonGrantRevoked`, `ReasonSubjectEpochRevoked`, `ReasonTokenInsufficientScope`, `ReasonDelegation*` $\rightarrow$ `ExitAuthzDenied (12)`
- `ReasonPath*`, `ReasonSymlinkEscape`, `ReasonInvalidPath` $\rightarrow$ `ExitPathViolation (13)`
- `ReasonInvalidArguments`, `ReasonMissingTraceContext` $\rightarrow$ `ExitBadInput (14)`
- `ReasonAuditLogFailed`, `ReasonAuditIntegrityBroken` $\rightarrow$ `ExitAuditFailure (15)`
- 그 외 알 수 없는 에러 $\rightarrow$ `ExitInternalError (16)`

## 4. 사전 점검 및 실패 위험 분석 (Pre-Mortem)

1. **위험: 기존 테스트에서 `errors.Is(err, token.ErrTokenExpired)` 형태로 검사하던 코드가 깨질 가능성**
   - *방어책*: `domain.NewError(reason, stage, msg, ErrTokenExpired)`와 같이 기존 센티넬 에러를 `Cause`에 담아 래핑하고 `(e *Error) Unwrap() error`를 구현함으로써, `errors.Is`와 `errors.As`가 모두 100% 작동하도록 보장한다.
2. **위험: `DefaultAudience`를 `"authz-harness"`로 변경했을 때 기존 `token_test.go`나 `exchange_test.go`에서 `"authz-service"`를 하드코딩해 기대하던 단언문이 실패할 가능성**
   - *방어책*: `token_test.go` 및 `exchange_test.go`에서 기본 Audience 기대값을 `domain.DefaultAudience`(`"authz-harness"`)와 대조하도록 함께 정렬한다.

## 5. 4층위 검증 범위 설계

1. **1층위 (정적 분석 및 안티패턴 스캔)**:
   - AST 정적 검사 테스트(`TestNoStringContainsOnErrors`)를 작성하여 `internal/` 전역에서 `strings.Contains(err.Error(), ...)` 호출이 0건임을 자동 검증.
   - `internal/authn/keys`에서 자체 `Clock` 인터페이스가 제거되고 `domain.Clock`만 사용됨을 확인.
2. **2층위 (단위 및 구조 검증)**:
   - `internal/domain/error_test.go`: 모든 `Reason` 상수에 대한 `ExitCodeForReason` 매핑 테이블 테스트, 다중 래핑된 `*domain.Error`에서 `ReasonFromError`·`ExitCodeFromError`·`errors.Is` 추출 테스트, 에러 메시지 문구를 임의 변경해도 동일 `Reason`/`ExitCode`가 반환됨을 증명하는 테스트.
3. **3층위 (상태 및 정합성 검증)**:
   - 주입된 고정 시계(`OffsetClock`) 하에서 `pap.CreateGrant`, `pap.RevokeGrant`, `pdp.Decide`, `pep.Execute`가 생성하는 타임스탬프가 시스템 시계가 아닌 주입 시계와 100% 일치함을 검증.
4. **4층위 (CLI 통합 검증)**:
   - `--aud` 플래그 생략 상태로 `authz-harness token issue` 실행 후 발급된 토큰으로 `authz-harness pep read` 실행 시 Audience 불일치 없이 즉시 통과함을 확인.

5. 상위 대시보드([README.md](../README.md))의 `010` 단계 상태를 `Done`으로 갱신.
