다음 성질을 카탈로그의 G13 6대 시나리오로 통합 증명한다.
- 서명 체크포인트가 꼬리 절단·전체 재작성·파일/키 부재를 잡는다.
- 인자·결과 지문은 남고 원문은 남지 않는다.
- 관측성 포트에 장애가 나도 인가·감사는 영향을 받지 않는다.
- v1·v2가 섞인 체인도 VALID다.

## 3. 신규 시나리오 명세 (`G13`)

공통 사항:
- 스택은 `setupHarnessStack(env)`으로 조립한다([`helpers.go`](../../../../internal/harness/catalog/helpers.go) 71행).
- 체크포인트 키·파일 경로는 `filepath.Dir(env.PrivKeyPath)`(Zone A)와 `filepath.Dir(env.PubJWKSPath)`(Zone B) 아래 040의 기본 이름이다.
- E2E-61·62·63은 [E2E-30](../../../../internal/harness/catalog/g7_observability_audit.go)의 **사후 검증 패턴**을 따른다. 즉 정상 PEP 쓰기 → 변조 → 검증기 직접 호출 → `domain.ExitCodeFromError(verifyErr, domain.ExitSuccess)` 반환이다.

| ID | 시나리오명 | 실행 절차 | 기대 Exit | 기대 감사 (`ExpectedAssertion.Audit`) | 핵심 증거 |
|:---:|---|---|:---:|---|---|
| `E2E-61` | 꼬리 절단 적발 | `file:write` 허용 → `checkpoint.Create` → `audit.jsonl` 마지막 줄 삭제 → `checkpoint.Verify` | `15` | `pep.allow`/`allow`/`AUTHORIZED` (남은 줄의 Stage 4 사전 감사), `RequireValidChain: true` (남은 체인 자체는 유효) | 체인이 VALID인데도 `AUDIT_TRUNCATION_DETECTED` |
| `E2E-62` | 전체 재작성 적발 | `file:write` 허용 → `Create` → 첫 레코드 `resource` 변조 후 모든 줄 해시 재계산(v2 공식) → `Verify` | `15` | `pep.allow`/`allow`/`AUTHORIZED`, `RequireValidChain: true` (재계산했으므로 체인은 유효) | 체인 VALID + `AUDIT_CHECKPOINT_MISMATCH` |
| `E2E-63` | 체크포인트·키 부재 Fail-Closed | `file:write` 허용 → `Create` → 공개키 파일 삭제 → `Verify` | `15` | `pep.allow`/`allow`/`AUTHORIZED`, `RequireValidChain: true` | 검증 재료가 없으면 통과가 아니라 `AUDIT_CHECKPOINT_MISMATCH` (교정 전의 로테이션 시나리오를 대체) |
| `E2E-64` | 인자·결과 지문, 원문 비노출 | `"G13_SECRET_PAYLOAD"` `file:write` → 같은 파일 `file:read` | `0` | `pep.allow`/`allow`/`AUTHORIZED`, `RequireValidChain: true`, `NoRawTokenLeak: true` | `audit.jsonl`에 평문 0건. 쓰기 이벤트 `arg_hash`와 읽기 완료 이벤트 `result_hash`가 `domain.DataDigest(payload)`와 일치. 불일치면 `Execute`가 `ExitInternalError` 반환 |
| `E2E-65` | 관측성 포트 장애 격리 | 모든 메서드에서 panic하는 Observer로 `app.BuildStack(AppConfig{…, Observer: panicObserver})`를 직접 조립한 뒤 허용된 `file:read` | `0` | `pep.allow`/`allow`/`AUTHORIZED`, `RequireValidChain: true` | 텔레메트리 장애가 판정·Fail-Closed 감사를 바꾸지 않음 |
| `E2E-66` | v1·v2 혼합 체인 하위 호환 | Setup에서 v1 픽스처 3줄(`schema_version` 없음, v1 공식으로 해시한 `prev_hash`/`curr_hash`)을 감사 파일에 씀 → PEP `file:write` 허용(writer가 마지막 `curr_hash`를 승계해 v2로 이어 씀) | `0` | `pep.allow`/`allow`/`AUTHORIZED`, `RequireValidChain: true` | v1 3줄 + v2 레코드가 한 체인으로 VALID. 마지막 레코드의 `schema_version == 2` |

- E2E-61·62·63의 「기대 감사」는 변조가 끝난 뒤의 파일을 평가기가 읽은 결과다. 평가기는 `ExpectedAction`이 맞는 이벤트를 골라 판정·사유를 대조한다([`assertion.go`](../../../../internal/harness/assertion.go) 159~220행). 남은(또는 재계산된) 레코드에 `pep.allow`/`AUTHORIZED`가 있으므로 E2E-30과 같은 기대값을 쓴다. `RequireValidChain: true`는 「체인은 멀쩡한데 체크포인트가 잡았다」는 대비를 판정에 넣기 위한 것이다. 기대값을 실행 결과에 맞춰 바꾸지 않는다(동어반복 금지, [AGENTS.md](../../../../AGENTS.md) §2).
- E2E-62의 재계산은 감사 패키지의 공개 함수 `audit.ComputeEventHash`를 쓴다. 공격자도 공식을 알고 있다는 전제다.
