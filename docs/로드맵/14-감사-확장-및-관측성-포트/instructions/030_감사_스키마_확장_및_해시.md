## 1. 목적 및 배경

감사 로그에 민감한 도구 입력 데이터나 파일 내용 원문을 기록하면 비밀 유출 위험이 생기고, 아예 기록하지 않으면 "어떤 입력과 결과였는지" 사후 대조할 수 없다.
본 단계에서는 감사 이벤트에 `SchemaVersion`(`1` 또는 `2`), 입력 지문(`ArgHash`), 결과 지문(`ResultHash`)을 추가하되, **구버전(`SchemaVersion` 미기재 또는 `1`) 레코드의 `ComputeEventHash` 공식을 그대로 보존**하여 기존 감사 파일 픽스처가 새 검증기에서도 100% `VALID`로 통과하도록 하위 호환성을 보장한다 ([006번 보고서](../../../보고서/006-차기로드맵_10_16_타당성_및_단계분할_정밀검토_보고서.md) §3.5).

## 2. 파급 범위와 무영향 근거

- **변경**:
  - `internal/audit/audit.go`: `Event`에 `SchemaVersion int` (`json:"schema_version,omitempty"`), `ArgHash string` (`json:"arg_hash,omitempty"`), `ResultHash string` (`json:"result_hash,omitempty"`) 추가. `ComputeEventHash`에서 `ev.SchemaVersion <= 1`이면 기존 9필드 공식을 사용하고, `ev.SchemaVersion == 2`일 때만 확장 필드 공식을 사용하도록 분기
  - `internal/authz/pep/gateway.go`: 요청 데이터(`req.Data`)와 읽기 결과(`res.Data`)의 SHA-256(또는 키 기반 HMAC) 지문을 계산해 `ArgHash`, `ResultHash`로 감사에 전달(원문 기록 금지)
  - `internal/audit/schema_compat_test.go` [신규]: v1 픽스처·v2 레코드 혼합 체인 검증 및 원문 비노출 단위 테스트
- **무영향**:
  - 기존 테스트와 시나리오가 생성한 v1 감사 레코드 해시 검증은 단 1바이트도 깨지지 않는다.

---

## 3. 세부 명세

1. **버전별 해시 공식 분리 (`ComputeEventHash`)**:
   - `ev.SchemaVersion <= 1`: 기존 `fmt.Sprintf("%s|%s|%s|%s|%s|%s|%s|%s|%t", prevHash, ts, traceID, actor, action, resource, decision, reason, success)` 공식 100% 유지.
   - `ev.SchemaVersion == 2`: 기존 9필드 뒤에 `|v2|%s|%s`(`ev.ArgHash`, `ev.ResultHash`)를 결합하여 `arg_hash`·`result_hash` 위변조까지 해시 체인으로 보호한다.
2. **원문 비노출 원칙**:
   - `req.Data`나 `res.Data` 원문 문자열은 `audit.Event`의 어느 필드에도 넣지 않으며, 오직 `sha256` 16진수 지문만 기록한다.

## 4. 인수 테스트 시나리오

| ID | 입력 | 기대 결과 |
|:---:|---|---|
| **TC-030-01** | 기존 v1 형식 `audit.jsonl` 픽스처에 `VerifyHashChain` 실행 | `VALID` (`nil` 반환) |
| **TC-030-02** | v1 레코드 3개 뒤에 v2 레코드 2개가 이어진 혼합 파일에 `VerifyHashChain` 실행 | `VALID` 통과 |
