## 1. 목적 및 배경

이 단계는 10번 로드맵의 본체다. [`spawner.go`](../../../../internal/orchestrator/spawner.go)는 지금 다음과 같이 동작한다.
- `exec.CommandContext`의 기본 종료를 써서 직계 자식 하나만 죽인다(94·97행). 손자 프로세스는 남는다.
- 출력은 상한 없는 `bytes.Buffer`에 쌓인다(104행).
- 타임아웃이 나면 표준에 없는 종료 코드 `1`을 낸다(120~122행).
- 자식이 낸 임의의 종료 코드(예: Go panic의 `2`)를 그대로 내보낸다.

이전 설계는 이 종료 판정 블록을 020(타임아웃·신호), 030(출력 상한), 040(감사)에서 세 번 나눠 고쳤다. 그 결과 분기가 겹치는 문제(017 C-02)가 생겼다. 이번에는 **"자식 프로세스가 어떻게 끝났는가"라는 상태 기계 하나를 이 단계에서 한 번에 완결**한다.

핵심 원칙은 세 가지다.
1. **부모가 관찰한 사실과 자식이 보고한 판정을 분리한다.** 부모가 관찰한 사실은 `Termination` 하나로 표현한다. 표준 종료 코드는 순수 함수 한 곳에서만 도출한다.
2. **`17`은 부모가 실제로 강제한 한계에만 쓴다.** 해당하는 것은 시간 초과와 출력 초과뿐이다. 원인을 모르는 종료(외부 신호, 부모 취소, 표준 밖 종료 코드)는 `16`이다.
3. **설정의 원천은 하나다.** `SpawnConfig.Timeout`을 없애고 `Limits`로 통일한다.

## 3. 세부 명세

### 3.1 `Limits` (`internal/orchestrator/limits.go`)
1. 상수: `DefaultSpawnTimeout = 10 * time.Second`(기존 값과 같음), `DefaultWaitDelay = 500 * time.Millisecond`, `DefaultMaxOutputBytes int64 = 1 << 20`
2. `type Limits struct { Timeout, WaitDelay time.Duration; MaxOutputBytes int64 }`. `stdout`과 `stderr`에 **각각** 상한을 적용한다.
3. `func DefaultLimits() Limits`
4. `func (l Limits) Normalize() (Limits, error)`: 음수 필드가 하나라도 있으면 `domain.NewError(domain.ReasonInvalidArguments, "orchestrator_limits", ..., nil)`(→ `14`). 영값 필드는 기본값으로 채운 사본을 반환한다.
5. `NewSubprocessSpawner`와 `NewMultiHopSpawner`는 생성 시 `Normalize()`를 한 번 호출한다. 에러가 나면 생성자가 에러를 반환한다. `NewMultiHopSpawner`의 시그니처는 `(*MultiHopSpawner, error)`로 바뀐다. 호출부 2곳(`g5_delegation_pdp.go`)은 에러를 `ExitInternalError`로 처리한다.
6. `Limits`는 `domain`이 아니라 `orchestrator`에 둔다. 한계 값은 인가 어휘가 아니라 스포너 설정이고, 사용처는 orchestrator와 그 호출부뿐이다.

### 3.2 `Termination`과 표준 종료 코드 도출 (`internal/orchestrator/termination.go`)
1. ```go
   type Termination string
   const (
       TermExited         Termination = "exited"          // 프로세스가 스스로 종료 코드를 내고 끝남
       TermTimedOut       Termination = "timed_out"       // 부모가 Timeout으로 그룹 종료
       TermOutputExceeded Termination = "output_exceeded" // 부모가 출력 상한으로 그룹 종료
       TermCanceled       Termination = "canceled"        // 부모 ctx 취소(Canceled)로 그룹 종료
       TermSignaled       Termination = "signaled"        // 부모가 강제하지 않은 신호로 종료
   )
   ```
2. 관찰 → `Termination` 결정 규칙. 아래 순서로 판정하며, 출력 초과가 그룹 SIGKILL을 일으키므로 출력 초과를 가장 먼저 본다.
   1. `stdout` 또는 `stderr`의 상한 초과 → `TermOutputExceeded`
   2. `execCtx.Err()`가 `DeadlineExceeded`(부모 ctx의 deadline 포함) → `TermTimedOut`
   3. 부모 `ctx.Err()`가 `Canceled` → `TermCanceled`
   4. `WaitStatus.Signaled()` → `TermSignaled`(신호 이름 기록)
   5. 그 밖 → `TermExited`(원시 종료 코드 기록)
3. 순수 함수 `func classifyExit(term Termination, rawExit int, childReason string) (domain.ExitCode, domain.Reason)`:

   | `term` | 표준 종료 코드 | Reason |
   |---|:---:|---|
   | `TermOutputExceeded` | `17` | `RESOURCE_OUTPUT_LIMIT` |
   | `TermTimedOut` | `17` | `RESOURCE_TIMEOUT` |
   | `TermCanceled`, `TermSignaled` | `16` | `SUBPROCESS_ABNORMAL_EXIT` |
   | `TermExited`, `rawExit ∈ {0, 11..16}` | `rawExit` | `childReason` (비어 있으면 `""`) |
   | `TermExited`, 그 밖의 `rawExit`(예: `1`, `2`) | `16` | `SUBPROCESS_ABNORMAL_EXIT` |

   이 표가 종료 코드 공간 `{0, 11..17}`을 닫는다. 이 함수 외에는 `SpawnResult.ExitCode`를 쓰지 않는다.

### 3.3 `SpawnResult` (`internal/orchestrator/spawner.go`)
1. 기존 필드(`TraceID`, `ExitCode`, `Response`, `StdoutRaw`, `StderrRaw`, `Duration`, `TimedOut`)를 유지한다. 의미는 다음과 같다.
   - `ExitCode`: `classifyExit`의 표준 코드
   - `TimedOut`: `Termination == TermTimedOut`인지 여부(호환용)
2. 추가 필드: `Termination Termination`, `Reason domain.Reason`, `RawExitCode int`(신호 종료면 `-1`), `Signal string`
3. 자식 JSON 응답(`Response`)은 `Termination == TermExited`일 때만 파싱한다. 강제 종료된 자식의 불완전한 출력은 판정에 섞이지 않는다. 이것은 별도 가드가 아니라 구조로 보장된다. `childReason`은 파싱된 `Response.Reason`이다.

### 3.4 프로세스 그룹 (`internal/orchestrator/procgroup.go`)
1. `func configureProcessGroup(cmd *exec.Cmd, waitDelay time.Duration)`:
   - `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}`
   - `cmd.Cancel = func() error { return killProcessGroup(cmd) }`
   - `cmd.WaitDelay = waitDelay`
2. `killProcessGroup`: `cmd.Process`가 nil이면 `nil`을 반환한다. `syscall.Kill(-pid, SIGKILL)`을 보내고, `ESRCH`이면 `nil`을 반환한다.
3. `cmd.Cancel`은 `os/exec`의 감시 고루틴이 호출한다. 그래서 출력 상한 쪽은 `cmd.Process`를 직접 건드리지 않고 `cancel()`만 부른다(데이터 레이스 차단).

### 3.5 출력 상한 버퍼 (`internal/orchestrator/limited_buffer.go`)
1. `type limitedBuffer struct { mu sync.Mutex; buf bytes.Buffer; max int64; exceeded bool; once sync.Once; onExceed func() }`
2. `Write(p)`: 누적량이 `max`를 넘으면 남은 여유분만 기록하고(보관량 `<= max` 보장), `exceeded = true`로 표시한 뒤 `once.Do(onExceed)`를 호출하고 `errOutputLimitExceeded`를 반환한다.
3. `Exceeded()`, `String()`, `Bytes()`, `Len()`
4. 스포너는 `stdout`과 `stderr`에 각각 `newLimitedBuffer(limits.MaxOutputBytes, cancel)`을 연결한다. 여기서 `cancel`은 `execCtx`의 cancel 함수다.

### 3.6 사후 감사 (`spawner.go`, 함수 말미 1곳)
1. 이벤트를 하나 조립해 `Audit.Log`를 **한 번만** 호출한다.
2. `ExitCode == 17`이면 다음과 같이 기록한다.
   `Action: AuditActionLimitExceeded`, `Step: "ORCHESTRATE_LIMIT_EXCEEDED"`, `Decision: "deny"`, `Reason: string(Reason)`, `Success: false`, `Metadata{exit_code, duration_ms, termination}`
3. 그 밖이면 기존 `ORCHESTRATE_COLLECT` 이벤트를 그대로 쓰고 `Metadata`에 `termination`, `raw_exit_code`, `signal`(있을 때)만 추가한다. `reason` 키는 넣지 않는다(§2 무영향 참조).
4. 감사 실패 시 지금처럼 `ReasonAuditLogFailed`(→ `15`) 에러를 반환한다(fail-closed).

### 3.7 시험 지원 (`internal/harness/process.go`, `spawner_test.go`)
1. `harness.WaitForProcessGone(pid, timeout) bool`: 10ms 주기로 `syscall.Kill(pid, 0)`을 확인한다. `ESRCH`이면 `true`, 시간이 다 되면 `false`. 고정 sleep으로 추측하지 않는다. `harness` 패키지는 `orchestrator`를 import하지 않으므로, `orchestrator`의 테스트가 이 함수를 import해도 순환이 생기지 않는다.
2. `TestHelperProcess`에 다음 모드를 **직접** 구현한다(빌드 태그와 프로덕션 코드 위임 없음).
   - `hang`: `time.Sleep(1 * time.Hour)` (`select {}`는 Go 런타임 데드락 패닉을 내므로 쓰지 않는다)
   - `flood`: `os.Stdout`에 8 KiB 청크를 쓰기 에러가 날 때까지 반복
   - `spawn_child_hang`: `exec.Command("sleep", "60").Start()`(손자에 `Setpgid`를 쓰지 않아 같은 그룹에 속함) → `CHILD_PID=<pid>\n` 출력 → `time.Sleep(1 * time.Hour)`
   - `exit_2`: `os.Exit(2)` (표준 밖 종료 코드)
   - `self_kill`: `syscall.Kill(os.Getpid(), syscall.SIGKILL)` (부모가 강제하지 않은 신호 종료)
3. `helperSpawnerForTest`의 `Timeout: timeout`을 `Limits: Limits{Timeout: timeout}`으로 바꾸고, 출력 상한 시험용 변형을 하나 추가한다.
