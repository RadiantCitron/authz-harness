## 3. 신규 시나리오 명세 (`G9`: 서브프로세스 자원·수명 통제)

| ID | 시나리오명 | 입력 조건 | 기대 Exit | 기대 감사 (`ExpectedAction` / `ExpectedReason`) | 핵심 검증 증거 |
|:---:|---|---|:---:|---|---|
| `E2E-40` | 멈춘 서브프로세스(Hang) 타임아웃 강제 종료 | `-test-fault hang` 워커 + `Timeout: 100ms` | `17` | `agent.limit_exceeded` / `RESOURCE_TIMEOUT` | 약 100ms 내 종료, `agent.limit_exceeded` 기록, workspace 0바이트 무변화 |
| `E2E-41` | 손자 프로세스 생성 후 멈춘 워커의 프로세스 그룹 일괄 소멸 | `-test-fault spawn_child_hang` 워커 + `Timeout: 300ms` (`C-07`) | `17` | `agent.limit_exceeded` / `RESOURCE_TIMEOUT` | `StdoutRaw`에서 `CHILD_PID=<pid>` 추출 후 `WaitForProcessGone(pid, 1s) == true` 확인(잔존 프로세스 0), workspace 무변화 |
| `E2E-42` | 출력 폭주(Stdout Flood) 워커 바이트 상한 즉시 차단 | `-test-fault flood` 워커 + `MaxOutputBytes: 16 * 1024` (16 KiB) | `17` | `agent.limit_exceeded` / `RESOURCE_OUTPUT_LIMIT` | 상한 도달 즉시 강제 종료, 부모 버퍼 보관량 `<= 16 KiB`, workspace 무변화 |
| `E2E-43` | MCP `tools/call` 경로의 서브프로세스 타임아웃·토큰 비노출 | MCP `SubprocessExecutor`가 `-test-fault hang` 워커(`Timeout: 100ms`) 호출 | `17` | `agent.limit_exceeded` / `RESOURCE_TIMEOUT` | JSON-RPC `isError: true` 응답에 `[RESOURCE_TIMEOUT]` 및 `exit code 17` 포함, 원시 JWT 토큰 노출 0건 |
| `E2E-44` | 기본 `Limits`(`DefaultLimits()`) 하에서 정상 위임 워커 비회귀 실행 | 유효한 읽기 토큰 + `DefaultLimits()` 적용 스포너로 `file:read` 수행 | `0` | `pep.allow` / `AUTHORIZED` | 정상 파일 읽기 성공, 기존 워커 동작 비회귀 증명 |

### 3.1 실행 모드 호환 규칙 (`subprocess` 및 `inproc`)
- `E2E-40`~`E2E-44`는 OS 서브프로세스 스포너(`SubprocessSpawner`)의 자원·수명 통제를 검증하는 시나리오이므로, `env.BinaryPath`가 비어 있는 `inproc` 모드로 호출되었을 때도 패키지 내 공유 `harness.NewCachedBinaryProvider()`를 통해 테스트 바이너리 경로를 획득하여 실제 서브프로세스를 스폰하도록 구현한다.

### 3.2 하네스 판정기(`runner.go:216`) 가짜 통과(False-Pass) 원천 차단 규약 ([017번 보고서](../../../보고서/017-10번로드맵_반복결함_원인분석_및_검토방법론_메타위험_진단보고서.md) `C-06` — 핵심 주의사항)
- [`internal/harness/runner.go` 216행](../../../../internal/harness/runner.go)은 `overallPassed := assertionRes.Passed && (execErr == nil || actualExitCode != domain.ExitSuccess)`로 구현되어 있다.
- 따라서 기대 종료 코드가 `17`(`ExitResourceLimit != 0`)인 `E2E-40`~`E2E-43`의 `Execute(ctx, env)` 메서드 안에서 부가 검증(손자 PID 소멸, 출력 버퍼 크기, MCP 응답 포맷 등)이 실패했을 때 `return domain.ExitCode(res.ExitCode), fmt.Errorf(...)`와 같이 `17`을 그대로 반환하면, **`execErr`가 무시되어 시나리오가 가짜 `PASS`로 판정되는 치명적 오라클 결함**이 발생한다!
- 이를 원천 차단하기 위해 `Execute(ctx, env)` 내 부가 불변식 검증이 실패하면 **반드시 `domain.ExitInternalError(16), fmt.Errorf(...)`를 반환**하여 `actualExitCode(16) != Expected.ExitCode(17)`로 Quad-Assertion을 즉시 `FAIL`시켜야 한다:
  1. **`E2E-41`**: `res.StdoutRaw`에서 `CHILD_PID=<pid>` 파싱에 실패하거나 `!orchestrator.WaitForProcessGone(childPID, 1*time.Second)`이면 즉시 `return domain.ExitInternalError, fmt.Errorf("...")` 반환.
  2. **`E2E-42`**: `!res.OutputExceeded`이거나 `len(res.StdoutRaw) > 16*1024`이면 즉시 `return domain.ExitInternalError, fmt.Errorf("...")` 반환.
  3. **`E2E-43`**: MCP JSON-RPC 응답에서 `isError != true`이거나 텍스트에 `"[RESOURCE_TIMEOUT]"` 또는 `"exit code 17"`이 없거나 `mcp.ContainsRawToken(text)`가 `true`이면 즉시 `return domain.ExitInternalError, fmt.Errorf("...")` 반환.
