## 1. 목적 및 배경

`010`~`040` 단계에서 구축한 서브프로세스 자원·수명 통제 메커니즘을 하네스 공식 카탈로그의 **G9 그룹(`E2E-40`~`E2E-44`, 5대 시나리오)**으로 편입하여 Quad-Assertion(종료 코드 `17`/`0`, 파일 무변화, 감사 `agent.limit_exceeded` 및 사유 코드, 감사 해시 체인 무결성)으로 자동 검증한다.

---

## 2. 파급 범위와 무영향 근거

- **변경**:
  - `internal/harness/catalog/g9_resource_limits.go` [신규]: `E2E-40`~`E2E-44` 5개 시나리오 정의 및 실행 로직 구현
  - **Open-Closed 원칙 준수 ([016번 보고서](../../../보고서/016-다중로드맵_일괄설계_안티패턴_진단_및_10번로드맵_단독집중_구조정제_보고서.md) `R10-04`)**: 이미 완료된 09번 파일(`g8_mcp_adapter.go`)은 수정하지 않고, `g9_resource_limits.go` 내부에서 `-test-fault hang` 및 `Timeout: 100ms`가 설정된 `SubprocessSpawner`를 `mcp.NewSubprocessExecutor`에 직접 연결하여 `E2E-43`을 독립 검증
  - `internal/harness/catalog/catalog.go`: `AllScenarios()`에 `g9Scenarios()` 추가 (총 시나리오 수 39개 → 44개)
  - `internal/harness/catalog/catalog_test.go` 및 `internal/cli/run_test.go`: 전체 시나리오 개수(`39` → `44`, 예: `TestRunCLI_AT_CLI_04_JSONOutput`의 `report.Total == 44`) 갱신 및 G9 실행 검증 추가
- **무영향**:
  - 기존 `E2E-01`~`E2E-39` 시나리오의 입력, 판정 로직, 기대 종료 코드는 일절 수정하지 않는다.

## 3. 신규 시나리오 명세 (`G9`: 서브프로세스 자원·수명 통제)

| ID | 시나리오명 | 입력 조건 | 기대 Exit | 기대 감사 (`ExpectedAction` / `ExpectedReason`) | 핵심 검증 증거 |
|:---:|---|---|:---:|---|---|
| `E2E-40` | 멈춘 서브프로세스(Hang) 타임아웃 강제 종료 | `-test-fault hang` 워커 + `Timeout: 100ms` | `17` | `agent.limit_exceeded` / `RESOURCE_TIMEOUT` | 약 100ms 내 종료, `agent.limit_exceeded` 기록, workspace 0바이트 무변화 |
| `E2E-41` | 손자 프로세스 생성 후 멈춘 워커의 프로세스 그룹 일괄 소멸 | `-test-fault spawn_child_hang` 워커 + `Timeout: 150ms` | `17` | `agent.limit_exceeded` / `RESOURCE_TIMEOUT` | `StdoutRaw`에서 `CHILD_PID=<pid>` 추출 후 `WaitForProcessGone(pid, 1s) == true` 확인(잔존 프로세스 0), workspace 무변화 |
| `E2E-42` | 출력 폭주(Stdout Flood) 워커 바이트 상한 즉시 차단 | `-test-fault flood` 워커 + `MaxOutputBytes: 16 * 1024` (16 KiB) | `17` | `agent.limit_exceeded` / `RESOURCE_OUTPUT_LIMIT` | 상한 도달 즉시 강제 종료, 부모 버퍼 보관량 `<= 16 KiB`, workspace 무변화 |
| `E2E-43` | MCP `tools/call` 경로의 서브프로세스 타임아웃·토큰 비노출 | MCP `SubprocessExecutor`가 `-test-fault hang` 워커(`Timeout: 100ms`) 호출 | `17` | `agent.limit_exceeded` / `RESOURCE_TIMEOUT` | JSON-RPC `isError: true` 응답에 `[RESOURCE_TIMEOUT]` 및 `exit code 17` 포함, 원시 JWT 토큰 노출 0건 |
| `E2E-44` | 기본 `Limits`(`DefaultLimits()`) 하에서 정상 위임 워커 비회귀 실행 | 유효한 읽기 토큰 + `DefaultLimits()` 적용 스포너로 `file:read` 수행 | `0` | `pep.allow` / `AUTHORIZED` | 정상 파일 읽기 성공, 기존 워커 동작 비회귀 증명 |

### 실행 모드 호환 규칙 (`subprocess` 및 `inproc`)
- `E2E-40`~`E2E-44`는 OS 서브프로세스 스포너(`SubprocessSpawner`)의 자원·수명 통제를 검증하는 시나리오이므로, `env.BinaryPath`가 비어 있는 `inproc` 모드로 호출되었을 때도 패키지 내 공유 `harness.NewCachedBinaryProvider()`를 통해 테스트 바이너리 경로를 획득하여 실제 서브프로세스를 스폰하도록 구현한다.
