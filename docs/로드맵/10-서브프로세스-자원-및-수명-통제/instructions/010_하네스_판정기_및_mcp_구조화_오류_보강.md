## 1. 목적 및 배경

10번 로드맵은 증거를 모으는 경로(판정기, MCP 종료 코드)를 넓힌다. 그런데 그 경로에 두 가지 기존 결함이 있다. 이 결함을 그대로 두고 `17`을 추가하면 결함이 새 기능 안으로 옮겨진다. 그래서 자원 통제 코드를 쓰기 **전에** 이 두 결함을 먼저 고친다. 이 단계는 동작을 바꾸지 않는 보강이며, 기존 39대 시나리오는 그대로 PASS해야 한다.

1. **판정기 가짜 통과(E-1)**: [`runner.go`](../../../../internal/harness/runner.go) 216행 `overallPassed := assertionRes.Passed && (execErr == nil || actualExitCode != domain.ExitSuccess)` 때문에, 종료 코드가 0이 아닌 시나리오에서는 `Execute`가 반환한 에러가 무시된다. 시나리오가 부가 불변식(손자 프로세스 소멸, 버퍼 크기 등) 위반을 알릴 방법이 없다.
2. **MCP 종료 코드 문자열 복원(E-2)**: [`g8_mcp_adapter.go`](../../../../internal/harness/catalog/g8_mcp_adapter.go)의 `executeMCPCall`은 응답 텍스트에서 `strings.Contains(text, "exit code 11")`~`"15"`로 종료 코드를 되살리고, 일치하는 것이 없으면 `12`로 떨어진다. 구조화 타입 [`mcp.ErrorDetail`](../../../../internal/mcp/errors.go)은 정의만 있고 쓰이지 않는다.

  - `internal/mcp/errors.go`: `MapSubprocessError`가 `StructuredContent`에 `ErrorDetail{ExitCode, Reason, Message}`를 채움
  - `internal/mcp/errors_test.go`: 구조화 필드 검증 추가

  - `InvariantViolation`은 새 타입이다. 기존 시나리오는 이 타입을 반환하지 않으므로 기존 판정은 그대로다.

  - 종료 코드·Reason 상수, PDP·PEP, 감사 스키마는 변경하지 않는다.

## 3. 세부 명세

### 3.1 불변식 위반 에러 (`internal/harness/invariant.go`)
1. `type InvariantViolation struct { Detail string }`와 `func (e *InvariantViolation) Error() string`.
2. `func Invariantf(format string, args ...any) error`는 `&InvariantViolation{Detail: fmt.Sprintf(...)}`를 반환한다.
3. 시나리오는 "종료 코드·감사로는 드러나지 않는 부가 증거"가 실패했을 때 이 에러를 반환한다. 이때 종료 코드는 실제 관찰 값을 그대로 반환한다. 판정을 위해 코드를 바꿔치기(예: `16` 반환)하지 않는다.

### 3.2 판정기 (`internal/harness/runner.go`)
1. 216행을 다음 의미로 바꾼다.
   ```go
   var iv *InvariantViolation
   invariantBroken := errors.As(execErr, &iv)
   overallPassed := assertionRes.Passed && !invariantBroken &&
       (execErr == nil || actualExitCode != domain.ExitSuccess)
   ```
2. `invariantBroken`이면 `assertionRes.FailureReasons`에 `"invariant violation: <Detail>"`을 추가해 보고서에 원인이 남게 한다.
3. 기존 조건(`execErr == nil || actualExitCode != ExitSuccess`)은 유지한다. 감사 실패처럼 0이 아닌 코드와 에러를 함께 반환하는 기존 시나리오([`helpers.go`](../../../../internal/harness/catalog/helpers.go) `executeHarnessAction`)가 있기 때문이다.

### 3.3 MCP 구조화 오류 (`internal/mcp/server.go`, `errors.go`)
1. `ToolExecutionResult`에 `StructuredContent *ErrorDetail` 필드를 추가한다(JSON 키 `structuredContent`).
2. `MapSubprocessError`는 지금처럼 `Content` 텍스트를 만들고, 같은 값으로 `StructuredContent = &ErrorDetail{ExitCode: exitCode, Reason: reason, Message: sanitizedMsg}`를 채운다. `Message`는 텍스트와 같은 `sanitizeMessage`를 거친 값이어야 한다(원시 JWT 비노출).
3. 성공 응답(`IsError == false`)은 `StructuredContent`를 비운다.

### 3.4 하네스의 구조적 읽기 (`internal/harness/catalog/g8_mcp_adapter.go`)
1. `executeMCPCall`에서 `isError == true`일 때, `result.structuredContent.exit_code`(JSON 숫자)를 읽어 `domain.ExitCode`로 반환한다.
2. `structuredContent`가 없거나 `exit_code`가 숫자가 아니면 `domain.ExitInternalError`와 에러를 반환한다(fail-closed). 기존의 "모르면 `12`" 폴백은 없앤다.
3. `strings.Contains(text, "exit code N")` 블록을 삭제한다. 이후 새 종료 코드(`17`, `18`)가 생겨도 이 함수는 고치지 않는다.
