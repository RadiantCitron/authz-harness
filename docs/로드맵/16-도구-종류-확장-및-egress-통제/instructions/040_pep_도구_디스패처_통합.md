## 1. 목적 및 배경

020의 netguard와 030의 execguard를 **기존** [`Gateway.Execute`](../../../../internal/authz/pep/gateway.go) 파이프라인 안에 넣는다. 새 입구·새 단계·새 파일·새 인터페이스는 만들지 않는다. 15번이 고정한 단계 순서는 그대로다.

```
Gate 0 → Gate 1 → Gate 2(PDP) → StageReplay → Gate 2c → StageApproval → Stage 3b Budget → Stage 4 → Stage 5
```

바뀌는 곳은 네 군데다: Gate 0(액션 해석·`net:fetch` 정규화), Gate 2c(액션별 경계 검사), Stage 3b(예산 사전 차감 조건), Stage 5(액션별 실행). 지금 `runPipeline`은 `runStage` 클로저를 인라인으로 이어 쓴 함수다(218~432행). 원안이 말한 「45줄 Template Method」「`stage3PreCommitLedgers` rollback」은 없으므로(025번 T-10), 그 구조를 만들지 않고 현재 구조에 `switch`만 넣는다.

PEP는 토큰 스코프를 따로 검사하지 않는다(025번 T-4). 정규화된 자원을 PDP에 넘기면 PDP가 지금처럼 Grant와 3단 스코프를 판정한다.

## 2. 파급 범위와 무영향 근거

  - [`internal/app/builder.go`](../../../../internal/app/builder.go): `AppConfig.NetAllowList []string`. `BuildStack`은 항상 `netguard.NewGuard(cfg.NetAllowList, 0, 0)`(오류면 조립 실패)와 `execguard.NewRunner(cfg.WorkspaceDir, 0, 0)`를 PEP에 주입한다.
  - [`internal/cli/subagent.go`](../../../../internal/cli/subagent.go): `-net-allow` 플래그(쉼표 구분 `host:port`) → `AppConfig.NetAllowList`. 잘못된 항목은 `ExitBadInput`(14).

  - `internal/authz/pep/tool_dispatch_test.go` [신규].
- **무영향**: PDP·PIP·토큰·감사 스키마, `file:*` 요청의 단계·사유·종료 코드·감사, 단계 이름(`StageGate2cJail` = `"gate2c_jail"`은 감사·관측 호환을 위해 이름을 유지하고 의미만 「경계 검사」로 넓힌다), pep CLI(`read`·`write` 서브커맨드만, 새 도구 서브커맨드는 범위 밖 — 025번 T-14).

## 3. 세부 명세

1. **Gate 0 (입력 해석)**
   - `file:read`·`file:write`: 지금과 같다.
   - `net:fetch`: `len(req.Data) > 0`이면 `INVALID_ARGUMENTS`(14). `netguard.ParseTarget(state.resource)`이 실패하면 `EGRESS_DENIED`(12)이고, 이때 `state.resource = "<invalid-url>"`, `state.argHash = domain.DataDigest([]byte(원문))`으로 바꿔 **원문 URL이 감사에 남지 않게** 한다. 성공하면 `state.resource = t.HostPort`, `state.fetchTarget = t`, `state.argHash = domain.DataDigest([]byte(t.URL))`(D-10).
   - `exec:run`: 자원(등록 ID)과 `argHash = DataDigest(req.Data)`는 지금 그대로다. 형식 검사는 Gate 2c에서 한다.
   - URL 형식 거부(12)는 토큰 검증(Gate 1)보다 먼저 난다. 지금 Gate 0의 `INVALID_ARGUMENTS`(14)가 인증 전에 나는 것과 같은 성격(입력 해석)이며, 어느 쪽이든 거부다.
2. **Gate 2 · StageReplay**: 바꾸지 않는다. PDP는 `127.0.0.1:<port>`·`echo-safe`를 파일 경로와 똑같이 비교한다. 승인(`ask`)·Epoch·위임 계보도 그대로 걸린다.
3. **Gate 2c (경계 검사, `switch state.normAction`)**
   - `file:*`: 지금의 `Jail.ResolvePath`. `state.safePath`를 채운다.
   - `net:fetch`: `NetGuard == nil` → 16. `NetGuard.Check(state.resource)` 실패 → `EGRESS_DENIED`(12). Zone B에 그 포트의 Grant가 있어도 코드 측 allow-list에 없으면 거부된다.
   - `exec:run`: `ExecRunner == nil` → 16. `execguard.Validate(state.resource, string(req.Data))` 실패 → `EXEC_NOT_ALLOWED`·`EXEC_ARG_REJECTED`(12).
   - jti는 이미 StageReplay에서 소비됐다. 경계 위반에도 jti는 돌아오지 않는다(지금 Jail 위반 13과 같은 규칙).
4. **StageApproval**: 바꾸지 않는다. 바인딩의 `Resource`·`ArgHash`가 정규화된 값이므로 `/status`를 승인받고 `/admin`을 가져오면 `APPROVAL_MISMATCH`(18)다.
5. **Stage 3b (예산 사전 차감)**: 조건을 `state.budgeted && (normAction == file:write || normAction == exec:run)`으로 넓힌다. 차감량은 지금처럼 `Consume(jti, 1, 0, len(req.Data))`. `exec:run`은 프로세스 실행이라는 부작용이 있으므로 읽기처럼 사후 차감하지 않는다(025번 T-7).
6. **Stage 5 (실행, `switch`)**
   - `file:*`: 지금과 같다.
   - `net:fetch`: `data, err := NetGuard.Fetch(ctx, state.fetchTarget)`. 가드 오류는 그 사유 그대로(12·16). 예산 토큰이면 `Consume(jti, 1, len(data), 0)` 사후 차감, 실패하면 데이터를 버리고 `BUDGET_EXHAUSTED`. `res.Data = data`, `res.BytesRead = len(data)`.
   - `exec:run`: 실행 직전에 `state.consumed = false`로 둔다(실행이 시작되면 실패해도 환급하지 않는다 — 부작용이 이미 났을 수 있다). `out, err := ExecRunner.Run(ctx, id, string(req.Data))`. 예산 토큰이면 `Consume(jti, 0, len(out), 0)` 사후 차감, 실패하면 출력을 버리고 `BUDGET_EXHAUSTED`. `res.Data = out`, `res.BytesRead = len(out)`.
   - 성공 감사의 `result_hash`는 지금처럼 `DataDigest(res.Data)`다(응답 본문·표준 출력의 지문).
7. **`finalize`·`logEvent`**: 바꾸지 않는다. `step`은 `pep.net:fetch`·`pep.exec:run`, `resource`는 정규화된 값이 된다.

## 4. 인수 테스트 시나리오

| **TC-040-02** | `file:read:a.txt` 토큰으로 TC-040-01 요청 | Gate 2 `TOKEN_INSUFFICIENT_SCOPE`(12), 서버 요청 0 |
