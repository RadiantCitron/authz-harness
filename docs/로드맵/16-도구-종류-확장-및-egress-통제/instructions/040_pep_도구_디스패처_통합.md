## 1. 목적 및 배경

`020`의 `netguard`와 `030`의 `execguard`를 별도 우회 입구가 아닌 **기존 [`internal/authz/pep/gateway.go`](../../../../internal/authz/pep/gateway.go) 단일 입출구 파이프라인(`Gateway.Execute`)**에 통합하고, [`internal/subagent/worker.go`](../../../../internal/subagent/worker.go)가 `net:fetch` 및 `exec:run`의 실행 결과 바이트를 손실 없이 부모로 반환하도록 연동한다.

---

## 2. 파급 범위와 무영향 근거

- **변경**:
  - `internal/authz/pep/gateway.go`:
    - `Config`에 `NetGuard *netguard.Guard`, `ExecGuard *execguard.Guard` 선택 필드 추가 (미주입 시 기본 안전 인스턴스 초기화)
    - `NormalizeAction`에 `"net:fetch"` → `domain.ActionNetFetch`, `"exec:run"` → `domain.ActionExecRun` 추가
    - `runPipeline`에서 액션 종류별 정규화·인가·실행 배선 통합(`Execute` 함수 내 `return` 문 1개 불변식 `TC-060-04` 유지)
  - `internal/subagent/worker.go`:
    - `Execute` 결과 매핑(`worker.go:66`)에서 `domain.ActionFileRead`뿐 아니라 `domain.ActionNetFetch`, `domain.ActionExecRun`일 때도 `resp.BytesRead = pepRes.BytesRead` 및 `resp.Output = string(pepRes.Data)`를 채우도록 확장
  - `internal/cli/pep.go`: `renderResult`에서 `ActionNetFetch`, `ActionExecRun` 실행 시 응답 본문 출력 지원
  - `internal/authz/pep/tool_dispatch_test.go` [신규]: 3종 도구(`file`, `net`, `exec`)에 대한 PEP 관문 통합 단위 테스트
- **무영향**:
  - 기존 `file:read`, `file:write` 요청 처리 경로와 종료 코드는 그대로 보존된다.

## 3. 세부 명세

1. **`net:fetch` URL 정규화와 Gate 2(PDP) / Gate 2c(`netguard`) 순서 정합성**:
   - 호출자는 `req.Resource`에 요청 URL(예: `"http://127.0.0.1:18080/status"`) 또는 `host:port`를 전달하고, Grant 및 3단 스코프에는 정규화된 `host:port`(예: `"127.0.0.1:18080"`)가 등록된다.
   - 만약 `netguard`가 URL을 정규화하기 전에 PDP가 원시 URL 문자열(`"http://127.0.0.1:18080/status"` 또는 `"http://127.0.0.1@evil/"`)로 Grant 일치를 먼저 비교하면, 정상 URL도 `NO_ACTIVE_GRANT`로 거부되고 SSRF 우회 URL도 `EGRESS_DENIED`가 아닌 `NO_ACTIVE_GRANT`로 잘못 떨어지게 된다.
   - 이를 방지하기 위해 `state.normAction == domain.ActionNetFetch`일 때는:
     1. 토큰의 스코프가 `net:fetch` 액션 자체를 전혀 포함하지 않으면(예: `file:read` 전용 토큰) Gate 2에서 즉시 `ReasonTokenInsufficientScope(12)`를 반환한다.
     2. 토큰이 `net:fetch`(2단 또는 3단) 스코프를 보유한 경우, `netguard.ParseAndNormalizeTarget(state.resource)`로 URL 정규화·루프백 리터럴·Allow-List 포트를 먼저 검증하여 위반 시 즉시 `ReasonEgressDenied(12)`를 반환한다.
     3. 검증을 통과해 추출된 정규화 `hostPort`(`"127.0.0.1:18080"`)를 `state.resource`로 설정(원본 요청 URL은 `state.safePath`에 보존)하여 Gate 2 PDP가 Grant(`"127.0.0.1:18080"`) 및 3단 스코프(`"net:fetch:127.0.0.1:18080"`)와 정확히 대조하게 하고, Stage 5에서는 `netguard.Fetch(ctx, state.safePath)`로 실제 루프백 응답을 가져와 `res.Data`에 담는다.
2. **`exec:run` 검증 및 인자 해시(`ArgHash`) 자동 연동**:
   - `state.normAction == domain.ActionExecRun`일 때 `state.resource`는 논리 바이너리 ID(예: `"echo-safe"`), `req.Data`는 인자 바이트열이다.
   - Gate 2(PDP)에서 `exec:run:<id>` 스코프·Grant를 확인하고, Gate 2c에서 `execguard.ValidateRequest(state.resource, string(req.Data))`를 수행해 미등록 ID는 `ReasonExecNotAllowed(12)`, 비허용 인자(`-e`, `;` 등)는 `ReasonExecArgRejected(12)`로 차단한다.
   - Stage 4 및 `finalize` 감사 기록에서는 `state.resource`에 논리 ID만 기록되고 `req.Data` 원문은 로드맵 14 `030`의 `ArgHash`(`sha256:...`)로만 기록되며, Stage 5 실행 출력(`res.Data`)은 `ResultHash`로 기록된다.

3. **4종 전 도구 공통 예산(`BudgetLedger`) 차감 규약 ([013번 보고서](../../../보고서/013-5대_표준공학검증기법_기반_잔여로드맵_전수정밀진단_및_교정_보고서.md) `DEF-06`)**:
   - 로드맵 12의 예산 통제가 `file:*`에만 머물지 않고 `net:fetch`와 `exec:run`에도 상시 적용되도록, `verifiedClaims.Claims.Budget != nil`일 때 요청 입력 바이트(`len(req.Data)`)는 `WriteBytes`로, 도구 실행 결과 바이트(`len(res.Data)`: 파일 내용, HTTP 응답 본문, 프로세스 표준출력)는 `ReadBytes`로 `BudgetLedger.Consume`에 동일하게 정산한다(한도 초과 시 `res.Data = nil` 폐기 후 `ReasonBudgetExhausted(12)` 반환).
