## 1. 목적 및 배경

새 도구가 서브프로세스 워커 경로(실제 바이너리)에서 정상 동작하고, 표기 우회·리다이렉트·인자 주입·자원 폭주·PEP 우회가 모두 막힘을 G15 6대로 증명한다. 번호는 G14 다음인 `E2E-74`부터다(원안 `E2E-73`~`78`은 G14와 겹침).

판정은 기존 관례를 따른다.
- 거부는 종료 코드 + 마지막 감사 이벤트(`ExpectedAction`·`ExpectedDecision`·`ExpectedReason`) + **부모가 관찰한 사실**(시험 서버 요청 수, 리스너 accept 수, 출력)로 한다. 자식의 자기보고는 근거가 아니다.
- 부모 상한은 G9 E2E-42와 같은 `g9LimitExpectation`(17, `agent.limit_exceeded`, `deny`)을 쓴다.
- 커널 차단은 G10 E2E-47과 같은 대조군 쌍 + `ExitPathViolation`(13, 「차단 관찰됨」) + `agent.confined`·`allow` 관례를 쓴다. `CONFINEMENT_VIOLATION`이라는 사유는 없다.

원안 E2E-78(「netguard 우회 소켓 연결 → 격리 켬 차단」)은 E2E-47과 같으므로 버리고, 포트 단위 격리(055)를 증명하는 E2E-79로 바꿨다.

## 3. 시나리오 명세 (`G15`)

모든 시나리오는 `RequiresSubprocess: true`이며 Grant·토큰은 3단 스코프로 직접 발급한다.

| ID | 시나리오 | 입력 | 기대 Exit | 기대 감사 (Action / Decision / Reason) | 부모 관찰 증거 |
|:---:|---|---|:---:|---|---|
| `E2E-74` | 루프백 allow-list `net:fetch` 정상 실행 | 시험 서버 P, `-net-allow 127.0.0.1:P`, `net:fetch:127.0.0.1:P` Grant·토큰, `http://127.0.0.1:P/status` | `0` | `pep.allow` / `allow` / `AUTHORIZED` | 서버 요청 1. 감사 `resource = 127.0.0.1:P`, `arg_hash = DataDigest(정규 URL)`, `result_hash = DataDigest(본문)` |
| `E2E-75` | 표기 우회와 비허용 포트 차단 | ① `http://127.0.0.1:P@evil/` ② `http://2130706433:P/` ③ `http://localhost:P/` ④ Zone B에 Q의 Grant·토큰이 있는 `http://127.0.0.1:Q/`(allow-list는 P만) | `12` | `pep.deny` / `deny` / `EGRESS_DENIED` | 서버 P·Q 요청 0. 감사에 `evil` 문자열 0건. ④는 Grant가 있어도 코드 측 allow-list가 막음을 보인다 |
| `E2E-76` | 리다이렉트 차단 | 서버 P가 서버 R로 `302` 응답 (P만 allow-list) | `12` | `pep.deny` / `deny` / `EGRESS_DENIED` | 서버 R 요청 0, 워커 출력에 본문 없음 |
| `E2E-77` | `exec:run` 정상 실행 뒤 주입·미등록 ID 차단 | 대조: `echo-safe` + `hello_123` → 0, 출력 `hello_123`. 실험: `echo-safe` + `a;touch_pwned`, ID `sh`(Grant 있음) | `12` | `pep.deny` / `deny` / `EXEC_NOT_ALLOWED` (마지막 시도) | 대조 출력 일치(정책이 너무 좁은 가짜 차단 배제), 워크스페이스 무변화, 앞 시도의 감사 사유 `EXEC_ARG_REJECTED` |
| `E2E-78` | 부모 출력 상한이 새 도구에도 걸림 | 서버 P가 64 KiB 본문, 스포너 `Limits.MaxOutputBytes = 16 KiB`(가드 기본 상한 1 MiB보다 작게) | `17` | `agent.limit_exceeded` / `deny` / `RESOURCE_OUTPUT_LIMIT` (`g9LimitExpectation`) | 부모가 받은 출력 ≤ 16 KiB. 가드 상한(12)이 아니라 부모 상한(17)이 먼저 걸림 |
| `E2E-79` | 포트 단위 격리 대조군 쌍 | 정책 `WorkerPolicy` + `AllowConnectPorts=[P]`. ① 격리된 **정직 워커**의 `net:fetch` P ② faultworker `bypass_open_socket` → 리스너 Q: 대조군(Noop) / 실험군(플랫폼 격리) | `13` | `agent.confined` / `allow` (E2E-47 관례) | ① 0, 서버 P 요청 1 ② 대조군 Q accept 1, 실험군 Q accept 0 |

- E2E-75·77은 한 시나리오 안에서 여러 시도를 하고, 앞 시도들의 종료 코드·사유를 `Invariantf`로 확인한 뒤 마지막 시도의 종료 코드를 반환한다. 시도마다 새 토큰을 쓴다(jti는 PDP allow 뒤 소비되므로 Gate 2c 거부에서도 소진된다).
- E2E-79는 `RequiresConfinement: true`다. 격리를 쓸 수 없는 환경에서는 G10과 같은 방식으로 건너뛴다.
- E2E-74의 Grant에 `RequiresApproval`은 쓰지 않는다(승인과 새 도구의 결합은 040 TC-040-07로 증명).
