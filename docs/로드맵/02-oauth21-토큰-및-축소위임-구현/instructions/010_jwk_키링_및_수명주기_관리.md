> **상위 대시보드**: [README.md](../README.md) | **마스터 설계**: [ROADMAP.md](../ROADMAP.md)

## 1. 목적 (Context & Why)

본 지시서는 OAuth 2.1 및 RFC 9068 Bearer Access Token 서명과 검증(Gate 1)의 신뢰 기반(Root of Trust)이 되는 **Zone A/B 비대칭 서명 키 링(Key Ring)**과 **RFC 7517 키 수명주기 관리자**를 구축하는 작업이다.

보안 불변식에 따라:
1. 비밀 서명 키는 **Zone A (`./.authz-state/private/signing_keys.priv.json`)**에만 격리하여 저장하며, 외부 워커나 하위 프로세스가 메모리에 올리는 것을 원천 차단한다.
2. 검증에 필요한 공개 키 목록은 RFC 7517 JWK Set 형식으로 **Zone B (`./.authz-state/public/jwks.pub.json`)**에 원자적으로 동기화하여 검증기(Verifier)와 PIP가 읽기 전용으로 안전하게 참조하게 한다.
3. 키 식별자(`kid`)를 기반으로 **`active` (서명/검증 가능) -> `verify-only` (키 회전 후 기존 토큰 검증만 허용) -> `retired` (키 폐기, 즉시 무효화)**의 3단계 상태 머신을 완성하고 CLI 명령(`keys list`, `keys rotate`, `keys revoke`)으로 제어한다.

## 2. 패키지 배치 및 6계층 DAG 구조

```text
Layer 5:  [cmd/authz-harness] ──> [internal/cli] (keys list/rotate/revoke)
                                      │
Layer 2A:                             v
          [internal/authn/keys] (KeyManager, FileStore, JWK Generator)
            │               │
            v               v
Layer 1:  [internal/audit]  (key.created, key.rotated, key.revoked 이벤트 기록)
            │
            v
Layer 0:  [internal/domain] (Key, KeyStatus, JWK, JWKS, KeyReason, ExitCode)
```

- **Layer 0 (`internal/domain`)**: JWK, JWKS, KeyStatus, ExitCode 등 순수 도메인 모델 정의.
- **Layer 1 (`internal/audit`)**: 키 수명주기 변경에 대한 해시 체인 감사 추적.
- **Layer 2A (`internal/authn/keys`)**: Zone A 비밀키 및 Zone B 공개키 파일의 배타적 잠금(`flock`) 및 Atomic Rename 동기화 관리.
- **Layer 5 (`internal/cli`)**: 운영자 및 하네스 러너 대상 `keys` 명령군 제공.

## 3. 세부 설계 및 JSON 스키마

### 3.1 Zone A 비밀 서명 키 저장소 스키마 (`signing_keys.priv.json`)
- 경로: `./.authz-state/private/signing_keys.priv.json` (퍼미션 `0600`)
- 암호 알고리즘: `Ed25519` (`kty: OKP`, `crv: Ed25519`, `alg: EdDSA`) — Go 표준 라이브러리 `crypto/ed25519` 활용.

```json
{
  "version": 1,
  "updated_at": "2026-11-01T18:50:00Z",
  "active_kid": "key-20261101-01",
  "keys": [
    {
      "kid": "key-20261101-01",
      "kty": "OKP",
      "crv": "Ed25519",
      "alg": "EdDSA",
      "status": "active",
      "pub": "<base64url-encoded-public-key>",
      "priv": "<base64url-encoded-private-seed>",
      "created_at": "2026-11-01T18:50:00Z",
      "rotated_at": null,
      "retired_at": null
    }
  ]
}
```

### 3.2 Zone B 공개 검증 키 링 스키마 (`jwks.pub.json`)
- 경로: `./.authz-state/public/jwks.pub.json` (퍼미션 `0644`, RFC 7517 호환)
- **Zero Leakage 규칙**: `priv` 필드는 절대 기록되지 않으며 오직 공개 파라미터(`x`)만 노출.

```json
{
  "version": 1,
  "updated_at": "2026-11-01T18:50:00Z",
  "keys": [
    {
      "kid": "key-20261101-01",
      "kty": "OKP",
      "crv": "Ed25519",
      "alg": "EdDSA",
      "use": "sig",
      "status": "active",
      "x": "<base64url-encoded-public-key>",
      "created_at": "2026-11-01T18:50:00Z",
      "rotated_at": null,
      "retired_at": null
    }
  ]
}
```

### 3.3 핵심 인터페이스 계약 (`internal/authn/keys`)

```go
type KeyManager interface {
    // ListKeys 는 현재 키 링의 모든 공개 메타데이터와 상태를 반환한다.
    ListKeys() ([]domain.JWK, error)

    // GetActiveSigningKey 는 토큰 서명에 사용할 현재 활성(active) 개인키를 반환한다.
    GetActiveSigningKey() (*domain.SigningKey, error)

    // GetVerificationKey 는 kid에 해당하는 공개 검증 키를 반환한다. (retired 키는 에러 반환)
    GetVerificationKey(kid string) (*domain.JWK, error)

    // RotateKey 는 새 Ed25519 키를 생성하여 active로 설정하고 기존 active 키를 verify-only로 전이한다.
    RotateKey(auditCtx domain.AuditContext) (*domain.JWK, error)

    // RevokeKey 는 지정한 kid의 키를 retired 상태로 전이하여 해당 키로 서명된 모든 토큰을 즉시 무효화한다.
    RevokeKey(kid string, auditCtx domain.AuditContext) error
}
```

## 4. 작업 내역 및 산출물 (구현 대상)

1. `internal/domain/key.go`:
   - `KeyStatus`: `active`, `verify-only`, `retired` 상수 정의
   - `JWK`: RFC 7517 표준 구조체 (`kid`, `kty`, `crv`, `alg`, `use`, `status`, `x`, 타임스탬프)
   - `JWKS`: `keys` 배열 래퍼
   - `SigningKey`: 내부 서명용 구조체 (`kid`, `alg`, `ed25519.PrivateKey`, `ed25519.PublicKey`)
2. `internal/domain/constants.go`:
   - 토큰 및 키 관련 Reason 추가 (`ReasonTokenKeyRetired`, `ReasonTokenInvalidSignature`, `ReasonTokenKeyNotFound`)
3. `internal/authn/keys/store.go`:
   - Zone A 및 Zone B 디렉토리 자동 생성 및 파일 락(`flock`) 동시성 제어
   - Ed25519 키 쌍 생성 및 Base64URL 인코딩 유틸리티
   - Atomic Rename 기반 Zone A / Zone B 동시 갱신 트랜잭션
4. `internal/authn/keys/manager.go`:
   - `KeyManager` 구현체 및 상태 전이 검증 (예: 이미 retired된 키의 중복 폐기 방지, active 키 없는 상태 방지)
   - `internal/audit.Writer` 감사 이벤트(`key.created`, `key.rotated`, `key.revoked`) 연동 (Zero Leakage 준수)
5. `internal/authn/keys/keys_test.go`:
   - 초기화, 회전, 폐기 수명주기 전이 단위 테스트
   - Zone B 및 감사 로그 내 개인키 누출 여부 전수 검사 (Zero Leakage 테스트)
   - 다중 고루틴 동시 접근 race-free 검증 (`-race`)
6. `internal/cli/keys.go`:
   - `authz-harness keys list`: 표 형식 시각화 출력 (KID, ALGORITHM, STATUS, CREATED_AT)
   - `authz-harness keys rotate`: 새 키 생성 및 회전 알림
   - `authz-harness keys revoke --kid <kid>`: 키 폐기 알림
7. `cmd/authz-harness/main.go`:
   - `keys` 서브커맨드 라우팅 배선

## 5. 사전 인수 테스트 시나리오 (Acceptance Scenarios)

- **시나리오 1 (최초 자동 초기화)**: 상태 디렉토리가 비어 있을 때 `KeyManager` 초기화 시 최초 활성 키(`active`) 1개가 자동 발급되고, Zone A(`signing_keys.priv.json`)와 Zone B(`jwks.pub.json`)가 정합성을 유지하며 생성된다.
- **시나리오 2 (키 점진적 회전 — verify-only)**: `keys rotate` 호출 시 신규 키가 `active`가 되고 기존 키는 `verify-only`로 변경된다. 두 키 모두 Zone B에서 조회 가능하지만, `GetActiveSigningKey`는 신규 키만 반환한다.
- **시나리오 3 (키 긴급 폐기 — retired)**: `keys revoke --kid <kid>` 호출 시 대상 키 상태가 `retired`로 변경된다. `GetVerificationKey` 호출 시 `ErrKeyRetired` 에러를 반환하여 검증기가 즉시 거부(`TOKEN_KEY_RETIRED`)할 수 있게 한다.
- **시나리오 4 (Zero Leakage 불변식)**: Zone B 파일(`jwks.pub.json`) 내용 및 `audit.jsonl`에 기록된 이벤트 페이로드를 전체 검색했을 때 `priv` 필드 또는 시드 바이트가 일절 존재하지 않아야 한다.
- **시나리오 5 (CLI 사용자 경험)**:
  - `authz-harness keys list` -> 활성 키 목록 표 출력 (종료 코드 `0`).
  - `authz-harness keys rotate` -> `"Key rotated successfully. New active kid: ..."` 출력 (종료 코드 `0`).
  - `authz-harness keys revoke --kid <kid>` -> `"Key revoked successfully. Kid: ..."` 출력 (종료 코드 `0`).
  - 존재하지 않는 kid 폐기 시 -> `EXIT_BAD_INPUT(14)` 또는 명확한 에러 메시지와 함께 비정상 종료.

## 6. 4층위 검증 방법

1. **1층위**: `python3 scripts/public_safety_scan.py --tree`로 개인키 하드코딩 여부 스캔.
2. **2층위**: `go test -v -race ./internal/authn/keys/...`로 상태 전이 및 동시성 100% 통과.
3. **3층위**: 키 회전 및 폐기 후 `audit.jsonl`의 해시 체인 무결성(`audit verify`) 확인.
4. **4층위**: 빌드된 CLI 바이너리로 `keys list` -> `keys rotate` -> `keys list` -> `keys revoke` 시나리오 검증.
