## 1. 목적 (Context & Why)

본 지시서는 OAuth 2.1 및 [RFC 8693(OAuth 2.0 Token Exchange)](https://datatracker.ietf.org/doc/html/rfc8693) 표준에 부합하는 **축소 위임(Downscoping) 및 위임 계보(`act` 클레임) 검증 엔진**을 구축하는 작업이다.

멀티 에이전트 환경에서 오케스트레이터(팀장 워크로드)가 서브에이전트(작업자 워크로드)에게 작업을 분배할 때, 자신이 부여받은 권한의 일부만을 안전하게 위임하고 위임 체인을 투명하게 추적할 수 있어야 한다. 본 단계에서는 부모 토큰의 무결성 검증, 권한 단조 감소(Monotonic Scope/TTL Reduction), 위임 계보 보존, 깊이 제한을 강제하여 권한 상승(Privilege Escalation) 공격을 원천 차단한다.

### 보안 불변식 및 설계 원칙

1. **단조 감소(Monotonic Reduction / Downscoping)**:
   - **Scope 부분집합 불변식**: 자식 토큰의 Scope 집합은 부모 토큰 Scope 집합의 엄격한 부분집합이어야 한다 ($S_{child} \subseteq S_{parent}$). 부모가 소유하지 않은 권한을 단 하나라도 요청하면 `DELEGATION_SCOPE_EXCEEDED` 사유로 원천 거부한다.
   - **만료 시각 상한 불변식**: 자식 토큰의 만료 시각($exp_{child}$)은 부모 토큰의 만료 시각($exp_{parent}$)을 절대 초과할 수 없다 ($exp_{child} \le exp_{parent}$). 부모 잔여 TTL을 초과하는 요청은 `DELEGATION_TTL_EXCEEDED` 사유로 즉시 거부한다.
2. **Gate 1 부모 토큰 무결성 선행 검증 강제**:
   - 위임 요청에 제출된 부모 토큰(`subject_token`)은 발급 전 반드시 Step 020의 `TokenVerifier`를 거쳐 암호학적 서명, 키 상태(`retired` 여부), 만료 여부(`exp`), Replay 여부 등 9단계 검증을 모두 통과해야 한다. 유효하지 않은 부모 토큰은 교환 자체가 불가능하다.
3. **위임 계보(`act` Claim) 및 깊이(`delegation_depth`) 추적**:
   - RFC 8693 §4.1 표준에 따라 자식 토큰 클레임에 `act` (`actor`: 부모 `sub`, 부모 `jti`) 필드를 기록한다.
   - 다단계 위임 시 `act` 체인을 중첩 구조(`act.act`)로 보존하며, 무한 위임 체인 공격을 방지하기 위해 최대 위임 깊이(`MaxDelegationDepth = 3`) 초과 시 `DELEGATION_DEPTH_EXCEEDED` 사유로 차단한다.
4. **자기 순환 위임 방지 (Self-Loop Prevention)**:
   - 부모 Subject와 자식 Subject가 동일하거나, 기존 `act` 위임 계보에 자식 Subject가 이미 존재하는 경우 순환 위임(`DELEGATION_SELF_LOOP`)으로 판정하여 거부한다.
5. **Zero Leakage 및 감사 증거 분리**:
   - 위임 성공(`token.exchanged`) 및 위임 거부(`authn.exchange_denied`) 시 원시 토큰 문자열(Raw JWT)은 디버그/감사 로그에 일절 노출하지 않고, 오직 `parent_jti`, `child_jti`, `parent_sub`, `child_sub`, `granted_scope` 메타데이터만 `audit.jsonl`에 해시 체인으로 기록한다.

## 2. 패키지 배치 및 6계층 DAG 구조

```text
Layer 5:  [cmd/authz-harness] ──> [internal/cli] (token exchange)
                                       │
Layer 2A:                             v
          [internal/authn/exchange] (ExchangeService, DownscopeValidator)
             │                │                │
             v                v                v
Layer 2A: [internal/authn/token] (TokenIssuer, TokenVerifier, ClientRegistry)
             │                │
Layer 1:     v                v
          [internal/audit]  (token.exchanged, authn.exchange_denied 이벤트)
             │
Layer 0:     v
          [internal/domain] (ActorClaim, TokenClaims 확장, Reason, ExitCode, Clock)
```

- **Layer 0 (`internal/domain`)**: `ActorClaim` 구조체 정의, `TokenClaims`에 `act` 및 `delegation_depth` 필드 추가, 축소 위임 관련 `Reason` 상수 정의.
- **Layer 1 (`internal/audit`)**: `token.exchanged`, `authn.exchange_denied` 감사 이벤트 기록.
- **Layer 2A (`internal/authn/token`)**: 부모 토큰 검증(`TokenVerifier`), 자식 토큰 서명 발급(`TokenIssuer`), 클라이언트 인증(`ClientRegistry`).
- **Layer 2A (`internal/authn/exchange`)**: RFC 8693 Token Exchange 엔진, Scope 부분집합 검증기, TTL 상한 검증기, 계보 체인 생성기.
- **Layer 5 (`internal/cli`)**: `authz-harness token exchange` CLI 서브커맨드 라우팅 및 계보 트리 시각화 출력.

### 3.3 Scope 부분집합 판정 알고리즘

- 공백으로 구분된 문자열을 파싱하여 정규화된 스코프 슬라이스로 분리:
  예: `"file:read:docs/plan.txt  file:write:docs/out.txt "` -> `["file:read:docs/plan.txt", "file:write:docs/out.txt"]`
- 자식 스코프 $S_{child}$의 모든 항목 $s$에 대해 $s \in S_{parent}$ 만족 여부를 판정:
  - 부모에게 존재하지 않는 항목이 1개라도 감지되면 즉시 거부하고, 위반된 스코프 항목 목록을 에러 세부 정보에 포함.
  - 빈 스코프 요청: 자식 스코프가 비어있는 경우 최소 권한 위임 거부(`DELEGATION_SCOPE_EMPTY`).
  - 접두사 착시(Prefix Confusion) 방지: 단순 `strings.HasPrefix`를 사용하지 않고 개별 토큰 단위의 완전 일치(Exact Match) 집합 포함 관계를 엄격히 검증.

### 3.4 핵심 인터페이스 계약 (`internal/authn/exchange`)

```go
// ExchangeRequest 는 RFC 8693 Token Exchange 요청 명세다.
type ExchangeRequest struct {
    ClientID     string
    ClientSecret string
    ParentToken  string
    ChildSubject string
    Scope        string
    Audience     string
    TTL          time.Duration
}

// ExchangeResult 는 토큰 교환 결과다.
type ExchangeResult struct {
    TokenString     string             `json:"token"`
    Claims          domain.TokenClaims `json:"claims"`
    ParentJTI       string             `json:"parent_jti"`
    DelegationDepth int                `json:"delegation_depth"`
}

// DownscopeValidator 는 권한 축소 및 위임 불변식 검증 포트다.
type DownscopeValidator interface {
    ValidateDownscope(parentClaims *domain.TokenClaims, childSub, requestedScope string, childTTL time.Duration, now time.Time) error
}

// Service 는 RFC 8693 Token Exchange 오케스트레이션 서비스다.
type Service interface {
    Exchange(ctx context.Context, req ExchangeRequest, auditCtx domain.AuditContext) (*ExchangeResult, error)
}
```

## 4. 작업 내역 및 산출물 (구현 대상)

1. **`internal/domain` (모델 및 사유 코드 확장)**:
   - `ActorClaim`: RFC 8693 `act` 구조체 (`Subject string`, `JWTID string`, `Actor *ActorClaim`).
   - `TokenClaims` 확장:
     - `Actor *ActorClaim` (`json:"act,omitempty"`)
     - `DelegationDepth int` (`json:"delegation_depth,omitempty"`)
   - 표준 `Reason` 추가:
     - `ReasonDelegationScopeExceeded = "DELEGATION_SCOPE_EXCEEDED"`
     - `ReasonDelegationTTLExceeded = "DELEGATION_TTL_EXCEEDED"`
     - `ReasonDelegationDepthExceeded = "DELEGATION_DEPTH_EXCEEDED"`
     - `ReasonDelegationSelfLoop = "DELEGATION_SELF_LOOP"`
     - `ReasonDelegationScopeEmpty = "DELEGATION_SCOPE_EMPTY"`
2. **`internal/authn/exchange/validator.go` (축소 위임 검증기)**:
   - `DownscopeValidator` 구현체.
   - Scope 부분집합 판정: Set Inclusion 검증 및 초과 항목 산출.
   - TTL 상한 판정: $exp_{child} \le exp_{parent}$.
   - 깊이 판정: `parent.DelegationDepth + 1 <= MaxDelegationDepth(3)`.
   - 순환 검증: `childSub == parent.Subject` 및 `act` 체인 순환 순회 탐지.
3. **`internal/authn/exchange/service.go` (Token Exchange 서비스)**:
   - 클라이언트 인증(`ClientRegistry`).
   - 부모 토큰 Gate 1 무결성 검증(`TokenVerifier.VerifyToken`).
   - 축소 위임 검증(`DownscopeValidator.ValidateDownscope`).
   - `act` 체인 구성 (부모 `sub`/`jti` 및 기존 `parent.Actor`를 하위로 중첩).
   - 자식 토큰 발급 (`TokenIssuer`).
   - `internal/audit.Writer`를 통해 `token.exchanged` 및 실패 시 `authn.exchange_denied` 해시 체인 감사 기록.
4. **`internal/authn/exchange/exchange_test.go` (단위, 경계값, 동시성, 퍼징)**:
   - 10대 사전 인수 시나리오 단위 테스트.
   - `FuzzScopeValidator`: 공백, 쉼표, 개행, 악의적 문자열 파싱 시 패닉 및 부정 판정 방어.
   - 다중 고루틴 동시 교환 요청 검증 (`-race`).
5. **`internal/cli/token.go` 및 `internal/cli/token_test.go` (CLI 확장)**:
   - `authz-harness token exchange` 서브커맨드 라우팅.
   - 플래그: `--parent-token`, `--child-sub`, `--scope`, `--ttl`, `--client-id`, `--client-secret`, `--aud`, `--clock-offset`.
   - 초보자 친화적 위임 계보 트리 출력:
     ```text
     ┌─────────────────────────────────────────────────────────────┐
     │ RFC 8693 Token Exchange & Downscoping Pipeline [SUCCESS]    │
     ├─────────────────────────────────────────────────────────────┤
     │ Parent Token:  [VALID] jti: a1b2c3d4... (sub: orchestrator) │
     │ Scope Reduced: [OK] 2 scopes -> 1 scope (Subset Validated)  │
     │ TTL Bound:     [OK] 30m0s <= 59m42s remaining               │
     │ Actor Chain:   orchestrator -> worker-01 (Depth: 1)         │
     ├─────────────────────────────────────────────────────────────┤
     │ Delegated Child Token Issued:                               │
     │ eyJhbGciOiJFZERTQSI...                                      │
     └─────────────────────────────────────────────────────────────┘
     ```
   - 실패 시 사유 박스 및 표준 종료 코드(`0` 또는 `11`) 매핑.
6. **`cmd/authz-harness/main.go`**:
   - `token exchange` 명령어 배선 및 플래그 연동 확인.

## 5. 사전 인수 테스트 시나리오 (Acceptance Scenarios)

- **시나리오 1 (정상 축소 위임 및 `act` 클레임 생성)**:
  - 입력: 부모 토큰 Scope `"file:read:docs/plan.txt file:write:docs/out.txt"`, 자식 요청 Scope `"file:read:docs/plan.txt"`, 자식 요청 TTL 30분 (부모 잔여 1시간).
  - 기대 결과: 정상 발급 (`ExitSuccess 0`), 자식 토큰의 `act.sub == "orchestrator"`, `delegation_depth == 1`. `audit.jsonl`에 `token.exchanged` 해시 체인 이벤트 기록.
- **시나리오 2 (부모 Scope 초과 요청 차단)**:
  - 입력: 부모 Scope `"file:read:docs/plan.txt"`, 자식 요청 Scope `"file:read:docs/plan.txt file:write:docs/secret.txt"`.
  - 기대 결과: 교환 거부, 사유 `DELEGATION_SCOPE_EXCEEDED`, 종료 코드 `11` (`ExitTokenInvalid`), `audit.jsonl`에 `authn.exchange_denied` 기록.
- **시나리오 3 (부모 잔여 TTL 초과 요청 차단)**:
  - 입력: 부모 잔여 유효 시간 10분, 자식 요청 TTL 30분.
  - 기대 결과: 교환 거부, 사유 `DELEGATION_TTL_EXCEEDED`, 종료 코드 `11`.
- **시나리오 4 (변조된 부모 토큰 제출 시 교환 차단)**:
  - 입력: `--tamper-signature`로 서명이 변조된 부모 토큰으로 `token exchange` 시도.
  - 기대 결과: 부모 Gate 1 검증 실패, 사유 `TOKEN_INVALID_SIGNATURE`, 종료 코드 `11`.
- **시나리오 5 (만료된 부모 토큰 제출 시 교환 차단)**:
  - 입력: 가상 시계 `--clock-offset +2h`로 만료 상태인 부모 토큰 제출.
  - 기대 결과: 부모 Gate 1 검증 실패, 사유 `TOKEN_EXPIRED`, 종료 코드 `11`.
- **시나리오 6 (서명 키 폐기된 부모 토큰 제출 시 교환 차단)**:
  - 입력: 부모 토큰 발급 후 해당 키에 대해 `keys revoke` 수행, 이후 해당 부모 토큰으로 교환 시도.
  - 기대 결과: 부모 Gate 1 검증 실패, 사유 `TOKEN_KEY_RETIRED`, 종료 코드 `11`.
- **시나리오 7 (다단계 위임 및 최대 깊이 초과 차단)**:
  - 입력: Depth 1 -> Depth 2 -> Depth 3 위임 후, Depth 3 토큰으로 Depth 4 위임 시도 (`MaxDelegationDepth = 3`).
  - 기대 결과: 교환 거부, 사유 `DELEGATION_DEPTH_EXCEEDED`, 종료 코드 `11`.
- **시나리오 8 (동일 주체 순환 위임 차단)**:
  - 입력: 부모 Subject가 `worker-01`인데 `--child-sub worker-01`로 요청하거나, 상위 `act` 체인에 이미 존재하는 Subject로 재위임 시도.
  - 기대 결과: 교환 거부, 사유 `DELEGATION_SELF_LOOP`, 종료 코드 `11`.
- **시나리오 9 (Zero Leakage 및 감사 증거 분리 검증)**:
  - 입력: `token exchange` 정상 성공 및 실패 후 `audit.jsonl` 전수 검사.
  - 기대 결과: 부모 및 자식의 원시 JWT 토큰 문자열이 일절 기록되지 않고, `parent_jti`, `child_jti`, `parent_sub`, `child_sub`, `granted_scope`만 기록됨.
- **시나리오 10 (발급된 자식 토큰의 Gate 1 및 inspect UX 검증)**:
  - 입력: `token exchange`로 발급받은 자식 토큰에 대해 `token verify` 및 `token inspect` 실행.
  - 기대 결과: `token verify` Gate 1 `[PASS]`, `token inspect` 결과 JSON에 `act` 객체 및 `delegation_depth`가 명확히 표시됨.

## 6. 4층위 검증 방법

1. **1층위 (자동화 정적 분석)**:
   - `python3 scripts/public_safety_scan.py --tree` 실행으로 비밀키 및 시크릿 유출 여부 점검.
2. **2층위 (단위 및 퍼징 검증)**:
   - `go test -v -race ./internal/authn/exchange/...` 실행 (100% 통과).
   - `go test -fuzz=FuzzScopeValidator -fuzztime=10s ./internal/authn/exchange/...` 퍼징 방어 검증.
3. **3층위 (상태 및 감사 정합성 검증)**:
   - 교환 전후 `audit.jsonl`의 해시 체인 무결성 확인 (`authz-harness audit verify`).
4. **4층위 (CLI E2E 검증)**:
   - `token issue` -> `token exchange` -> `token inspect` -> `token verify` 체인 시연 및 초과 위임 거부 동작 확인.
